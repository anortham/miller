## Fixed Miller UTF-16 follow-up after julie-extract 2.5.1

- **WHAT:** Added Miller-side decoding for BOM-marked UTF-16LE/UTF-16BE source bytes after the extractor pin moved to `julie-extract 2.5.1`.
- **WHY:** `julie-extract 2.5.1` can now index BOM-marked UTF-16 SQL files, but Miller still re-read workspace files as UTF-8 in derived/read paths. That caused `inspect --depth full` body text to render as NUL-padded junk and content/source search to skip the file as non-UTF8.
- **HOW:** Added shared `SourceTextDecoder` in `Miller.Indexing`; routed content corpus writing, legacy content projection loading, `ExtractReader.ReadBody`, and source-region search indexing through it. Hash checks and `source_bytes` remain based on original disk bytes; byte spans are still sliced as UTF-8 byte offsets over decoded source text. Added regression coverage for body slicing, content corpus/source search, and source-region slicing from a UTF-16LE BOM file.
- **IMPACT:** Miller now matches the extractor's new accepted source encodings for downstream display/search surfaces while malformed/unsupported encoding still fails closed.
