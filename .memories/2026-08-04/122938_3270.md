## v1.16.0 levels dogfood — round-1 timings + four tool findings

Dogfooded all nine MCP tools against Miller 1.16.0+98b63273 and benchmarked progressive
indexing levels (`MILLER_INDEX_LEVELS`) cold-open vs blocking-full across local repos.

### Method
Harness at `scratchpad/bench-levels.sh`: wipe `.miller`, `workspace open` under a policy,
then `workspace full` to upgrade. Serial runs on purpose — the machine-wide scan governor
shares admission, so parallel runs would contaminate wall-clock.

### Round-1 A/B (progressive symbols-first vs `MILLER_INDEX_LEVELS=full`)
- **openclaw** (16,019 tracked files, 660,921 symbols): 48.7s → symbols (1.8 GB),
  +175.8s upgrade → full (4.8 GB). Blocking full: 160.6s.
  **3.3× faster to first usable, +40% total indexing work.**
- **graphify** (29,370 symbols): 2.4s → symbols; blocking full 7.7s.
  **3.2× faster to first usable, +14% total work.**
- Overhead ratio grows with repo size — the symbols pass is thrown away when the full
  rebuild promotes over it.

### Findings
1. **Validation errors are logged as `internal_failure`.** A bad `mode=markers` marker list
   and an ambiguous workspace selector both recorded `error_category=internal_failure` in
   telemetry, while the correct buckets (`bad_input`, `unknown_workspace`) already exist and
   are used elsewhere. 165 rows machine-wide are `internal`/`internal_failure` +
   InvalidOperationException — inflates the `errors=N` health warning.
2. **`inspect` on a nonexistent path says "No indexed symbols in \<path\>"** (`expected_empty`),
   indistinguishable from a real-but-empty file. A typo'd path reads as "file has no symbols".
3. **`mode=markers` reinterprets `query` as the marker list**, undocumented in the MCP tool
   description — an agent passing a phrase gets a confusing error. (markers itself is correct;
   it reads extractor marker facts and does cover doc_comment.)
4. **`SidecarStagingReaper` is build-triggered only** (called from `SearchIndexWriter.Write` /
   `ContentCorpusWriter`), so a workspace whose builds keep failing never reaps. Found
   1.18 GB of orphaned `.search-build-*.db` in `~/.hermes/hermes-agent/.miller`, whose
   registry row is stuck in a scan error.

### Measurement trap worth remembering
A `find(1)` code-file sweep is a bad size proxy: sealab looked like a 25,722-file repo and has
113 git-tracked files (rest vendored/ignored). Symbols count or `git ls-files` is the real
signal. Round-1 sealab/miller-python numbers are therefore not large-repo datapoints.

### Also observed
openclaw open log: `scan_duration_ms: 25341` vs `duration_ms: 48296` — roughly half of a
symbols-level open is Miller-side sidecar building (search.db/content.db/vectors), which
levels does not accelerate.
