## Turso versus SQLite research for Miller

### WHAT
Researched current Turso Database/libSQL positioning and compared it to Miller's live SQLite architecture.

### WHY
Miller uses SQLite as a public/local artifact contract (`symbols.db` from julie-extract plus Miller-owned `search.db`, `content.db`, registry, and telemetry). A storage swap could break reliability, FTS, local-first behavior, and package simplicity.

### HOW
Checked Miller repo surfaces with Miller MCP: `FullRebuildPromotion`, `WorkspaceRegistry`, `WorkspaceIndexProvider`, `SearchIndexWriter`, `ContentCorpusSchema`, and `content-corpus-v1`. Verified current upstream Turso docs/GitHub: Turso Database is a Rust rewrite of SQLite, latest stable release is 0.6.1 with 0.7.0 prereleases, the README still warns it is not SQLite-level production-ready for mission-critical use, compatibility is partial, SQLite FTS3/4/5 is not supported, and .NET bindings exist as `Turso.Data.Sqlite` but have caveats around raw SQLite handles, FTS virtual tables, and async behavior.

### IMPACT
Recommended keeping SQLite as Miller's production substrate. Promising Turso experiments are narrow: optional semantic/vector sidecar for a future non-core product layer, optional sync for non-sensitive telemetry/registry sharing, and a compatibility/performance spike against `.NET` bindings. Avoid uploading `content.db` or source-derived artifacts to Turso Cloud by default.
