## v1.19.0 shipped; fast-suite flakiness measured at ~30% and partly fixed

### WHAT shipped

**Miller v1.19.0 is published and live.** Stable, not a draft, 8 assets (4 archives + 4 `.sha256`),
release body carries the real notes from `docs/release-notes/v1.19.0.md` (the workflow picked them up —
no `gh release edit` was needed). Release run #116 succeeded on tag commit `0da4f60a`.

Three commits pushed to `main`:
- `0da4f60a` release: prepare 1.19.0
- `3ad8164f` docs: README → live v1.19.0 facts + release verification finding
- `e18e8b64` test: raise two starved-thread-pool backstops + flakiness finding

### The flakiness discovery (the important part)

Ten consecutive fast-suite runs on ONE unchanged tree produced **three failures, three different
tests, three different mechanisms**. The suite is ~30% red on good code.

1. `BootstrapAdmissionRetryTests.AStoreRollbackFailureRetriesUntilTheBootstrapBinds` — 5 s,
   hardcoded deadline starved by thread-pool contention. **FIXED** (5 s → 60 s, plus its latent twin
   `WorkspaceBindingServiceTests.WaitUntilAsync`).
2. `JulieSchemaGateTests.Verify_MissingRequiredSchemaFiveTable_ThrowsNamingTheTable("pending_resolutions")`
   — 88 ms, NOT a timeout. **Undiagnosed.**
3. `SharedSemanticBrokerConnectionFactoryTests.ExitedOwner_IsRetiredBeforeTheReplacementOverwritesItsHandles`
   — 570 ms, `Assert.NotNull`. **Undiagnosed.**

This explains CI: #342 and #343 ran the SAME commit and disagreed; #344's red `windows-fast` went
green on #345 with only a docs diff. **A single red CI run on this repo is not evidence of a
regression.**

### A retraction worth remembering

I confidently told the user the CI failures were caused by process-global `SetCurrentDirectory` /
`SetEnvironmentVariable` mutations under xUnit parallelism. **The evidence contradicted that** —
instance 1 was a timeout budget. Those mutations are a real hazard (7 CWD sites in
`WorkspaceBindingServiceTests`, 16 env sites in `CliDispatchTests`, 11 in `VectorConvergeServiceTests`,
no `DisableTestParallelization` anywhere) but are NOT an established cause. Recorded as a hazard,
not a diagnosis.

### Another methodology lesson

Running the two affected classes alone 10 times passed 10/10 — and that proves **nothing**, because
29 tests in isolation have none of the contention that causes the failure. Only full-suite runs
reproduce it. Do not accept a focused-run green as proof for a contention flake.

### Two failed local reproductions, both invalid for the same reason

A live Miller MCP server (pid 34388) holds `src/Miller.Server/bin/Release/net10.0/*.dll`, so Release
had to build into a scratch artifacts path. That breaks three separate fixture path walks:
`ScaleTestSupport.RepoRoot` (fixable via `EROS_WORKSPACE_ROOT`),
`SharedSemanticBrokerConnectionFactoryTests.RequireBrokerHostExecutable`, and the private
`DashboardFragmentCachingTests.RepoRoot`. A faithful local Release run needs that server stopped.
