## Dogfooded Miller 1.18.1 after restart

### WHAT

Exercised workspace lifecycle, lexical/semantic/content/source search, patterns, inspect, trace, impact, context, edit preview, and CLI version/capability contracts against the live Miller repository.

### WHY

The newly rebuilt 1.18.1 server needed live evidence that extractor upgrade convergence and all public read surfaces behave correctly.

### HOW

- Confirmed server `1.18.1+c56fe0751529`, extractor `2.31.4`, schema 6, semantic policy 2.
- Observed startup progress through resolver convergence and the required extractor-upgrade full scan; steady state arrived with queue empty and search/content/vectors current at revision 7032.
- Verified semantic retrieval returned `FullRebuildPromotion.Promote` first for a natural-language rebuild-safety query; broker became ready on Vulkan with one spawn.
- Verified a Miller edit dry run produced a disk-verified one-line preview and wrote nothing.
- Reproduced a readiness-specific JSON defect: while `resolution_state=converging`, compact inspect/trace/impact correctly returned `resolution_converging`, but `format=json` returned `invalid_json_output`.
- Traced the cause to those tools setting `output = string.Empty` and then calling `ToolDiagnosticRenderer.Attach`; `AttachJson` unconditionally calls `JsonNode.Parse(output)`. Existing resolution-layer tests cover compact output only.
- Measured two query-only, reference-off context calls at about 32.9s and 33.3s; a usage-enriched context call did not return within roughly 90s and was terminated. Historical telemetry already shows context p95 463.866s and max 7,539.290s, so this is not proven new to 1.18.1.

### IMPACT

Steady-state search and navigation are correct, the upgrade path converges, and semantic startup works. The release still has one concrete JSON diagnostic bug during resolution convergence and a serious context-latency problem worth separate fixes.
