## Spike: `julie-server extract` → SQLite → C# contract + .NET 10 perf, PROVEN

Validated the target architecture for reviving codesearch as a C# code-intel tool that reuses julie's tree-sitter extraction with **zero in-process Rust / zero FFI**.

### WHAT
- New standalone spike project `spike/Codesearch.Spike` (net10.0, not wired into the main solution, no dependency on the old FFI `Codesearch.Interop` cdylib).
- Shelled the **prebuilt** `julie-server extract scan --root <repo> --db x.sqlite --standalone --json` (binary at `/Users/murphy/source/julie/target/release/julie-server`, v7.12.1) — no cargo build needed.
- C# read the canonical SQLite via `Microsoft.Data.Sqlite` 10.0.8: symbols/identifiers/types/relationships/symbol_annotations.
- Ported julie's `src/search/tokenizer.rs` splitting to a ~120-LOC span-based `CodeTokenizer` (camelCase + acronym + snake + digit boundaries).
- Hand-rolled Stopwatch benchmarks (warmup+median+alloc tracking).

### RESULTS (Apple Silicon)
- **Extract**: 166 files → 5,284 symbols / 11,106 identifiers / 1,825 types / 516 rels in **0.43s** (317% CPU). DB 21MB.
- **Contract: PASS** — annotations came through cross-language (C# dllimport/fact, Python pytest.mark.asyncio, Rust tokio::test).
- **Cosine (TensorPrimitives SIMD vs scalar)**: 10k×768d = 3.2ms (3.0x); 100k×768d = 19ms (3.4x). ⇒ brute-force vector search is trivial at single-repo scale; **LanceDB is deletable**.
- **Tokenizer (span vs regex)**: 11,106 real idents in 1.6ms vs 5.6ms, 828KB vs 3.9MB ⇒ **3.5x faster, 4.7x less alloc**.

### IMPACT
- The load-bearing assumption holds: parsing stays in a prebuilt Rust binary (no Rust dev pain), everything else is C#.
- `extract` schema already includes `symbol_vectors_*` (sqlite-vec vec0 shadow tables) — vector path is a loadable C extension, not Rust.
- 3-3.4x SIMD = ARM NEON 4-wide lane; would be larger on AVX-512/AVX10.2 x64.
