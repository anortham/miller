## WHAT

Reviewed the proposed idle freshness stamp and WAL checkpoint slices without changing product code.

## WHY

Two Miller processes currently run `FreshnessService` every 500 ms. Each store-mode poll reads the workspace pointer, opens the live family `store.db` with private cache and pooling disabled, validates metadata and manifest identity, and reads the view-scoped store-log cursor. Those opens keep `store.db-shm` active and make a large WAL harder to fold even when indexing is complete.

## HOW

- Confirmed `FreshnessService.PollThenSwap` depends on revision plus family generation/view/manifest identity to detect both ordinary advances and promoted/replaced artifacts.
- Confirmed `WorkspaceFreshnessProbe` also carries store root and serving binary version; a four-field stamp is incomplete.
- Found normal incremental reconciliation uses update/delete requests directly in `ApplyIncrementalFileDelta`, not only import/resolve.
- Found store-log semantics deliberately expose nonterminal L1 publication during an active full import.
- Confirmed `.miller` is already excluded by `WatchPathFilter`, so a workspace-local stamp and its atomic temporary file do not feed the source watcher.
- Confirmed `JulieStoreClient.OpenStoreMutationAnchor` holds read transactions on both store and coordinator databases while julie-extract runs; `StoreMutationAnchorCoversProcessExecution` proves `wal_checkpoint(TRUNCATE)` returns BUSY until those anchors are released.
- Determined that `FullRebuildPromotion.FoldWalIfPresent` is not reusable unchanged for a live store because it ignores the checkpoint result and assumes a private rebuild file.

## IMPACT

The safe smallest design is a separate schema-versioned stamp validated against `store.json`, invalidated before every visible mutation, and atomically republished from a final validated probe after completion. Missing/dirty/malformed/mismatched stamps retain the current SQLite fallback, preserving correctness and progressive L1 visibility. WAL maintenance should inspect checkpoint result rows and run as bounded background maintenance with one retry, never inline with scan completion.
