## Dashboard: rejected Blazor Server, fixing the real causes in htmx

The user asked whether to replace htmx with Blazor Server because the dashboard "blinks" and lacks
smooth real-time updates. Answer: no. Measurement showed the dashboard is not a rendering-model
problem.

### Measured on the author's own 59-workspace registry (warm, Release build)

| Request | Now | `MILLER_INDEX_STORE=off` |
|---|---|---|
| `/fragments/workspaces` (30s poll) | 3.01 s | 0.013 s |
| `GET /` | 3.04 s | 0.078 s |
| `GET /workspace?workspace_id=…` | 2.86 s | 0.98 s |
| `/fragments/refresh-status` (2s poll) | 2.82 s, 102,646 B | — |
| `/fragments/activity` (5s poll) | 0.005 s | — |

The 3 s is pure CPU (sampled `utime+stime` from `/proc/<pid>/stat`), not an expired `busy_timeout`.

### Root causes

1. **`DashboardIndexFactsCache.cs:24-25`** returns before its own cache whenever store mode is on —
   the default. Not an accident: added by `d7743cd1`, documented in
   `docs/findings/2026-08-09-index-store-ph3-acceptance.md:91-92` as a guard against the *legacy
   file timestamp*, which is meaningless under store mode. Fix is a store-mode witness
   (`WorkspaceReadSessionFactory.Probe`), not removing the guard. `MILLER_DASHBOARD_INDEX_CACHE_SECONDS`
   was inert for the same reason.
2. **`dashboard.css:1494-1498`** unscoped `.htmx-request { opacity: .5; pointer-events: none }`.
   htmx puts that class on the *requesting* element and every polled panel is its own requester, so
   the Workspaces panel sits half-faded and click-dead for ~3 s out of every 30.
3. **`/fragments/refresh-status`** returns the whole ten-panel stack to fill an empty span, on a
   2s timer **that never stops**. htmx's `ct` captures the trigger in a closure; the only
   `clearTimeout` is in `De`, reached from `Pt`, which only runs on nodes matching `Ht`'s
   attribute selector. The terminal render strips every htmx attribute, idiomorph preserves the
   node by id, so the timer runs forever.
4. `updateRelativeTimes` rewrites 37-49 text nodes every 5 s unconditionally, even on a hidden tab.
   `htmx:afterSwap` re-sorts all 59 rows on every panel's swap once a sort header is clicked.
5. Repeated rows carry no `id`, so idiomorph matches positionally.

### Two claims REFUTED — do not re-introduce

- "Relative timestamps defeat the fragment ETag." False. With a cookie jar the ETag is stable and
  304 fires; the earlier measurement used a cookie-less `curl`, which changes the antiforgery salt
  by design. The waste is still real: `FragmentETagAsync` renders the whole fragment before hashing,
  so a 304 still costs the full 3 s.
- "`WorkspaceTestsPanel` leaks its poll timer too." False. `kt` calls `Pt` on the swap root before
  walking `Ht`, so a *self-targeted* swap clears its own timer. Only ancestor-targeted swaps leak.
  Corollary: self-targeted `morph:outerHTML` stops the poll fine — the target matters, not the swap
  style.

### Why not Blazor Server

Leaves the 3.0 s facts read and the ~1 s detail read untouched (server CPU, not transport). An
unkeyed `@foreach` diffs positionally exactly as idiomorph does without ids — same bug, new
spelling. Adds per-tab server state and a forced reload in every open tab on every Miller upgrade
(`DashboardCliLauncher` replaces a dashboard running a different build). Deletes three named guard
tests and the CLAUDE.md dashboard rule. Three independent judges scored it last: 5/6/5 of 40 against
33/32/34 for the winner.
