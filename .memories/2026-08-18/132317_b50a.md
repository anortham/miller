## Query-time resolution spike: 100% parity, ≤24 ms worst-case refs query

**WHAT:** Built and ran the throwaway spike `spike/query-time-resolution/` (C# console) answering the assessment's §7 question. Results in `docs/findings/2026-08-18-query-time-resolution-spike.md`. Spike captured on branch `prototype/query-time-resolution`.

**WHY:** User approved retiring the materialized resolution layer if query-time resolution proves parity and latency. Two weeks of store-resolution firefighting; resolve phase costs 12–77 s p95 per save batch, 171 s full on Linux.

**HOW:** Extracted julie's exact resolver policy (RESOLUTION_VERSION=6) from resolution.rs via subagent spec; reimplemented tiers 1–4, pending resolution, span-based tier-1 propagation; compared against frozen snapshot ground truth (base 374850… + delta gen 499, view 7857a50b, manifest gen 412).

**Results:**
- Parity 475,377/475,377 = **100.000%** (outcome, target, tier, method)
- Refs query warm: p50 0.02 ms, p95 4.4 ms, **max 23.6 ms** (`Assert`, 19,925 sites) vs 500 ms gate
- Full-corpus resolve **0.8 s** vs julie's 171 s phase; load 3.4 s + propagation 0.5 s one-time
- Peak RSS 719 MB naive instrument (production model must intern/stream; budgets 350/600 MB)
- Parity ladder: reference_site join→span join (21,543), dotted-namespace flattening (37), kind-aware scope-stop rule (21)

**IMPACT:** Proves the materialized graph is a pure function of current fact tables, recomputable in <1 s at Miller scale. Confirms the §4 architecture direction: retire bases/deltas/rebases/proofs/scope-journal/resolve-subprocess. Whole-graph products become a ~1 s batch sweep. Remaining risks: dotnet/runtime scale untested, memory model unproven, per-file invalidation not built.
