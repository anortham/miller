## Dogfood found a release blocker: 2.34.0 wedges existing stores

**WHAT:** Dogfooding the restarted session (miller 1.19.6+f9dea838) hit `capability snapshot conflict for extraction epoch 1` on every store import into the real family store — 3 consecutive scan failures, stale served view.

**ROOT CAUSE (julie-extractors):** 2.34.0 dropped the 109 `reference_resolution.*` capability gap rows from its snapshot but kept `EXTRACTION_IDENTITY_EPOCH = 1`. `sync_capability_snapshot`'s per-epoch count check (old: 128 gaps, new: 19) conflicts forever on any pre-2.34.0 store. Exports already filter those rows; import did not. Fresh stores never conflict — which is why all Scale tests and the off-mode smoke passed.

**FIXES:**
- Local repair: deleted epoch-1 rows from the 4 capability tables in the wedged `store.db` (backup taken first); next import committed; workspace converged (fresh, vectors ready).
- Root cause: julie-extractors commit `18bb7dbd` (unpushed, main) — writer open reaps retired `reference_resolution.%` gap rows. TDD test `writer_open_reaps_retired_reference_resolution_gap_rows`; artifact+cli crates green, clippy clean. End-to-end proof against a copy of the wedged store: released binary conflicts, fixed binary commits and reaps 109 rows.

**Other dogfood results:** all read surfaces good (trace refs with query-time evidence, inspect overview, impact over git base, semantic search, context). Server logging to `~/.miller/logs` on deferred launch is by design (Program.cs:51), though the refresh-failure hint says "check the Miller log" without naming which.

**IMPACT:** Miller must NOT release with the 2.34.0 pin — every existing user store would wedge on upgrade. Recorded in the adoption finding. Path: julie ships 2.34.1 with the reap → Miller re-pins → then release. Both repos have unpushed commits awaiting user approval to push/release.
