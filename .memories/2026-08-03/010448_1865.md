## F1/F2/F3 — bootstrap empty-artifact reuse, governor admission on a lock, seeder TOCTOU

**WHAT.** Three confirmed defects fixed on top of W8 (`dda53d1a`).

- **F1** `IndexBootstrapService.DecideBootstrapScan` reused an artifact on `dbExists && rootMatches` alone, and
  that decision runs BEFORE any lock attempt — so `WinnerArtifactProbe.IsFinished`, which correctly refuses a
  metadata-only artifact, was never consulted. julie-extract writes `artifact_metadata` (root_path included) in
  autocommit the moment it opens the writer, so for a whole cold scan there is a DB matching this root with zero
  committed rows. A second Miller starting in that window bound it and logged `0 symbols indexed at revision 0`.
  Fix: `hasCommittedRevision` becomes a fourth pure parameter; no committed revision ⇒ delta-scan, which routes
  into the lease block where the existing winner-probe makes the loser wait for the finished artifact.
- **F2** `TryScanAsLeader` took machine-wide scan admission and THEN blocked on `_opsGate`, so a thread sat on the
  one-at-a-time machine lease for the full duration of a governor-exempt holder's extract while N sibling
  worktrees were refused — the fleet starvation the governor exists to prevent, inverted. Fix: bounded
  `Monitor.TryEnter(_opsGate, 1s)`, release admission and re-arm the latch on timeout. Lock order is UNCHANGED
  (`SingleWriterLock -> ScanGovernor -> _opsGate -> IndexerCore gate`), only the hold is bounded.
  `HoldsLeaderOps()` also had to stop taking `_opsGate` — it parked the caller before the bounded entry could run.
- **F3** `JulieIgnoreSeeder.EnsureSeeded` was check-then-`WriteAllText` (which TRUNCATES), so a `.julieignore`
  authored inside the window — by a user or a sibling process — was silently replaced. Fix: `FileMode.CreateNew`;
  the racing creator wins. `ScanIgnorePolicy.WriteInvariantIgnoreFile` deliberately stays last-writer-wins
  (generated, Miller-owned, and CreateNew would strand workspaces on a stale pattern set).

**WHY the lead re-reviewed.** Three review lenses raised the same F2 rendering issue and the verifiers split 1-2.
Reading all three, the disagreement was narrow and the residue real: `WorkspaceTool`'s Queued arm hard-coded the
machine-wide-admission cause and pointed at a `scan_governor` object that is absent for the new ops-gate cause.
Fixed by extracting `QueuedNote`/`QueuedRefusal` as named seams (same move as `AutomaticRefresh`), making the copy
cause-neutral and letting `HolderDescription` carry the mechanism.

**HOW — two things I verified myself rather than accepting.**
1. F1's risk was a legitimately EMPTY repo rescanning forever. Measured against the real extractor: an empty repo
   gets `revision_id = 1` with 0 symbols, so reuse still works. Reasoned answers were available; the measurement
   is what settles it.
2. The Scale gate failed. Rather than accept "flaky", I built a detached worktree at `dda53d1a`, symlinked
   `.tools`, and measured: HEAD also fails ~1/3 in the same class. **Pre-existing**, not mine — recorded as its
   own task rather than bundled into this commit.

**IMPACT.** Unblocks W9 (the last implementation workstream). The de-flake task is now the Scale gate's own
credibility problem: `ScanGovernorContentionScaleTests` IS the gate for W3's governor, and a gate that fails a
third of the time would mask a real regression.
