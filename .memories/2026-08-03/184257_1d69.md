## Sidecar staging-file reaper shipped + 3.9 GB orphans reaped

**WHAT:** Reaped 3,856 MiB of orphaned `.search-build-*.db`/`.content-build-*.db` staging files across miller/eros/julie workspaces (19 files in miller/.miller alone), then added `SidecarStagingReaper` (src/Miller.Indexing/SidecarStagingReaper.cs) called at the top of `SearchIndexWriter.Write` and `ContentCorpusWriter.Write`.

**WHY:** Staging names carry a GUID so a SIGKILL mid-build (the fleet kill-storms) leaves a file no later build overwrites — accumulates forever; nothing reaped them. Found while investigating the user's disk-pressure complaint (28× index amplification question).

**HOW:** Age-based orphan detection (15-min `DefaultStaleAge`; a live build's SQLite writes keep mtime fresh) + caller's own staging path shielded + best-effort IOException swallow. Callers hold the single-writer lock so age cannot race a legitimate sibling build. 4 fast-suite tests incl. end-to-end `SearchIndexWriter.Write` reaping a stale sibling.

**IMPACT:** Fast suite 5,768 passed / 0 failed, build 0W/0E. Disk story quantified: all .miller dirs = 19.3 GB total; dotnet artifact breakdown says ~80% of bytes are the reference layer (identifiers 4.2 GiB + reference_sites 3.5 GiB + ~8.7 GiB of their indexes; identifiers has NINE indexes) → levels L1 split is also the disk answer; index audit next.
