## W10 measured — the fleet-safety program's expensive gate is answered

Ran the 74k-file scale repro against pinned `julie-extract 2.21.0` on a 24-core / 64 GiB machine.

### What was measured
- **Fixture:** generated polyglot repo, 74,000 files / 289 MB / 8 languages, realistic symbol density; artifact = 1.62M symbols, 3.96M identifiers, **9.2 GB symbols.db**.
- **Healthy force scan (--jobs 4):** 3,677 s wall, **peak WAL 9.28 GB**, peak spool 5.4 GB, symbols.db stuck at **4,096 bytes for 3,582 of 3,677 s** (one transaction; the whole artifact lives in the WAL). Peak transient disk about 24 GB for a 289 MB tree (83x).
- **Kill during extraction (t=60s):** extractor peak RSS **135 MB**. Leftover: 5.2 GB spool, no artifact.
- **Kill during artifact write (WAL=3 GB):** leftover about **8.3 GB** (5.3 GB spool + 3.0 GB WAL + shm + 4 KB db).

### The diagnosis this changes
Extraction peaks at **135 MB**; the ~30 GB peak RSS is entirely the **artifact-write / resolution phase**, which --jobs does not bound. So **W2's jobs cap is not the OOM fix — W3's machine-wide governor is.** Chunked commits would bound transient disk but would NOT lower the memory peak. Recommendation recorded: land W4/W5/W6 first, revisit chunking with these numbers; it is a julie-extractors decision, not Miller's.

### Two claims independently corroborated
- The field report's "~14 GB WAL, ~50 min" is real: 9.28 GB / 61 min here on a synthetic repo of the same file count.
- The spool leak is real on this machine right now: TMPDIR held **48 orphaned spool files, 680 MB**, zero live owners, from four days of ordinary Scale runs by one agent.

### W1 fix validated against the real failure state
An OOM-killed scan leaves an artifact that is root-matching and metadata-complete but **empty** (MAX(revision_id)=0, 0 files, 0 symbols) — exactly the state the hasCommittedRevision gate was added for. Verified by running the production query against both a killed and a healthy artifact.

### Fleet end-to-end (program success criterion 1: MET)
3 concurrent `miller workspace open --full` over 3 sibling git worktrees (each .git a FILE), shared isolated HOME: **max concurrent extractors = 1** (383 samples), all 3 carried `--jobs 4`, all exit 0 / state ready / revision 1, .julieignore seeded in all 3, zero leftover spool. duration_ms staircase 34s / 69s / 105s against a flat 28s scan_duration proves serialized admission.

### Criterion 2 NOT met
"At most one dead-PID spool, reaped on the next scan" requires the unreleased W4 reaper. With 2.21.0 pinned, every killed scan leaks its spool permanently.

### Harness lesson (repeated twice)
Matching processes by name alone picked up an unrelated session's julie-extract and reported "3 concurrent scans" where the governor had allowed 1; summing every spool in TMPDIR attributed a foreign scan's spool to mine. Both fixed by scoping to the launched PID tree. Every number in the findings doc comes from the scoped harness.
