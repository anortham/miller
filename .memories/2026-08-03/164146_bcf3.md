## v2.23.1 clean baseline on dotnet/runtime — profiler verdict lands

**WHAT:** Completed the uncontended cold-scan baseline (julie-extract 2.23.1, dotnet/runtime @ a2f953fe266, --jobs 4) and wrote `docs/findings/2026-08-03-dotnet-runtime-v2231-baseline.md` + docs map pointer.

**Numbers:** 76.3 min wall, 3,246 s CPU (~71% of one core), 19.6 GiB peak RSS, 22.84 GiB artifact, 2.58 M symbols / 12.86 M identifiers / 15.5 M reference sites, exit 1 `status: partial` (8 non-UTF-8 read failures, by design).

**Phase partition (the load-bearing discovery):**
- Extraction+spool 0–210 s (5%), bulk load →~950 s (16%), **resolution ~950–4,177 s = 70% of wall**, index finalize 4,177–4,580 s (9%).
- Resolution decay curve (decile db growth): 0.44→0.22 GiB at flat ~60% CPU duty — decay is intrinsic, not contention.

**WHY it matters / profiler verdict:** three regimes inside the write phase — early `pread` 3,182/4,200 top-of-stack (b-tree probe misses), mid `pwrite` 2,902→3,894 + `memjrnlTruncate` 1,095→45 (cache spill mid-savepoint + in-memory statement journal churn; RSS ~18 GiB = journal pre-images), finalize `pread`+`vdbeRecordCompareString`. Both #18 hypotheses (cache thrash, memjrnl) are facets of ONE root cause: `SQLITE_BULK_CACHE_SIZE_KIB = -131072` (128 MiB) vs a 12+ GiB working set.

**IMPACT:** First #18 experiment = single-variable cache raise in the resolver-decay worktree (writer.rs:39), not savepoint surgery. 64 GiB box, budget exists. Even 2–4× resolution win leaves ~30–40 min cold scan → levels program still the product answer; this doc is the L-P3 yardstick.
