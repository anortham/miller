## Auto-heal had a latent SQLite pool-staleness bug — caught by merge-readiness audit, now fixed

**Correction to the earlier checkpoint** (which claimed the auto-heal was verified via a 21/21 scale pass): that pass was **timing luck**. The new `LiveBootstrapAutoRebuildTests` actually failed **5/5 in isolation**.

**Bug:** `IndexBootstrapService.LoadIndexWithAutoRebuild` called `forceRescan()` (julie force-rebuild, which REPLACES the DB file/inode) then immediately retried `load()` with **no SQLite pool barrier**. `SqliteReadOnlyAccess.Open` uses **default pooling** (unlike `TelemetryLedger`/`WorkspaceRegistry`/`DashboardData` which set `Pooling=false`), so the pooled read connection from the failed first load still pointed at the OLD schema-1 inode and the retry re-read schema 1 → re-threw `IncompatibleExtractException`. In production this means a cold start against an incompatible reused DB could still crash with the exact "MCP failed to connect" error the fix targets.

**Fix:** Added a required `onBeforeRetry` barrier param to `LoadIndexWithAutoRebuild`, invoked AFTER rescan and BEFORE the retry load. `Run()` and the live test wire it to `SqliteConnection.ClearAllPools` so the retry opens a fresh handle on the rebuilt file. Kept the helper SQLite-free (injected hook) so a new fast unit test pins the ordering `load1 → warn → rescan → barrier → load2`.

**Verified:** new live test **5/5 green in isolation** (was 0/5); fast suite **1307** (+1 ordering test); scale suite **21/21** three consecutive runs (flake eliminated); build 0/0.

**Discovery method:** a 5-lane merge-readiness Workflow (tests lane ran the new test in isolation and caught the deterministic failure the full-suite run masked). Lesson: Scale/live tests that touch SQLite must be proven green IN ISOLATION, not just in-suite, because concurrent `ClearAllPools` from sibling tests hides pool bugs.
