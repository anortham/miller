## Phase 2 done — `FtsSymbolSearchIndex` on-disk FTS5 reader (TDD, ranking parity proven)

Built the read-only `search.db` reader for the collapsed-trigram symbol-search rebuild, strictly test-first. All untracked (not yet committed).

### What landed (4 TDD steps, each RED→GREEN[→REFACTOR])
1. **Phase 1 amend** — added `signature TEXT` to `search_symbols` in `SearchIndexWriter` (chosen via AskUserQuestion: "add signature column" so the reader is a pure, self-contained `search.db` consumer with full-fidelity results).
2. **`Bm25`** (`src/Miller.Core/Search/Bm25.cs`) — extracted shared scorer (K1/B/ExactNameBoost, `Idf`, `TermScore`); refactored `MillerSearchIndex` onto it (behavior-identical, guarded by existing tests). This makes FTS↔in-memory ranking parity **structural**, not hand-copied.
3. **`SymbolLookupTables`** (`src/Miller.Indexing/SymbolLookupTables.cs`) — extracted the id/name/path lookup maps (no BM25 postings) from `SymbolSearchProjection`; both backends now compose it.
4. **`FtsSymbolSearchIndex : ISymbolLookupIndex`** — pure `search.db` reader. Word arm = uncapped quoted-OR `body MATCH` + C# BM25 re-rank; trigram arm = collapsed-name interior substring, `LIMIT 200`, floored below word hits, excluded under AND.

### Key as-built decisions
- **DF via `COUNT(*) … WHERE body MATCH "term"`** (not `fts5vocab` — read-only DB can't create the vocab vtable; the count is the exact DF).
- **TF/doc-len re-tokenized** from resident `Name + " " + Signature`; `meta.avgdl`/`doc_count` give avgdl/N.
- **DocId re-derived** via `ORDER BY path, start_line, symbol_id` (byte-for-byte `SqliteSymbolReader`'s order) → DocIds + tie-break + `Resolve` match the in-memory index.
- **Per-query short-lived `Pooling=false` connection** (resident snapshot loaded once at `Open`); no held handle → no atomic-replace race, no lock, thread-safe; not `IDisposable`.

### Verification
- Fast suite **1367 pass, 0 warnings, ~9s**. Ranking-parity tests assert FTS word arm == in-memory `SymbolSearchProjection` (DocId order **and** scores to 1e-9) for **OR and AND**.
- Adversarial multi-lens review (parity/FTS-SQL/lifetime/contract, refute-by-default verifiers): **no code bugs**, only 2 test-gaps — both closed (AND parity + signature-only/no-boost parity).
- Caveat for the eval phase: FTS5 `unicode61` folds diacritics → per-term DF can drift for accented non-ASCII identifiers (recall stays exact; only scores shift). ASCII parity exact.
