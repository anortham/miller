## Bumped Miller to julie-extract v2.1.0 (compatibility only)

Moved Miller's pin from `julie-extract` v2.0.3 (schema/contract/report **1**) to **v2.1.0** (all **2**). v2.1.0 adds a `source_regions` row domain (spans for comments, doc comments, string literals, embedded-language regions for Rust/JS/JSX/TS/TSX/Python/HTML/Vue). This change is **compatibility-only** — Miller does NOT yet consume `source_regions`; that is the planned "consume next" piece.

- **WHY:** julie-extract 2.1.0 is a contract break (schema/contract/report 1→2). Miller's `JulieSchemaGate` is exact-equality on version, so a v2.1.0 extract DB was hard-rejected until this bump.
- **Key facts that shaped it:**
  - The ONLY SQLite change v1→v2 is the *addition* of the `source_regions` table + 3 indexes; every table Miller reads is unchanged, so readers needed zero changes.
  - julie's incremental `scan` hard-fails on a schema-mismatched DB (only `scan --force` rebuilds), so a leftover v1 DB can only be upgraded by `workspace full`, never `workspace refresh`.
  - Decision: **hard-cut** to schema 2 (not a dual-accept window) — a dual-accept would let v1 DBs read while `refresh` fails (confusing half-state). Re-indexing is routine.
- **HOW (changes):** `MillerExtractContract.cs` (4 constants 1→2, pin "2.0.3"→"2.1.0", docstrings); `scripts/julie-pins.json` (version + 4 archive sha256s); `ExtractVersionMismatch.BuildMessage` older-path remedy now leads with `workspace full`; `JulieSchemaGate` docstrings v1→v2; tests cascade via `PinnedSchema`/`Expected*` (fixed `MillerExtractContractTests` literals, `ReportWith` default, `SqliteBridgeReaderTests` wrong-schema literal, added `workspace full` assertions).
- **IMPACT:** Miller reads v2.1.0 extracts; the new `source_regions` table is tolerated and ignored (validated — scale tests run the real v2.1.0 binary which emits source_regions, and Miller reads those DBs fine).
