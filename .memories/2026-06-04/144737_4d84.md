## codenav trigram experiment → Miller search recommendation (analysis only, no product code yet)

Analyzed the codenav trigram-on-symbols search experiment to extract takeaways for Miller. User then lifted the "in-memory BM25 only / FTS5 parked" constraint: goal is now the best code-search algorithm. Ran a design bake-off (in-memory feeder vs disk FTS5 vs tiered vs wildcard) + adversarial feasibility check against real Miller code.

- **Durable win = recall, not scale.** Index a COLLAPSED identifier (`format_external_extract`→`formatexternalextract`), shingle trigrams, union as an extra recall feeder into the UNCHANGED BM25 ranker. codenav: strict superset, zero ranking regression, 6 langs; Miller's own C# corpus 0.57→0.84 interior recall.
- **Miller's gap is narrower** than codenav's (Miller already splits CamelCase/snake into components) but real for interior substrings (`thenti`), boundary-crossing (`tionprov`), and a snake/camel asymmetry.
- **Re-baselining flipped the bake-off headline.** The bake-off picked a disk FTS5 sidecar to "kill the 6.2s/1.2GB first-search cliff" — but that cliff is the FULL `RepositoryIndexLoader.Load`, which search ALREADY bypasses via the shipped symbol projection (OpenClaw search ≈1.8s/+55MB per `docs/plans/2026-06-02-search-projections-design.md`). So FTS5's scale rationale for search evaporates; the cliff belongs to trace/impact/context.
- **Recommendation:** Phase 0 `CollapseName` (pure, shared) + Approach A in-memory collapsed-trigram feeder now; defer FTS5 sidecar to a profiling-gated bootstrap-RSS optimization. Verifier also showed the sidecar's external-first build story is infeasible as written (external search built lazily by a non-leader reader; writing a foreign `.miller` is a multi-writer hazard).

Wrote `docs/plans/2026-06-04-symbol-search-collapsed-trigram-design.md` with full design, impl plan (Phases 0-3), eval plan (Scale-tagged recall@5/MRR on OpenClaw/Hermes), and brief update. No product code changed.
