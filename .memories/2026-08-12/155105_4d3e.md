## Miller fully healthy — duplicate server gone, semantic retrieval live on Vulkan

All three requested items landed, verified after a Claude Code restart. `workspace health` went **`degraded` → `usable_with_warnings`**; the only remaining warning is the pre-existing "111 open capability gaps" (a julie-extractors language-coverage matter, unrelated to this work).

### 1. Duplicate MCP server — resolved without deleting `.mcp.json`
The user asked to delete `.mcp.json` believing it was unused. **It is not.** Evidence: `.codex-plugin/plugin.json:22` sets `"mcpServers": "./.mcp.json"`, and `tests/plugin/plugin-manifest.test.cjs` pins its exact contents at lines 117/146/156/157/158. Deleting it breaks Codex plugin installs and fails four assertions — and Codex is the harness that consumes it in this dual-run setup.

Instead wrote `.claude/settings.local.json` with `{"disabledMcpjsonServers": ["miller"]}` — gitignored at `.gitignore:55`, so it stops Claude Code loading the duplicate while leaving Codex intact. **Confirmed working:** the `miller` server disconnected on restart, only `plugin:miller:miller` remains, and that single process (pid 46364) is now `[leader]` instead of a permanent reader. `workspace refresh`/`full` are reachable from the tool surface again. Offered the real deletion (Codex manifest + test + `docs/install.md` updates) if the user still wants it.

### 2. Semantic retrieval — fixed, and it's GPU-accelerated
Root cause: **nothing in Miller ever downloads the embedding model.** Only the explicit `miller semantic prepare` CLI verb does; `bin/miller-plugin-launcher.cjs` has zero model handling. Ran `miller semantic prepare --model bge-small-en-v1.5-f32` → 133,609,568 bytes, sha256 matches the `eval/model-bench/bench-pins.json` pin, cached to `%LOCALAPPDATA%\julie-semantic\` (**not** under `~/.miller`, which is where I wasted time looking first).

It printed `still_not_ready` because `SemanticPrepareCli` only activates an *already-running* broker. After restart: `vectors: ready`, `semantic_broker: ready`, `model: bge-small-en-v1.5-f32`, `backend: vulkan` on an NVIDIA RTX A1000 6GB, `accelerator_lease: held`, `spawns: 1`. Proved end-to-end with a natural-language query having no literal keyword overlap ("how does the indexer decide it is allowed to become the leader" → `TryReindexAsLeader`, `RunLeadershipSessionAsync`, `MaybeRequestYield`).

### 3. Registry pruned
23 dead rows removed (old plugin-cache versions, deleted worktrees, temp dirs), 22 kept.

### Two transients I chased that self-healed — don't panic next time
- **A second revision storm** after restart (rev 5857→6189 at ~10/sec). Not the store migration this time; it was post-restart sidecar reconvergence plus the vector build embedding 225k symbols. `store.db` mtime froze and it settled on its own.
- **`scan_failure: IncrementalReconcile x1, exit_code: null`** at 10:48:17 ("Startup delta scan failed"). The persisted 30s backoff retried and succeeded; the `scan_failure` line is gone from status. Working as designed.

### Product gap identified (answered the user's "how do other users avoid this?")
Not Windows-specific — **every fresh install, and plugin users cannot reach the fix at all.** `README.md:15` advertises semantic as on-by-default; the prepare step appears only in `docs/known-limits.md:17`. Proposed, awaiting the user's go-ahead:
1. **`src/Miller.Indexing/VectorSidecar.cs:300` is a real diagnosability bug** — it tells users to run `miller workspace refresh` when the vector artifact lacks a completeness stamp, which can never fix a missing model. It misdirected me for minutes.
2. Auto-prepare on first run when `MILLER_SEMANTIC != off` and no model is cached (product call: 134MB unprompted network).
3. Actionable `workspace health` warning + `onboarding` mention.
4. Document in README + `docs/install.md`.
Rejected: bundling weights — the sidecar manifest forbids it and it would push the archive from ~97MB to ~230MB when 97MB already fails to download.
