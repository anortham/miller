## Recovered populated family stores with an unpublished target view

The first override fix handled an empty family root, but a real failed import left valid family files and a serving generation for another view. Miller passed eligibility, selected incremental reconcile, then failed because the registered target view had never been published.

- **What:** Extended the producer-backed regression to create a real `coord.db` and serving `store.db` for another root in the same family
- **Why:** The live replay still failed with `The store has no view for the workspace root.` under the explicit override
- **How:** Under the override only, classify unreadable active stores as `RootRebind`, re-plan the missing existing member view, and treat only `Planned + ViewNotFound` as no prior state for import
- **Safety:** Default refusal is unchanged; corrupt CURRENT, schema, family, and other read failures still propagate
- **Impact:** Explicit recovery can publish the missing target view into an existing populated family without weakening normal store validation
