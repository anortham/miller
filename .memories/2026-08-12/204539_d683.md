## Fixed both v1.18.3 bugs: git-backed `impact` hang and dashboard detail-page hang

Root-caused and patched the two blockers found in the v1.18.3 smoke test. Both verified end-to-end.

### Fix 1 — `src/Miller.Server/Git/GitDiffReader.cs`

**Symptom:** every git-backed `impact` mode (no args, `base=`, `staged=`, `git=true`) blocked exactly 30s
in the MCP server, then failed `git_diff_failed`. The CLI ran the same code fine.

**Cause:** `ProcessGitDiffReader` redirected stdout/stderr but NOT stdin, so the spawned git inherited
Miller's stdin. The trigger needs BOTH conditions: the child inherits the handle AND the parent has an
in-flight read on it — which the MCP stdio transport does permanently. Git for Windows then blocks in
startup handle probing and never runs (0.00s CPU, `Wait, Executive` + 3x `Wait, EventPairLow`, killed at
timeout). The CLI is immune because its stdin is a console.

**Proof** (minimal .NET repro in scratchpad, identical ProcessStartInfo):
- console stdin, inherited → 207ms
- pipe stdin no pending read, inherited → 171ms (this is why my first hypothesis test wrongly cleared stdin)
- **pipe stdin WITH pending read, inherited → 30031ms timeout**
- pipe stdin WITH pending read, redirected+closed → **161ms**

**Fix:** `RedirectStandardInput = true` + `process.StandardInput.Close()`. Extracted
`internal static CreateStartInfo(GitDiffRequest)` so the argv/redirect contract is unit-testable.

### Fix 2 — `src/Miller.Indexing/CloneGroupReader.cs`

**Symptom:** dashboard `/workspace?workspace_id=…` (the URL `workspace operation=dashboard` hands back)
never responded — >7min, dashboard CPU climbed past 5,400s. `/` was 0.68s.

**Cause:** `dotnet-stack` showed every stuck thread in
`ReadSnapshot → ReadLocalMetricsPanel → CloneGroupReader.ReadConnection → SqliteDataReader.NextResult()`.
The `clone_hashes` CTE was not materialized, so at a SMALL limit SQLite inlines it and re-runs the
whole-table `GROUP BY body_hash` per join probe. Measured on the 226k-symbol store, scan idle:

| `--limit` | before | after |
|---|---|---|
| 50 | 5s | 6s |
| 20 | 5s | — |
| 10 | 6s | 6s |
| **5** (what the dashboard asks for) | **never finished (>180s)** | **5s** |

**Fix:** `WITH clone_hashes AS MATERIALIZED (…)`. Not contention — the limit alone flips the plan.

### Verification

- `dotnet build Miller.slnx -c Release` → 0 warnings, 0 errors.
- New tests: `GitDiffReaderTests` (6) + `CloneGroupReaderTests` (5) → 11/11 pass. The dashboard's exact
  `limit:5, minCount:2, symbolsPerGroup:3` combination had NO prior coverage.
- Fast suite: **6460 passed, 3 failed, 22 skipped**. The 3 failures are all
  `CliDispatchTests.WorkspaceStatus_DefaultOnAndShadowPassivelyObserveAnExistingSharedBroker`
  (expects `backend=cpu`, gets `vulkan`). **Pre-existing and environmental** — reproduced identically in a
  pristine worktree at HEAD 3c68ba4e without my changes. The test's passive observer attaches to the live
  machine-global broker, which holds the accelerator lease on vulkan.
- Real MCP stdio server driven over JSON-RPC (python probe): all four git modes now succeed —
  `base=HEAD~1` 12.7s, `git=true` 10.8s, `staged` 0.12s, no-args 11.6s, all `isError=false`. The no-args
  case previously returned a misleading "Usage:" message that was really the 30s timeout.
- Patched dashboard: detail page **4.8s**, `/fragments/dashboard` 5.2s (was: never).

### Still open

- 4.8s for the detail page is still slow, and the ~5s clone query runs on EVERY render with no cache and
  no cancellation, so stacked requests each burn a core. Consider moving the metrics panel to a lazy
  fragment or caching it.
- Clone groups are low-signal: the top group is 4,599 one-line variable declarations sharing a body hash.
- `content import` still cannot open a file another process holds (needs `FileShare.ReadWrite`).
- `content shape` severity classifier still ignores Serilog `[WRN]`/`[INF]`/`[ERR]`.
- Neither fix reaches the installed plugin until a new release ships.
