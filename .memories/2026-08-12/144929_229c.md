## All nine Miller MCP tools verified working after the startup fix

Swept every tool on the restored `plugin:miller:miller` server (pid 42004, v1.18.2+c49dc3712ad8). **All nine work.** Two real issues remain, neither blocking.

- **workspace** — status, health, list, leader, refresh, onboarding
- **search** — auto, `mode=markers`, `mode=content`, `mode=source`, `retrieval=lexical`
- **inspect** — `depth=overview` (docs, children, refs, body preview)
- **context** — pivots + `disposition=sufficient`

- **impact** — 5 impacted symbols + 7 likely tests
- **patterns** — list (42 pattern ids / 164,536 facts / 12 languages) + search with continuation
- **content** — import, search, shape, read roundtrip
- **edit** — `replace_text` preview with match proof; **confirmed it wrote nothing** (`git status` clean, line 31 unchanged)

### What the first pass looked like (important for future sessions)
`search`/`inspect`/`impact` initially failed hard with *"Search sidecar for view … is missing or stale"*. That was **correct fail-visibly behavior**, not a bug — this workspace was doing a **first-time migration to the versioned family store** (`generation=1`, `migration=legacy_preserved`, 923MB `store.db`, 225,814 symbols). During ingest the store_log sequence climbed ~10/sec (rev 4869→5304), so no sidecar could earn a completeness stamp.

I briefly misread the leader as wedged (silent in logs for 2+ min while holding leadership and the scan governor). CPU/working-set sampling disproved it: pid 27960 was at ~100% of a core with WS climbing 456MB→1.6GB. **It was converging, not hung** — sidecar builds emit no progress logging. Waiting was correct; a `leader handoff=true` would have aborted real work. After ~4 min: `search_db current`, `content_db current` (1,622 sources / 4,666 chunks), `resolution=unbound → exact`, structural facts `0 → 164,536`.

### Issue A — duplicate Miller servers (should fix)
Both `miller` (from the repo's own `.mcp.json`, pid 27960) and `plugin:miller:miller` (pid 42004) are registered and running against this workspace. pid 27960 won leadership, so **the server my tools talk to is a permanent reader** — `workspace refresh` and `full` refuse from the tool surface with `workspace_refresh_not_leader`. Same version, so version-aware leadership won't thrash, but it doubles CPU/RAM and makes lifecycle ops unreachable. Fix by dropping the `.mcp.json`-sourced entry.

### Issue B — semantic retrieval has never worked here
`semantic_broker: not_started`, `vectors: unavailable` (no completeness stamp), health pinned at `degraded`. Root cause: **no `.gguf` model anywhere under `~/.miller`** — only `semantic/accelerator-v1.lock` and `broker-*.lock`. The `julie-semantic-sidecar.exe` + full llama/ggml runtime ARE present in the package, so this is a missing model download, almost certainly the same large-download failure that broke the plugin zip. Lexical output is byte-identical by ADR-0003, so nothing is broken for search — but the default-on semantic arm does zero work.

### Issue C — registry hygiene
45 workspaces registered, **23 with missing roots**. `workspace prune` (dry_run first) would clean it.
