## Miller MCP server would not start — root-caused to a truncated plugin download plus a dead venv config entry

Miller's MCP server failed to start in Claude Code on `C:\source\miller` with **no `.miller/logs` output at all** (last log line: 2026-07-17). Two independent faults, both now diagnosed.

### Fault A — plugin launcher download truncating (the real blocker)
`bin/miller-plugin-launcher.cjs` fetches the release zip via plain `https.get` with **no resume and no retry**. The v1.18.2 Windows asset is `101,430,677` bytes. Three launcher attempts today (09:17, 09:18, 09:20) died at **2.5MB / 39MB / 44.5MB**, leaving orphaned `*.tmp-<pid>-*` files and three **empty** `stage-*` dirs under `~/.miller/plugin-cache/1.18.2/x86_64-pc-windows-msvc/`. No `package/` dir was ever promoted, so `miller.exe` never launched — hence zero logs, since Serilog file logging only starts inside the Miller process.

- **Fix applied:** cleared the partials, ran `gh release download v1.18.2 --pattern "miller-1.18.2-x86_64-pc-windows-msvc.zip"` into the launcher's `downloads/` dir, verified SHA-256 against the sidecar, then drove `ensureMillerPackage` via node to extract. This works *without* touching Miller's code because `ensureMillerPackage` reuses an already-present archive whose hash matches (`miller-plugin-launcher.cjs:189`) and early-returns when `package/<binary>` exists (`:487`).
- **Verified:** `miller.exe version` → `1.18.2+c49dc3712ad8`, and `claude mcp list` now reports `plugin:miller:miller — ✔ Connected`.

### Fault B — dead project-scoped MCP entry (could not fix from inside the session)
`~/.claude.json` → `projects["C:\source\miller"].mcpServers.miller` pointed at `C:\source\miller\.venv\Scripts\miller-server.exe` — a **Python venv path in a .NET repo**; neither the exe nor `.venv` exists. It showed as `✘ Failed to connect — -32000`.

`claude mcp remove miller -s local` reported success and a fresh `claude mcp list` confirmed removal, but **the live session flushed its in-memory copy back over it**. Cannot win that write race from inside the session — handed to the user.

### Discoveries worth keeping
- The source checkout genuinely matches the installed plugin: HEAD `00f9a8a8` is docs-only on top of `c49dc371`, which is the plugin binary's build SHA.
- The repo's own `.mcp.json` registers a *second* `miller` server via the same launcher; with Fault B's entry gone it surfaced as `⏸ Pending approval`. It should be **declined** — approving runs a duplicate Miller instance against the same workspace.
- `.tools/` is correctly restored (julie-extract 2.32.1 + semantic sidecar), so a source build is also viable via the launcher's `MILLER_BINARY` escape hatch (`:543`).
- Stale plugin caches for 18 prior versions (~1.5GB) remain under `~/.miller/plugin-cache/`.

### Impact
Miller tooling is restored for the *next* session (this one started before the fix, so its tool list is still empty). Expect Fault A to recur on every version bump until the launcher gains resume/retry — that is a genuine product weakness in `miller-plugin-launcher.cjs`.
