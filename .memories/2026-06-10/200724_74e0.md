## Task 3: Hardened leader liveness probe (M1) + stale identity clear on write failure (L1)

**WHAT:** `workspace health` leader diagnostics hardened against Windows pid-reuse crashes and stale `leader.json` truth.

- `LeaderIdentityFile.IsProcessAlive`: catch-all probe guard. Probe exceptions beyond ArgumentException/InvalidOperationException (e.g. `Win32Exception` access-denied probing an elevated pid-reuse process on Windows) collapse to **alive**, never crash, never spuriously `indexer_leader_dead`.
- Pid-reuse cross-check: new `IsProcessAlive(LeaderIdentity)` compares `Process.StartTime` (UTC) against the recorded `StartedAtUtc` with a ±10s tolerance (`PidReuseStartTolerance`); a process that started >10s AFTER the identity was recorded is a recycled pid → not alive. Legacy files without `startedAtUtc` (default timestamp) skip the cross-check.
- Test seam: parameter-injected `Func<int, LeaderProcessProbe>?` (internal, null = real probe) threaded through `LeaderHealthFacts.Read` — no mutable static, so parallel xUnit classes can't race.
- L1: `IndexerService`'s identity-write catch now calls `LeaderIdentityFile.TryDelete(millerDir)` so a failed write never leaves a crashed predecessor's identity as the visible truth.

**WHY:** `Process.HasExited` throws `Win32Exception` (not in the caught set) on Windows when the recorded pid was reused by an elevated process — crashing `workspace health`, the platform that motivated the leader-identity feature (commit ea023cc).

**HOW (key collapse decision):** kept `bool` return (no tri-state); probe-failure collapses to alive because the pid provably exists at that point (`GetProcessById` succeeded) and a false would degrade health with a spurious dead-leader warning. Documented in `IsProcessAlive_ProbeThrows_CollapsesToAliveNotDead`.

**IMPACT:** Health renderers unchanged (no shape change); Windows health no longer crashable by pid reuse; dead-leader reports now resistant to pid recycling on all platforms.
