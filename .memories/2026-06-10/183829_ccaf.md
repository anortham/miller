## Root-caused agent "index stale on recently edited files" complaints

**WHAT:** Systematic review of the file watcher / freshness path. The watcher itself is healthy (rename/overflow/HEAD handling all correct; logs show events converging). The staleness complaints are structural read-your-writes latency plus multi-process topology.

**ROOT CAUSE (chain):**
- Leader debounce loop ticks every **1s** (`IndexerService.DebounceInterval`) before draining watcher events; then single-file extract + sidecar converge.
- In-memory index swap needs `FreshnessService` poll = **2s** in leader AND 2s in each reader.
- Edit gate (`FreshnessGate`) reads the DB directly → ~0–1.6s stale window after any disk write; search/inspect/context read the in-memory holder → up to ~3.5–5s in reader-served sessions. Agents' edit→tool gap is <1s, so they routinely hit it.
- **Sessions are almost never the leader**: first process wins the lease forever; right now this workspace's leader is the plugin-cache 0.3.6 binary (pid 84043) while the dev session server (84045) is a reader. `LeaderWriteThrough`/`TryReindexAsLeader` is a **no-op in readers**, and the only cross-process request is a whole-repo full scan (`LeaderScanRequestQueue`) — no single-file converge request exists. So a second Miller edit to the same file within ~1–2s is refused ("index stale for {file}", EditService.cs:469).
- Aggravator: stale long-lived processes (a 0.3.5 server from 7:03AM still running); this morning a schema-2 DB written by an old julie-extract forced a rebuild.

**RECOMMENDED FIXES (not yet implemented):** (1) gate-time self-heal — on stale verdict, leader reindexes the file inline and re-checks before refusing; (2) single-file cross-process converge requests so readers get write-through; (3) tighten debounce/poll intervals; (4) leader/process hygiene surfaced in `workspace health`.
