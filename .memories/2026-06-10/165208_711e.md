## Fixed Miller AccessIQ schema-mismatch thrash + added stale-binary build guard

**Problem:** AccessIQ (and `C:\source\miller`) Miller indexes kept failing with `IncompatibleExtractException` (DB schema 2 vs build-expected 3); the agent couldn't get the index to rebuild.

**Root cause:** Two Millers share the workspace indexes on this machine — **Codex** runs the local source Release build (`~/.codex/config.toml` → `bin/Release/net10.0/miller.exe`), **Claude Code** runs the downloaded plugin release. After commit `c5612cc` bumped the pin to julie-extract **2.2.1 (schema 3)**, the source build's `.tools/julie-extract.exe` was never re-restored, so it stayed **2.1.3 (schema 2)**. The plugin (2.2.1) wrote schema 3; the source build (2.1.3) rejected/overwrote to schema 2 → thrash. The build copies `.tools/julie-extract` with no version check, so the stale binary was silent.

**Fix (machine state):**
- `scripts/restore-julie-extract.ps1` → repo `.tools` now 2.2.1 (sha-verified)
- Rebuilt Release + Debug → output `.tools` now 2.2.1
- `miller workspace full` rebuilt AccessIQ (rev 254) and `C:\source\miller` (rev 63); all 6 registry workspaces now `ready`

**Fix (prevention, code):**
- Added `VerifyPinnedJulieExtractVersion` MSBuild target in `Miller.Server.csproj`: offline guard runs the restored binary's version, FAILS the build if it ≠ `scripts/julie-pins.json` pin (no-op when binary absent → offline builds preserved). User chose version-string check over hash/network.
- Added `ServerProjectGuardsAgainstStaleJulieExtractVersion` convention test.
- Documented in CLAUDE.md (+ synced AGENTS.md).
- Drive-by: `ContentCorpusContextReaderTests.Dispose` was missing `SqliteConnection.ClearAllPools()` (pre-existing Windows-only file-lock flake) — added it to match sibling convention.

**Verification:** Guard fail-path proven (bogus pin → build fails with restore message), pass-path green. Fast suite green: 1839 passed / 0 failed / 8 skipped.
