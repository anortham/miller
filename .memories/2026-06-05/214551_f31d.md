## Made disk symbol search lazy and cut OpenClaw CLI search to ~0.26s

- **WHAT:** Refactored `FtsSymbolSearchIndex` so `Open()` reads only `meta` and validates FTS tables instead of eagerly materializing every `search_symbols` row into `SymbolLookupTables`. Symbol metadata is now fetched on demand for FTS candidates, exact symbol/file lookups, and summary inspect resolution. Updated TODO and large-repo dogfood docs with the new measurements.
- **WHY:** After routing CLI `search` and summary `inspect` away from full graph hydration, OpenClaw one-shot CLI symbol search was still ~1.8s. DB timings showed the actual FTS candidate lookup was tens of milliseconds, while eager `SELECT ... FROM search_symbols ORDER BY path, start_line, symbol_id` took `real=1.82s` on its own.
- **HOW:** Kept the existing `ISymbolLookupIndex` interface and current search sidecar schema. `FtsSymbolSearchIndex` derives `DocId` from `search_symbols.rowid - 1`, relying on `SearchIndexWriter` inserting rows in the deterministic `SqliteSymbolReader` order. `Search()` joins FTS candidates to `search_symbols` and re-scores only candidates; lookup methods issue targeted SQL queries; path/extension helpers lazily load distinct paths only when needed.
- **IMPACT:** OpenClaw Release CLI `miller search "workspace status"` is stable at ~0.26-0.27s, scoped symbol search ~0.26s, file mode ~0.31s, summary inspect ~0.31s. Full inspect/context remain full-path at ~6.7s, which is now clearly the remaining graph-heavy lane rather than symbol search overhead.
