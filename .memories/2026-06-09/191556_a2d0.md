## Patterns tool design drafted

### WHAT
Added a design document for a future `patterns` MCP/CLI surface over `julie-extractors` v2.2.0 `structural_facts`.

### WHY
The user wants Miller to expose extractor-backed code shapes in a way that can expand to C#, htmx, and other future patterns without requiring Miller-specific branches for each one.

### HOW
The design treats extractor rows as sticky notes: `pattern_id` identifies the code shape, `metadata_json` carries pattern-specific details, and Miller only lists, filters, groups, and renders facts. It reserves generic `--where key=value` metadata filters alongside a required `pattern_id` to support cases like `htmx.attribute.v1` plus `name=hx-get` while keeping first-slice queries bounded.

### IMPACT
Future implementation can add a standalone `patterns` tool/CLI and a stable `patterns-json-v1` contract. Unknown future `pattern_id` values should work automatically after re-indexing, while friendly catalog labels remain optional decoration.
