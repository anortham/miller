## Wrote the full Miller performance recovery plan

### WHAT

- Added `docs/plans/2026-08-13-miller-performance-recovery-plan.md`, an eight-task cross-repository execution program.
- Added the plan to `docs/README.md`.
- Recorded measured evidence, Linux/Windows budgets, exact file ownership, serial/parallel lanes, rollback switches, TDD choreography, verification commands, completion criteria, and approval boundaries.

### WHY

Miller is fast for ordinary warm reads but slow in coupled producer convergence and selected relationship paths. The plan must recover performance without disabling the features that make Miller useful or confusing accumulated-store cost with a missing incremental resolver.

### HOW

- Producer path: characterize dead-import takeover, preserve exit-135 facts, measure import/resolve/bind/sidecar/vector phases, then repair only the proven phase.
- Resolution: prove the already-shipped scoped resolver against full digests and timing; move accumulated overlay retention to pin-safe publish-before-collect maintenance.
- Context: batch the current inbound/outgoing evidence reads and skip them only when the existing token estimator proves no identifier can fit.
- Impact: preserve the existing 500-2,000 traversal window and rank-before-limit behavior; optimize the candidate-driven SQLite/family-resolution read shape with exact parity.
- Platform: require Linux PSS and Windows PrivateUsage gates, dedicated Windows semantic-broker soak, and exact source-SHA restoration.
- Review: Grok 4.6 performed a read-only adversarial review. Accepted findings were applied; the proposed graph API expansion was rejected as unsupported by evidence.

### IMPACT

The next session can execute from a bounded plan without rediscovering root causes, duplicating shipped work, replaying stale commits, or crossing pin/push/release approval boundaries.
