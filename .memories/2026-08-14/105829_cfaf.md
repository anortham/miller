## WHAT

Lead review found and corrected one production ordering regression and found two additional replay-harness fidelity defects before baseline execution.

## WHY

A misleading replay would send optimization work toward the wrong owner. The staged Miller workspace and Julie source root require distinct validated view identities, and Julie's report generation is not the same identifier as the family store's generation directory.

## HOW

- Registry-first correction landed at `c3b8d7cf`: an existing usable registered lineage is checked before pointer adoption. Resolver 24/24 and combined coordinator/bootstrap 97/97 passed under lead verification.
- Public Julie source evidence proves an existing view rejects a different root with `view_root_mismatch`; `store import --view <new-id>` creates a view, while `store resolve` requires an existing view and accepts no root.
- `producer.retry.identical` cannot use the staged Miller view. It needs the original read-only source view but a newly created disposable request with disposable supervision paths; replaying the incident request is unsafe because its persisted spool/progress/ignore controls target the original workspace.
- Source-changing rows must clone the source into the temporary pointer workspace, create/import/resolve a fresh root-matching view before mutation, then change/import and measure resolve.
- Real Julie JSON reports `manifest.generation` as a number, while the harness's `ActiveStore.generation` is a directory such as `gen-007`; comparison must instead use the selected view's durable `current_generation`.

## IMPACT

Task 1B-C remains open. A Luna correction is active in `scripts/perf-recovery.py`, its tests, and the workload manifest. No copied-store baseline has been run, and no live pointer/store was mutated.
