## CT dogfood on the Miller repo — first findings

**WHAT:** Enabled and started the new CT (continuous testing) feature on the Miller workspace itself (miller 1.20.1+f955e1de). Ran enable → start → run and watched the sidecar.

**WHY:** Dogfood the tenth MCP tool (`tests`) on a real repo before wider use.

**HOW:** MCP `tests` operations plus read-only sqlite inspection of `.miller/ct.db` and `/tmp/miller-ct` build generations.

**Findings so far:**

- **Discovery over-matches projects.** `ContinuousTestProjectInventory.TryIdentify` accepts any `.csproj` whose file name contains "Test" (`namedTest` heuristic). It enabled `src/Miller.Testing/Miller.Testing.csproj` (a class library) and `tests/Miller.SharedBrokerTestHost` (a helper host). Both produced `ct_discovery_failure` runs: the library has no executable to start; the host crashed with exit 134 (missing `--endpoint` arg).
- **Red verdict from misclassified projects.** The aggregate verdict went red on those discovery failures while the real suites passed — a green repo shows red on first CT contact.
- **No default Scale exclusion.** `exclude_traits` is `[]` on enable, and the xunit provider runs the built test executable directly, so `VSTestTestCaseFilter=Category!=Scale` in the csproj does NOT apply. CT runs the full Miller.Tests suite including Scale tests. No CLI/MCP path found to set exclude_traits.
- **UX:** compact status prints the full composite `selected` key (hundreds of chars); `failures` next-step hint says "inspect — open a failing test" even when failures are discovery failures, not tests.
- Small eval suites (FusionArm.Tests, RetrievalEval.Tests) passed via CT correctly; ct.db schema and `/tmp/miller-ct` generation dirs work as designed.

**IMPACT:** Miller.Tests CT run still executing (started 18:24:37Z). Next: read final verdict, then decide fixes (tighten TryIdentify, seed/allow exclude_traits, verdict semantics for discovery failures).
