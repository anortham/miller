## Continuation tokens switched to a compact binary format

All opaque continuation tokens (inspect file listing, inspect depth=full body pages, trace refs pages, patterns pages, impact output pages) were JSON-with-hex-strings wrapped in base64url — ~470 characters for a population cursor. They now use a version-2 binary payload and come out at ~200 characters (43% of the old size).

- **Format:** `[version=2][type: 1=body|2=population][fields][raw 32-byte SHA-256 over the preceding bytes]`. Strings are flag+varint-length+bytes, where the flag marks lowercase-hex fields packed to raw bytes (the four 64-hex ids are where the size win lives). Integers are unsigned LEB128 varints.
- **Where:** all encode/decode lives in `ToolOutputBudget` (`src/Miller.Server/Tools/ToolContinuation.cs`) — one file, every tool benefits. Public API, diagnostic codes (`continuation_invalid`, `stale_continuation`, mismatch codes), and the opaque-token contracts are unchanged.
- **Compatibility:** tokens from older builds start with `{` (0x7B), fail the version-byte check, and get the existing `continuation_invalid` refusal with the restart action. Tokens are ephemeral mid-pagination state, so no legacy decode path was kept.
- **Cross-type safety:** a body token fed to the population decoder (or vice versa) is rejected by the type byte — new regression tests cover both directions, plus legacy-JSON rejection, non-hex/Unicode identity round-trip, and a ≤220-char compact-size gate.
- **Verified:** ToolContinuationTests 20/20; consumer classes (Inspect/Trace/Patterns/Impact/CliDispatch) 580 pass; fast suite 6822 pass.
