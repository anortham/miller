### Fix 3 — .NET provider argv chunking (the headline blocker)
Measured on the real assembly: 6047 xunit methods, avg FQN 100 chars, 659,135-char command line = 20.1x the 32,767 Windows cap; only ~300 methods fit. Proved xunit v3 has NO response-file option (runner rejects @file), so chunking is the only fix.
The audit added the fact I lacked: TestsCore.cs:592 and ContinuousTestDaemonHost.cs:347 enqueue with WorkspaceScope: true, so the FIRST explicit `tests run` builds the whole argv — no file change needed to trigger it.
Built shared Miller.Testing/Providers/Shared/CtArgvChunking.cs (Chunk over UNITS so a chunk boundary can never fall between a flag and its value; 120 units / 6KB). DotnetTestProvider gained BuildRunCommands (chunked), XunitSelectionUnits, BuildXunitRunCommand, and MergeRuns (worst-status wins, min start, max end, concat cases, union display names). Each chunk gets its own .partNNN.junit.xml so chunk N cannot overwrite N-1. FilterArguments override is NOT chunked — it is opaque argv with no safe split boundary.
Verified: disabling chunking turns 3 of the 6 new provider tests red.

### Fix 4 — Node provider could not launch on Windows at all (blocker)
JavaScriptTestProvider.PackageManager returned a bare "npm"/"pnpm"/"yarn" used directly as a process FileName. Proved empirically: bare npm with UseShellExecute=false throws Win32Exception "The system cannot find the file specified" (PATH search only considers npm and npm.exe; the extensionless file is an MSYS shell script). npm.cmd launches fine. Fix appends .cmd on Windows, mirroring LocalBin which already did this. Two tests that asserted "npm" encoded the bug; made them platform-aware.

### Fix 5 — CT control-plane atomic write (high)
CtDaemonJson.TryRead used File.ReadAllText (FileShare.Read) and WriteAtomic used File.Move(overwrite:true) with a FIXED "<path>.tmp".
IMPORTANT — the audit's proposed fix was WRONG and I disproved it. Measured matrix on Windows 11:
  File.Move(overwrite:true): UnauthorizedAccessException with reader share=Read AND with share=ReadWrite|Delete
  File.Replace:              IOException with share=Read, OK with share=ReadWrite|Delete
So File.Move + retry could never work (a poller holds the file open the whole time). BOTH halves are load-bearing: reader must share Delete, and publish must be File.Replace (Win32 ReplaceFile). Also made the temp name per-process-per-thread (bounded and self-cleaning; a Guid would orphan a file on every crash with no reaper).
