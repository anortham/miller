## Windows CT dogfood — baseline green, three defects found, two fixed

First native Windows run of the CT sidecar port (main @ 9322cfee).

### Test baseline on Windows
- Fast suite: 7348 passed / 2 failed / 27 skipped (7377 total, ~1m22s)
- Scale suite: 147 passed / 0 failed / 13 skipped (1m39s) — julie-extract and CT providers all spawned natively and passed
- Installed pytest 9.1.1; PythonProviderScaleTests converted SKIP to pass (1/1)

### Defect 1 — test holds store.db open across Directory.Delete (FIXED)
QueryTimeResolutionReaderTests.FamilyModeEvidenceWorksWithNoAttachedResolutionBase failed deterministically in isolation: "process cannot access the file store.db". Line 119 built FixtureReadSession (owns a SqliteConnection, implements Dispose) WITHOUT using, so the handle was live when the fixture ran Directory.Delete recursive. Linux unlinks open files; Windows refuses. Fix: added using. 15/15 green.

### Defect 2 — CT discovery descends into nested checkouts (FIXED, with tests)
miller tests enable reported 6 projects for a 3-project repo, walking into .worktrees/fix-windows-dogfood-read-availability — a gitignored linked worktree on a DIFFERENT branch. CT would build and run another branch's source under this workspace's freshness key. Root cause: EnumerateCandidateFiles filtered only a fixed name set (bin, obj, node_modules...) with no nested-repo awareness. Fix: IsNestedCheckout stops the walk at any directory containing a .git file OR directory — the file case is essential since a linked worktree's .git is a FILE holding gitdir. Verified red-without-fix, green-with-fix; after clearing ct.db, enable reports 3.

### Defect 3 — enable never prunes, materialize never checks existence (OPEN)
TestsCore.Enable line 188 discovers but line 202 returns ALL store rows, so stale rows persist. MaterializeProjectWorkItems has no File.Exists check, so a deleted project becomes a work item and fails to build every cycle. Store has no delete, only SetContinuousTestProjectEnabled.

### Windows argv cap — measured, not yet fixed
xunit v3 emits -method per test, unbounded. Measured on the real assembly: 6047 methods, avg FQN 100 chars, total command line 659,135 chars (644 KB) = 20.1x the 32,767 Windows cap. Only ~300 methods fit. xunit v3 has NO response-file option, so chunking is the fix. RustTestProvider already solves this (MaxFiltersPerInvocation=120, MaxFilterBytesPerInvocation=16KB, ChunkFilters) — that is the house pattern to copy.

### Empirical: .cmd shims cap at 8191, not 32767
Modern .NET CAN launch npx.cmd with UseShellExecute=false (tested OK). But that routes through cmd.exe, so the limit is 8191: at ~7691 chars exit 0; at ~8331 chars exit=1 with stderr "The command line is too long." — a nonzero exit, NOT an exception. Node provider (npm/pnpm/yarn shims) needs the tighter bound.

### Windows dev friction
A running miller MCP server (PID 30852) holds Miller.Testing.dll open and BLOCKS a Release rebuild (MSB3027). Worked around by building Debug. Did not kill the user's server.
