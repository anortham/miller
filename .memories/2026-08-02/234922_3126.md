## W8 complete — persisted scan-failure policy + ScanIntent enum, after two fix rounds

**WHAT.** `ScanIntent` (six members) replaces `bool force` at the orchestration boundary; a persisted
`<workspace>/.miller/scan-failure.json` becomes the SOLE whole-repo retry timer (30s/2m/10m/30m-max, jitter only
adds); a downgrade becomes a THIRD scan outcome; `--jobs 1` clamp after exit 137.

**WHY.** N worktree agents each re-attempted an OOM-killed extractor from scratch because the backoff lived only
in process memory. Nothing about a failure survived a restart, so a force rebuild that could not succeed was
re-forced forever, each attempt taking the machine-wide scan lease.

**HOW — the two fix rounds mattered more than the first implementation.**
- Round 1 (G1–G8) fixed: a downgraded success spinning the drain loop forever (whole-repo delta every 250ms);
  `workspace full` reporting a delta as a completed rebuild; `bypassBackoff` skipping the timer but not the
  downgrade; `RecordSuccess` clearing unconditionally so routine `workspace refresh` erased the throttle; the
  registry rider demoting healthy rows; read traffic defeating the backoff; a completed force leaving
  `ExtractorUpgrade` armed (second byte-equivalent rebuild); Windows sharing violation losing the record.
- Round 2 (this session) fixed two defects the round-1 FIX introduced, both probe-proven by the confirmers:
  - **R-A**: a failed downgraded retry recorded intent verbatim, WEAKENING a force record to delta intent —
    after which the next routine refresh cleared it. G4 reopened in two steps. Fix: `RecordFailure` folds via
    `ScanIntentPolicy.Strongest`, so the record names the strongest scan still owed.
  - **R-B**: `RecordSuccess` reused `ScanIntentPolicy.Satisfies` (a LATCH-discharge rule) as the record-clearing
    rule. `Satisfies(UserFullRebuild, CorruptionHeal)` is false, so a failed repair left a record no
    `workspace full` could ever clear — and every future automatic rebuild was silently downgraded forever. Fix:
    a distinct `ScanIntentPolicy.ClearsFailureRecord` = `RequiresForce(completed) || !RequiresForce(recorded)`.

**HOW — the lesson.** The two rules WANT different answers. A latch tracks whether a promised repair happened
(own-intent-only). A failure record tracks whether scanning this workspace is still failing (any force is
evidence it is not). Reusing one for the other is what stranded the record.

**Also closed this round:** `WorkspaceIndexProvider.AutomaticRefresh` extracted as a named seam so its
`bypassBackoff: false` posture is testable (it was a constructor lambda a mutation could flip unobserved);
`ScanFailureJournal.TryClear`'s delete now retries like the write path; the cross-workspace refresh path emits
the downgrade note (unreachable today — every force caller passes bypass — but it would have shipped the same
lie the moment one dropped it); `ScanFailurePolicy.DescribeDowngrade/DescribeIntent` shared by both paths.

**IMPACT.** Unblocks W9, and unblocks tasks #11 (W1 bootstrap empty-artifact reuse gate) and #12 (ScanGovernor
admission held while blocking on `_opsGate`), both of which were held off because W8 was editing
`IndexBootstrapService.cs` / `IndexerService.cs` concurrently.

**Unproven:** the Windows sharing-violation hardening (G8) and the new delete retry (R-G) have no test — the
failure mode cannot be reproduced on macOS. CI's Windows fast-suite job exercises the path but does not assert
the contention behavior.
