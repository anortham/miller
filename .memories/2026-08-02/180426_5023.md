## W3 — machine-wide scan governor (fleet-safety)

### WHAT
`SingleWriterLock` is strictly per-workspace, so N git worktrees means N independent leaders with nothing above them — a fleet of agents ran N concurrent `julie-extract` processes and drove the reporter's machine into the OOM killer. W2 capped each pool's *width*; W3 caps how many pools run *at once*.

One user-global, capacity-1 lease at `~/.miller/scan/scan-v1.lock` gates every whole-repo extractor scan and the synchronous sidecar convergence that follows it. Per-file `update`/`delete` stay exempt — they are sub-second and gating them would stall interactive edits.

### Design decisions that a stale recon brief got backwards
- **NOT re-entrant.** The recon wanted a per-process re-entrancy counter to avoid a self-deadlock across `RunStartupDeltaScan` → upgrade rescan → drain rescan. Those run *sequentially*, so the nesting does not exist — while one process genuinely CAN scan two different workspaces at once via `WorkspaceIndexProvider._refresh`, which a counter would wrongly admit, defeating the entire point. Same-thread re-entry throws; different threads queue on the OS handle.
- **Admission is taken BEFORE `_opsGate`**, never inside it — `TryReindexAsLeader` holds that gate and is the `edit` tool's write-through.
- **There is no C# "semantic accelerator lease" to mirror** (the plan said there was). Miller only computes `accelerator-v1.lock` and hands it to the Rust sidecar. Mirrored its path convention and crash semantics; took the mechanism from `SingleWriterLock` + `ContentCorpusWriteLock`.
- **Budget principle:** a path that retries gets seconds; only a path with no retry gets the long operator budget. Bootstrap keeps its long wait (no retry, and W1 renders friendly not-ready); the debounce drain, MCP interactive paths, and every latch-re-arming site get 5s.

### What adversarial review caught that the suite did not
Three reviewers with distinct lenses, all `fix-first`. Three fix rounds, each surfacing consequences of the previous one.

**Critical, found independently by all three:** the drain passed `wholeRepoScanAdmitted: !mayScanWholeRepo || admission is not null`. When the pre-drain peek said "no scan needed," no admission was taken but the argument evaluated `true` — so a rescan flag arriving in the window (the tick blocks on `_opsGate` while an update runs; the watcher only takes the core gate) spawned a full extract with **no lease held**. The comment three lines above asserted the opposite guarantee.

**Two regressions W3 introduced:**
- `RequestWholeRepoScan()` carried no force bit, so a refused *forced* scan re-armed as a delta scan — which then succeeded (nothing changed on disk) and cleared the latch. That silently broke the load-bearing "newer-extractor leader auto-runs a forced full rescan" invariant.
- The retry latch had no backoff. Pre-W3 a failed whole-repo scan ran once; after, the 250ms debounce loop respawned the extractor forever, taking the machine-wide lease each time. An OOM-killed extract would loop indefinitely, starve every sibling worktree, and leak a spool per attempt — **recreating the exact ~130 GB two-day failure this branch exists to prevent.** Reverting the fix produced "took the machine-wide lease 240 times in 60s of ticks".

**The W1 lesson repeating:** the test claiming the lease spans sidecar convergence *could not fail* — it sampled a read that happens before the scan, so releasing the lease early passed every assertion. Five of eight governed call sites had no admission test at all, including the one carrying the critical bug.

**Round-2 consequences:** a governor refusal was rendered to the agent as "the scan failed, check the log for the extract error" (an error that does not exist) with nothing re-armed; and out-of-band successful scans never cleared the latch, so a successful forced rebuild could be immediately followed by a *second* from-scratch rebuild in the same tick.

**Round-3 consequences, fixed by hand:** a successful scan was not resetting the failure backoff on a generation mismatch (success is evidence the extractor is healthy — split `ResetScanFailureBackoff` from `ClearWholeRepoScanLatch`); and the drain bound was scoped out of the backoff path, leaving the same 1000-subprocess storm alive in that window. The cause does not matter — if a whole-repo scan is owed and will not run this tick, a large batch stays queued (`MaxDeferredScanDrain`).

### IMPACT
Closes the last P0. Status/health output stays byte-identical when the governor is idle; `MILLER_SCAN_GOVERNOR=0` is a genuine zero-work opt-out. Known limit, stated in the XML doc rather than overclaimed: the lease is under `~/.miller`, so it governs one *user's* fleet, not the machine — two OS users still run two concurrent scans.
