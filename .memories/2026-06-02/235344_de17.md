## Phase 2 search projection: basic `inspect` uses the lookup/search projection

Recovered and completed phase 2 of the search-projections design (`docs/plans/2026-06-02-search-projections-design.md`) after a crash that lost the original phase 2 checkpoint. The code+tests were already written before the crash; this checkpoint verifies and records that state.

### WHAT
Registered-workspace `inspect depth=summary` (the default depth) now resolves through the cheap `SymbolSearchProjection` instead of the full `MillerRepositoryIndex`. `inspect depth=full` still routes through the full repository projection for children/refs/callers/callees/body.

### HOW
- `MillerRepositoryIndex` now implements `ISymbolLookupIndex` (new interface: `FindByName`/`FindBySymbolId`/`FindByFilePath`/`IsIndexedFilePath`/`ResolveIndexedFilePath`/`KnownExtensions`, extends `ISymbolSearchIndex`). `SymbolSearchProjection` implements it too.
- `SmartTargetResolver` switched from holder-typed `MillerRepositoryIndex` to a `Func<ISymbolLookupIndex>` delegate; added an `ISymbolLookupIndex` ctor for projection-specific paths. The holder ctor still reads live per call.
- `InspectTool` split: `full` branch → `IWorkspaceIndexProvider.Resolve` (full index + cached resolver); summary branch → `IWorkspaceSearchProvider.ResolveSymbolSearch` (projection, builds a per-call resolver). Shared `RunCore` carries `MillerRepositoryIndex? fullIndex` and throws if full data is requested without it.
- `WorkspaceIndexProvider` gained `ResolveSymbolSearch` + `ResolveCurrent/RegisteredSymbolSearch`, a separate revision/path-keyed `_symbolSearchCache`, generic `EvictOtherEntriesForWorkspaceUnderLock<T>`, and single-flight `GetOrLoadSymbolSearch`. `ResolveRegisteredState` was extracted so full and search paths share refresh/root-verification.
- DI registers `WorkspaceIndexProvider` once and exposes it as both `IWorkspaceIndexProvider` and `IWorkspaceSearchProvider`.

### WHY behavior is preserved (byte-equivalence)
`SymbolSearchProjection.Build` constructs `bySymbolId`/`byName`/`byFilePath`/`byFileName`/`knownExtensions` with logic identical to `MillerRepositoryIndex.Build` (same `Add` helper, `LastPathSegment`, ordinal/ordinal-ignore-case comparers). `SmartTargetResolver` touches only the `ISymbolLookupIndex` surface. The summary render path never reads `byParentId`/graph/bridge — those are full-only. So summary resolution + rendering are identical; the projection just skips graph/bridge hydration. Current-workspace summary still uses the already-built full holder index by design.

### IMPACT
Registered-workspace `inspect` (the ~44%-of-calls tool) no longer pays full graph/bridge hydration on first read, matching the phase 1 win for `search`. Remaining design work: phase 3 content/docs search projection, phase 4 deliberate symbol-field widening.
