## CT provider expansion plan written for JVM, Ruby, PHP, GDScript

**WHAT:** Wrote `docs/plans/2026-09-01-ct-providers-jvm-ruby-php-gdscript-implementation-plan.md`. It plans four new CT provider families: JVM (Maven/Gradle/sbt behind an `IJvmTestBackend` seam), Ruby (RSpec), PHP (PHPUnit/Pest), GDScript (GUT). Nine serialized tasks: runner-surface spike, shared JUnit XML parser, then one vertical slice per ecosystem, docs closeout.

**WHY:** A gap audit from julie-extractors (2026-09-01) showed Miller CT covers 14 of 40 julie languages. The user picked JVM, Ruby, PHP, and GDScript as the next providers. The 2026-08-27 language-readiness audit confirms julie test facts are sufficient for all four; the blocker is Miller providers only.

**HOW (key decisions):**
- Framework values fixed as contract: `maven`, `gradle`, `sbt`, `rspec`, `phpunit`, `pest`, `gut`; `minitest` and `gdunit4` become recognized-but-refused via `ContinuousTestFrameworkSupport` (xunit-v2 pattern).
- Shared `JUnitXmlResultParser` in Providers/Shared feeds JVM backends, PHPUnit, and GUT.
- Maven and sbt get per-class cases (no dry-run listing); Gradle per-method via `--test-dry-run`; RSpec per-example via `--dry-run --format json`; GUT per-script. Python's per-file precedent covers the coarse granularities.
- Task 1 spike verifies every runner surface against real tools before provider code (grounding-in-current-docs).
- Ecosystem tasks serialize: they share ContinuousTestProviderFactory.cs, ContinuousTestProjectInventory.cs, ContinuousTestLanguageFamily.cs, CtProviderTestSupport.cs.

**IMPACT:** Plan awaits user approval. Not committed. Miller main worktree carries unrelated uncommitted marker-search changes; the plan file is additive and does not touch them.
