## Fixed Windows bootstrap crash-loop: UriFormatException in Blazor namespace resolution

**WHAT:** `BlazorProjectNamespaceResolver.TryReadXml` now opens project files via `FileStream` + `XmlReader.Create(stream)` instead of `XmlReader.Create(string path)`. Added regression test `QualifiedNames_ExtendedLengthWorkspaceRootResolvesProjectNamespace`.

**WHY:** Every Miller MCP server on Windows crash-looped at bootstrap with `Invalid URI: The hostname could not be parsed` in any workspace containing Blazor components (AccessIQ and the miller repo itself). Agents were falling back to grep/read and saving "Miller is broken here" memories.

**HOW (root cause chain):**
- julie-extract (Rust) records `artifact_metadata.root_path` in Windows extended-length form: `\\?\C:\source\AccessIQ` (Rust `canonicalize()` behavior).
- The Blazor namespace feature (2026-07-14, shipped in v1.10/1.11) is the first consumer to feed that artifact root into file paths: `BlazorComponentGraphReader.Read` → `BlazorNamespaceCatalog` → `TryReadXml`.
- `XmlReader.Create(string)` URI-parses the path; `new Uri("\\?\C:\...")` throws `UriFormatException` ("hostname could not be parsed" — the `?` is parsed as a UNC hostname).
- `UriFormatException` is a `FormatException`, not covered by the catch (`XmlException` + file-I/O types), so it escaped `RepositoryIndexLoader.Load` and killed bootstrap; the server restarts and crashes again forever.
- Why CLI `search`/`trace` looked fine: only `trace --mode bridge` calls `RepositoryIndexLoader.Load` in the CLI; other verbs use the FTS sidecar / lighter loaders. `miller trace X --mode bridge` was the deterministic CLI repro (exit 1, same message).

**IMPACT:** Fast suite green (3582 passed). Locally built miller loads the AccessIQ artifact and answers `trace --mode bridge` (bridge providers active: dotnet-web, blazor). Every Windows workspace with Blazor components is fixed once a release ships — plugin users still run broken 1.11.0 until then.
