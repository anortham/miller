## Idle Miller leaders spawned julie-extract every 250 ms tick

**WHAT:** `IndexerService.TryRetryStoreSidecarsOnIdle` (src/Miller.Server/Hosting/IndexerService.cs) ran on every empty debounce tick (250 ms) and opened a full family-store read session BEFORE checking whether a sidecar retry was due. Opening the session admits a reader via a `julie-extract store reader acquire` child process and writes `coord.db`.

**WHY:** Introduced by 3af49491 (2026-08-22, "reconcile quiet derived state"); shipped in 1.29.0. Symptom: idle miller.exe at ~12% CPU per leader, julie-extract spawning 1-2x/s, coord.db mtime churn, and reader-registration `Busy` failures for sibling readers.

**HOW:** Added an inspection gate to `StoreSidecarRetryState`: `ShouldInspect(now)` is true only when the 30 s `IdleInspectInterval` elapsed, a retry target is due, or `RequestInspect()` was called. The idle path calls `ShouldInspect`/`MarkInspected` before opening any session; the processed branch calls `RequestInspect()` right after `TryConvergeSidecarToLatest` so a failed converge is still discovered on the next tick. Existing test `IdleStoreSidecarRetry_ArmsThenConvergesOnceAndClears` now expects 2 inspections instead of 4 (the reduction is the point). New tests: `StoreSidecarRetryState_IdleInspectionWaitsForTheIntervalOrADueRetry`, `IdleStoreSidecarRetry_HealthyStoreIsInspectedOncePerIntervalNotPerTick`.

**Rejected:** making the inspection cheaper by reading the freshness stamp instead of a session (deeper change to the store read path); event-driven-only retry (drops the safety net for converges that fail outside the leader's own tick).

**IMPACT:** Idle leaders do ~120x fewer store opens. Needs a release to reach the plugin build.
