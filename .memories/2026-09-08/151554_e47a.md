## WHAT

Verified the pinned semantic sidecar's native batching and GPU placement behavior against the exact v0.1.0 release source.

## WHY

The full vector rebuild measured about 39 short symbol cards/s and 5 long chunks/s. The open question was whether `embed_batch` only batched IPC while invoking the model once per text.

## HOW

- `protocol::embed_batch` passes the complete text array to `EmbedEngine::embed` once.
- `LlamaEngine::embed` tokenizes all inputs and partitions them with `group_by_cell_budget` under `longest_tokens * sequence_count <= 2048` for the CLS-pooled BGE model.
- `encode_group` adds every grouped sequence to one `LlamaBatch` with distinct sequence IDs and calls `context.encode` once per group.
- Therefore batching is native, though an RPC of 64 long near-512-token chunks becomes roughly sixteen native groups of four rather than one 64-sequence forward. Short cards pack many more sequences per native forward.
- Accelerator placement keeps llama.cpp's `n_gpu_layers=-1` default for non-CPU candidates and applies the enumerated device index. No current runtime log captured llama.cpp's `offloaded N/N layers` line, so exact runtime layer residency remains unproven.

## IMPACT

The measured length-sensitive throughput is consistent with intentional token-cell microbatching, not a missing native batch implementation. No Miller or sidecar source change is indicated by this evidence.
