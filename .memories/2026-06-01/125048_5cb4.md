## Product Direction Checkpoint

### WHAT

Captured the post-dogfood Miller direction after the user rebuilt/restarted the MCP server.

- Large-workspace fixes are already committed on `main`: `afffbd2 fix: bound large workspace read costs`.
- Brief update is committed as `a75e702 docs: update miller dogfood brief`.
- User asked whether hot-reloading Miller MCP is worth solving; conclusion was no for now, to avoid sidetracking.
- Next product focus is first-read read-path performance for large workspaces.

### WHY

Miller's current product bottleneck is not registry status anymore. It is that cross-workspace `search` and `inspect` still route through full index hydration via `WorkspaceIndexProvider` / `RepositoryIndexLoader`, causing large first-read latency and memory cost on OpenClaw-scale repos.

### HOW

Recommended next design direction:

- Add projection-specific loading rather than one full `MillerRepositoryIndex` for every read.
- Keep `workspace status` and dashboard metadata on cheap facts reads.
- Start with search and inspect projections.
- Lazy-load graph/bridge structures only for trace/impact when needed.
- Keep SQLite FTS5 parked until profiling proves BM25 is actually the limiting factor.

### IMPACT

The next session should not restart the MCP-hot-reload discussion unless the user reopens it. It should move into a design for large-workspace read projections, with explicit acceptance targets for first `search` / `inspect` latency and memory on large registered workspaces.
