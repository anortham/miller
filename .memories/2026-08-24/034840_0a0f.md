## WHAT

Completed and lead-reviewed Task 4. `ContinuousTestDaemonHost.Evaluate` now asks `ContinuousTestStore` for one aggregate status row and feeds a pure aggregate projection, instead of materializing every detailed status and watermark collection every 250ms.

## WHY

The pre-change idle daemon consumed 7.08 CPU-seconds per minute while repeatedly allocating detailed objects for 8,368 states. User-facing detailed APIs still need those objects, but the daemon snapshot needs only total, pending, stale, and fresh-red counts.

## HOW

Added `ContinuousTestStatusAggregate`, a parity-preserving projection overload, two production-owned aggregate SQL shapes, and a single daemon call-site switch. Selected freshness requires committed green/red/skipped state at the exact identity+revision or a green watermark at the same identity with revision >= selected. Inline review caught and fixed a stale-at-exact-key false-green bug, removed an accidental serialization contract test, and made the EXPLAIN test use the exact production SQL constants.

## IMPACT

Fresh lead verification passes: projection 13/13, store 26/26, daemon 9/9. Query plans use existing status/watermark indexes with no temp sort. The allocation gate measured 720,480 bytes for detailed reads versus 38,624 bytes for aggregate reads (~94.6% lower). No schema, index, CLI, MCP, or detailed API changed.
