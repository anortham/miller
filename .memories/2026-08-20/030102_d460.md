### Defect A - `miller tests serve` hangs any shell that pipes its output

Proven by a discriminating experiment:
- stdout to a FILE: prints `started`, returns in 0s.
- stdout to a PIPE: prints `started`, then hangs. The CLI process exits, but the pipeline stays open.
- The pipeline returns the INSTANT the daemon stops.

So the detached `ct-daemon` holds the launcher's stdout pipe write end and the reader never sees EOF.
`CtDaemonLauncher.WindowsStartInfo` swaps the std handles to the log files, but
`RedirectStandardInput=true` forces `bInheritHandles=TRUE`, so the original pipe handle is inherited
as well. Any script, CI step, or terminal pipeline blocks forever. MCP `tests operation=start` is not
affected: it returns a pid at once.

### Defect B - `tests run --wait` returns before the run finishes

`TestsCore.WaitForVerdict` (src/Miller.Server/Tools/TestsCore.cs:724) returns on Green, Red, or
**Partial**. Partial is the normal in-flight state, so the wait ends almost at once. Observed: it
returned `partial` at t=12s while only the first of three projects had been built; the real verdict
later moved to `unknown`. A budget-paused daemon is also not an exit condition, so `--wait` against a
paused workspace spins for the full 10-minute timeout.

### Defect C - CT reports 366 red tests that pass outside CT

Control on the same tree: plain `dotnet test` gives **0 failed, 7492 passed, 27 skipped, 1m34s**
(1m50s wall with the build).

Under CT: **366 red, 5367 green, 354 stale**, the run wedged, and the stall guard killed it at
10m48s. The 366 reds span 50 test classes. The causes are all environment-shaped:
`Could not locate repo root (Miller.slnx)` (50), string and path comparisons (193+),
`The shared broker test host was not built under ...\miller-ct\...` (11),
`The input string '\Users\alann\AppData\Local\Temp\miller' was not in a correct format` (6).

Root cause: CT runs the built assembly from `%TEMP%\miller-ct\build\<hash>\<hash>\g<gen>\out\`, which
is outside the repo. Every test that walks up for the repo root, or that reads a repo-relative file,
fails there. CT's verdict for this repo is therefore not trustworthy today.
