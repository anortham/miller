### Defect 1 — CT discovery "fails" (SOLVED, proven)
Discovery succeeds; the **database write** fails. Recorded in ct.db all along:
`UNIQUE constraint failed: test_cases.workspace_id, test_cases.selector, test_cases.source`.
`DotnetTestProvider.cs:1588/1591` gives each case an id from the full display name but a selector from the
method name only (`XunitMethodName` cuts at the first `(`), so one theory method yields N ids and ONE
selector. `PutTestCase` (`ContinuousTestStore.cs:219`) handles `ON CONFLICT(id)` only; `CtSchema.cs:50`
declares the second unique index. Second theory row => SQLite error 19, and the whole inventory
transaction rolls back.
**Measured live** on Miller.Tests with `-list full/json -preEnumerateTheories`: 7697 cases, 7695 distinct
ids, 6237 distinct selectors, **407 shared selectors, 1460 colliding rows** (worst method: 42 rows).
**Second, quieter bug:** xUnit truncates long theory display names, so 3 rows of
`ScanFailureJournalTests.TryRead_ADamagedRecord_...` share one display name -> same id -> silent upsert,
2 cases vanish. Survives the constraint fix.

### Defect 2 — no daemon diagnostics (SOLVED)
The daemon is the `ct-daemon` CLI verb (`CliDispatch.cs:156`); the CLI branch starts no Serilog sink, so
`CtDaemonLog` is the only path to `.miller/logs`. `ContinuousTestDaemonQueue.Log` (`:793`) is
`_lifecycleLog?.Invoke` and **both** production constructions omit the argument
(`TestsCore.cs:381`, `:804`), so four existing log lines are dead. `RecordDiscoveryFailure` never logs.
`daemon.out.log` holds only the final "stopped" line the verb prints on exit.

### Defect 3 — my earlier diagnosis was WRONG (corrected)
I had said a 106s suite cannot finish before the revision advances. Refuted twice:
- all 12 run rows have `revision == selected_revision == completed_revision`;
- a full build + the 7576-test suite moved `store_log_sequence` by **zero** (bin/obj do not reach the index).
The 25068->25743 jump spans 14 hours between two runs, not one suite.
**Real cause, three facts:** `IsCommittedFreshAt` requires identity AND revision equality;
`WorkspaceReadSnapshot.IndexIdentity` already *contains* `StoreLogSequence` (visible as `:25068:` /
`:25743:` in live strings), so the identity changes on every index write; and
`AdvanceContinuousTestFreshWatermark` / `IsWatermarkFreshAt` have **zero production callers** — the
carry-forward machinery is built, tested, and unwired.
Measured: saving ONE markdown file moved `store_log_sequence` 25791 -> 25797 (six counts).
**Safety trap:** `TestsCore.SelectedFrom` (`:941-950`) picks the reported key from the stored rows
themselves, so removing the staleness signal without a replacement yields a permanent false green.

### New defect found (pin-related)
`store_meta.extraction_identity_epoch` does not advance when a newer-epoch binary imports into an
existing store. Miller filters four capability views on that pointer
(`FamilyStoreReadSession.cs:479`, `:906-923`), so it would serve the epoch-1 capability snapshot forever.
Evidence came from a hand-edited store — confirm on the first real re-extract.
