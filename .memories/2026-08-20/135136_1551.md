## Fixed the remaining CT dogfood defects (B, D, E, F1, F2, G, H, dashboard)

Continues the CT dogfood repair run. Defects A and C landed earlier in the session; this checkpoint covers everything else the user asked for ("fix all the remaining findings you described first").

### B + F2 — the daemon could not say what it was doing

**Problem.** `tests run --wait` returned in milliseconds. It waited on the VERDICT, and accepting a run marks the selected cases stale, which makes the verdict `Partial` at once — so the wait reported a mid-run answer as the result. Separately `daemon.status.json` froze at reason "executing" for a whole run (12 minutes in one dogfood run); only the heartbeat moved, so nothing could separate a slow suite from a wedged one.

**Fix.** New `CtRunActivityCell` (`src/Miller.Testing/Daemon/CtRunActivityCell.cs`) is the one place the daemon's activity lives. It separates DRAINING (the loop is busy; one drain runs every ready project) from RUNNING (a child is in flight) — collapsing the two would let a wait return in the gap between two projects of one drain. It also derives `CtRunActivity` (starting/active/quiet/stalled) from the child's last output, monotonically, so a clock jump cannot read as silence.

Wiring: `ContinuousTestProviderFactory.CreateDefault` builds the cell (it already resolves the stall bound) and hands `TestProcessRunnerOptions.OnOutput` to it; the queue calls `BeginRun`/`EndRun` around `RunSelectedAsync`; the daemon loop calls `BeginDrain`/`EndDrain`/`EnterQueued`/`EnterIdle`; `TestsCore.ServeHost` threads one cell through all three. `PulseHeartbeatAsync` now republishes the status too — the main loop is BLOCKED for the whole drain, so the pulse is the only thing that can keep the file moving.

`WaitForVerdict` was replaced by `WaitForDaemonToSettle`: it never tests the verdict, only daemon activity, with four bounded exits (idle, stopped, dead lease, timeout) plus a 30s cap on queued-behind-another-workspace so a budget-blocked run reports "still queued" instead of burning the full 10 minutes.

### D — every project built twice per run

Discovery and the run that follows it build the same source, but each called `CtGenerationPaths.Allocate`, and the generation directory IS the build's `OutDir` — so the second build found an empty output directory and repeated the copy. New `CtGenerationHandoff` (one instance per provider, keyed by build root) hands the discovery's generation to the next run, one-shot so two runs can never share one. Applied to the dotnet and rust providers (the only two that build during discovery).

### E — 6,233 cases discovered vs 7,723 run

Measured on Miller's own suite, not assumed. `-list full/json` reports one entry per test METHOD: 6,233 entries, none carrying arguments. With `-preEnumerateTheories`: 7,693 entries, 1,869 with arguments. At run time a delay-enumerated theory emits ONE `test-case-starting` whose display name has no arguments, with one `TestCaseUniqueID` shared by every row — so rows folded into one verdict.

Fix: pass `-preEnumerateTheories` to BOTH commands. Setting it on only one is worse than neither (discovery would record row ids no run could ever prove). Cost measured: ~100ms on a 400ms discovery. The argv does not grow — `XunitSelectionUnits` already collapses a method's rows to one `-method`.

### F1 — a stall-killed run looked like it was still running

`CompleteContinuousTestRun` now stamps `EndedAt` when the provider gives none, and a non-zero exit forces `Status = "failed"` so a killed assembly whose executed tests passed is not recorded green.

### G + H — `tests failures` was a dead end

Was 5 rows, hard ceiling 20, no paging, MCP-only. Now: default 20, ceiling 200 as a PAGE size, `offset` reaches the rest, `total`/`offset` in JSON, compact names the next offset, and `miller tests failures` is a CLI verb.

**Correction to the earlier finding:** the "unknown tests operation exits 0" half of H is NOT real. Measured: exit 2. The earlier reading was an artifact of piping the command through `tail`, which returns its own exit code.

### Dashboard launcher — same handle-inheritance class as defect A

`DashboardCliLauncher.DirectStartInfo` (Windows) spawned with no redirection, so the dashboard inherited the caller's stdout and `miller dashboard | anything` hung forever. Extracted the proven CT spawn into `Miller.Indexing/DetachedProcessStreams.cs` (shared by both launchers) and routed the dashboard through it. **Behaviour change to tell the user about:** on Windows the dashboard's output now goes to `~/.miller/dashboard.out.log` / `.err.log` instead of the caller's console — the same files Unix already used.
