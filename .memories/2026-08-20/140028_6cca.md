## CT dogfood repair: all eight remaining findings fixed and verified

### WHAT

Closed the last eight findings from the CT dogfood run. No commit yet.

**B + F2 — the daemon could not say what it was doing.**
New `CtRunActivityCell` (`src/Miller.Testing/Daemon/CtRunActivityCell.cs`) holds the daemon's live
activity. `CtDaemonProtocol` gained `CtDaemonActivity` (idle/queued/executing), `CtRunActivity`
(starting/active/quiet/stalled), and `CtDaemonRunProgress`, all as trailing optionals.
The heartbeat pulse now republishes the status record, so `daemon.status.json` no longer freezes at
"executing" for the whole run. `TestsCore.WaitForVerdict` was replaced by `WaitForDaemonToSettle`,
which waits on daemon ACTIVITY instead of a verdict value.

**D — every test project built twice per run.**
New `CtGenerationHandoff` (`src/Miller.Testing/Providers/Shared/CtGenerationHandoff.cs`) hands the
build generation from discovery to the run that follows. One instance per provider, one-shot.
Used by `DotnetTestProvider` and `RustTestProvider`.

**E — CT discovered 6105 cases while `dotnet test` ran 7519.**
The gap was theory rows. Added `-preEnumerateTheories` to BOTH the discovery argv and the run argv
in `DotnetTestProvider`.

**F1 — `test_runs.ended_at` stayed NULL after a stall kill.**
`ContinuousTestStore.Runs.cs` now stamps `EndedAt` when the completion carries none.

**G — `tests failures` was capped at 5 rows with no paging.**
`TestsCore.Failures` now takes `maxItems` (default 20, clamped 1-200) and `offset`.
`TestsFailuresResult` gained `Total` and `Offset`. Compact output names the next offset.

**H — `tests failures` was MCP-only.**
Added a `failures` case to `CliDispatch` with `--limit` / `--offset`, and the same two parameters
to the `tests` MCP tool.

**Dashboard — same handle-inheritance defect as A.**
Extracted the proven Windows spawn from `CtDaemonLauncher` into
`src/Miller.Indexing/DetachedProcessStreams.cs` and routed `DashboardCliLauncher` through it.

### WHY

Each item came from a real dogfood run, not a review. `--wait` returned in milliseconds because
accepting a run marks cases stale, which makes the verdict `partial` at once — so the wait read a
mid-run answer as the result. A verdict describes the store; it is not a completion signal.

### HOW — two decisions worth keeping

- **Draining and running are separate states.** One drain executes every ready project in turn, so a
  child ending is NOT the daemon going idle. Collapsing them would let a waiting caller return in the
  gap between two projects of the same drain.
- **`-preEnumerateTheories` on one command only is worse than on neither.** Discovery would record
  row ids no run could ever prove, leaving every row unproven forever.

### CORRECTION

I earlier reported that an unknown `tests` operation "exits 0". Measured properly it exits **2**.
The first reading came from piping through `tail`, so `$?` was `tail`'s exit code. That half of
finding H is not real and needed no fix.

### BEHAVIOUR CHANGE TO REPORT

On Windows the dashboard's stdout/stderr now go to `~/.miller/dashboard.out.log` and
`dashboard.err.log` instead of the caller's console. Unix already used those files.
