### Two plan errors found and corrected by measurement, not argument

**T4 cascade blast radius.** The plan named THREE tables referencing `test_cases(id)`. There are
**SIX**, all `ON DELETE CASCADE`: test_results, test_links, test_quality_findings, ct_test_states,
ct_case_fresh_watermarks, ct_coverage_maps. `CtSchema.Apply` runs `PRAGMA foreign_keys=ON` first, and
the pragma is a no-op inside a transaction. Negative control on a copy of the real 31 MB ct.db: the
same rebuild with keys ON destroyed 5,754 + 6,108 rows. The shipped migration reads the pragma BACK
to prove it took, re-counts rows, and rolls back on mismatch. Live result: all seven tables
unchanged, user_version 0 -> 2, foreign_key_check clean, 112 ms.

**T4 sub-task 4c is WRONG as specified and was refused.** Lead verified independently:
`DotnetTestProvider.cs:1734` mints the RUN's case id from the display name, so an ordinal added to
the INVENTORY id matches nothing the run emits; those cases never resolve; and
`ContinuousTestStatusSummary.ResolveVerdict:145` returns Unknown whenever `counts.Unknown > 0`, so
two unresolvable cases would pin the WHOLE workspace verdict at Unknown forever. 4a unblocks 1,464
rows; the 4c defect is 2 rows. Follow-up recorded instead: a worst-wins result merge, which the lead
verified cannot pin a flaky test red because `ScheduleFlakyRetries` re-enqueues into a NEW run.

**T3 found a second undocumented defect.** On the real xUnit artifact path `SelectorWithoutArguments`
yields `<classPath>::<class>.<method>`, which never matched the map's `<classPath>::<method>` key, so
those rows resolved to nothing and minted a duplicate case each.

### Task 6 — added after approval at the user's direction

The user pushed back on my claim that Miller could not handle the worktree, and was right. A healthy
linked worktree already exists in the registry (julie-extractors, revision 7434), and mine indexed
fine after `workspace remove` + `workspace open`.

The real defect: a workspace whose view is PLANNED but never PUBLISHED cannot recover itself.
An adversarial design workflow (3 designers -> judge -> 3 skeptics) corrected my chain in FIVE places:
- There are TWO throws in `ReconcileCatalog`; only `:241-242` is the wedge. `:235-236` (view known
  under a DIFFERENT root) must stay loud.
- It is not one chain but TWO INDEPENDENT wedges. Bootstrap has no leadership gate at all.
- I had the consequence backwards: `Evaluate` never runs, and callers convert the exception to
  **ineligible**. `Eligible: true` is the hazard a naive fix would CREATE.
- Bootstrap CANNOT pass `recoverUnpublishedView` — it calls an overload lacking the parameter.
- `MILLER_ALLOW_EXTRACTOR_DOWNGRADE=1` ALREADY violates the invariant it was supposed to protect.

Key enabler: `store_meta.binary_version` is family-wide and `Probe` reads it at family scope; only
`ReadManifestIdentity` needs the view. So a family-scope read returns the byte-identical string.
The policy already exists at `StoreWorkspaceCoordinator.ReadState:1050-1056` — two call sites forgot
it. Design saved at `.razorback/sdd/.../task-6-design.md`.

**Behaviour change to note in release notes:** change 4 adds a version gate bootstrap never had, so an
older Miller on a newer family store will fail bootstrap where it used to import.
