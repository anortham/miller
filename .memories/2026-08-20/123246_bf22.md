## CT defect triage — evidence pinned before any fix

Investigating 3 reported CT defects (A: `tests serve` hangs a piped shell; B: `run --wait` returns early; C: 366 false reds) plus smaller ones. Goal: pin each root cause with a discriminating experiment before writing code.

### Confirmed by direct evidence

- **Defect C is a one-sided env-var break.** `DotnetTestProvider.WorkspaceEnvironment` (src/Miller.Testing/Providers/Dotnet/DotnetTestProvider.cs:480) DOES set `MILLER_CT_WORKSPACE_ROOT`. The consumer `ScaleTestSupport.RepoRoot()` (tests/Miller.Tests/ScaleTestSupport.cs:42) still reads the RETIRED `EROS_WORKSPACE_ROOT`. docs/plans/2026-08-18-ct-sidecar-migration.md:21 required that rename; the producer side landed, the test helper was missed.
- **CT also overrides `TMP`/`TEMP`/`TMPDIR`** to the CT generation temp dir (DotnetTestProvider.cs:481-483). A large environmental difference, not yet tied to specific failures.
- **Defect F1 confirmed from data.** `.miller/ct.db` `test_runs` row `ct-run:a37c9ec6...` has `status='failed'` and `ended_at=NULL`. The two completed runs have `ended_at` set. All three rows share one `started_at`, and `command` is NULL on every row.
- **`.miller/` is excluded from BOTH the file watcher** (`WatchPathFilter.SkipSegments`, src/Miller.Server/Hosting/WatchPathFilter.cs:46) **and julie-extract indexing** (`ScanIgnorePolicy.InvariantPatterns`). So a CT build root under `.miller/` would cause no watcher or index churn. Note `ContinuousTestDaemonQueue.ValidateBuildOutputRoot` (:784) currently FORBIDS an in-workspace build root.

### New defects found

- **G — `tests failures` is unusable.** It returns at most 5 rows with `truncated: 361` and has no `limit`/paging parameter, in compact AND json. The failure list cannot be read through the product surface.
- **H — `tests failures` is MCP-only.** docs/contracts/tests-cli-v1.md lists only status/serve/run/enable/disable/stop. `miller tests failures` prints a usage line and **exits 0**, so a script cannot detect the error.
- **I — `failure_summary` in ct.db stores only the exception header**, no expected/actual. 80 rows read `Assert.Equal() Failure: Values differ` with nothing else.

### Method correction (important)

My first out-of-repo experiment looked like "location breaks 8 tests". It was an incomplete comparison — I had no in-repo baseline for the same filter. With matched filters via `dotnet test` (CT's real runner; CT does NOT run the exe directly):

- in-repo: 5 failed / 20
- out-of-repo: 8 failed / 20

Only **3** are the location effect, and all 3 are `RepoRoot()` consumers. The other 5 (`VectorSidecarOpenTests`) fail in-repo too when run in isolation — they are order-dependent and pass in a full run. Do not attribute them to CT.

### Red taxonomy from ct.db (366 reds, 50 classes, 30 message buckets)

Top: 80 `Assert.Equal Values differ`, 59 `Strings differ`, 54 `Contains not found`, 50 `Could not locate repo root (Miller.slnx)`, 24 `no .miller/store.json pointer`, 21 `KeyNotFoundException`, 11 shared-broker-host, 6 `FormatException: '\Users\...\Temp\miller'` (a path that lost its drive letter — possible real parser bug).

### Impact

Defect C is NOT "CT runs tests out of the repo, therefore CT is wrong". Only ~50 of 366 are explained by the repo-root walk so far. The rest need the full-assembly location diff, which is running now.
