## CT check-in verdict + one design decision to relay

An independent check-in session assessed the CT hardening arc (port → merge → dogfood → fix → audit → fix) at the user's request.

### WHAT — verdict
The approach is fundamentally sound; the sessions are NOT spinning wheels. Evidence: Windows baseline went 7,348/2-failed → 7,371/0-failed (+21 tests); Scale 148/0; every fix started from a measurement (659KB argv measured, File.Replace+FileShare.Delete matrix proven, bare npm vs npm.cmd proven); the audit's own wrong fix was refuted empirically. Defect classes are the canonical Windows CT-engine list NCrunch also solved (file locks, argv cap, .cmd shims, process trees) and the fixes use the same primitives (Job Objects, ReplaceFile, generation-dir builds).

### WHY — the one brute-force spot
`ContinuousTestImpactSelector.Select` (src/Miller.Testing/Selection/ContinuousTestImpactSelector.cs:97-107) returns EVERY known test-case id for WorkspaceScope. The .NET provider emits one `-method` pair per id; chunking splits ~6,000 methods into ~50 processes, each paying startup+discovery. Finding 8 measured per-method selection at 25s vs 6+ min for the same subset.

### HOW — the fix already half-exists
`DotnetTestProvider.BuildRunCommands` (src/Miller.Testing/Providers/Dotnet/DotnetTestProvider.cs:342-343) already runs the whole assembly with only trait exclusions when the selection is empty. Invert: workspace scope → empty selection; method lists only for small deltas. Constraints: (1) verdict rows must still record the full run as covering all known cases so composite-key freshness stays honest; (2) apply the same inversion to cargo/pytest full-suite paths.

### IMPACT
Removes the chunked slow path from every full run. Full note: docs/findings/2026-08-19-ct-checkin-workspace-scope-selection.md (indexed in docs/README.md). Also re-flagged for ranking: run stall timeout (finding 7) and the >120s foreground MCP `tests run` block; and a caution that ~6,245 uncommitted lines sit on main — commit in verified slices.
