## v1.3.2 published + real root cause of the tag-push publish 403

Follow-up to the earlier v1.3.2 incident checkpoint: the tag push triggered the release build, all 4 platform builds succeeded, but the **publish job 403'd** (`Resource not accessible by integration` on POST /releases) despite `contents: write`.

- **Real root cause:** GitHub's 2023 "workflow scope when creating a release" enforcement — creating a release whose target commit differs from default-branch HEAD by `.github/workflows` changes requires `workflows: write`, which GITHUB_TOKEN can never hold. We pushed 13 commits (including `162309a ci: remove HOL plugin scanner`, a workflow change) to main **while the tag build was running**, so by publish time `--target 07232c0` was a non-tip SHA with workflow diffs → 403. Not a GitHub regression; June tag pushes and the v1.3.1 promote all targeted the branch tip.
- **Recovery (v1.3.2 is LIVE):** promote dispatch was blocked by the script's run-conclusion guard (source run marked failure), so published locally: `gh run download 28592841424` + `release-promote.sh --artifacts-dir --target 07232c0 --prerelease false` under the user token. Verified: non-prerelease, Latest, 8 assets, launcher sidecar URL returns 200.
- **Durable fix:** `release-promote.sh` now omits `--target` when the tag already exists (redundant for existing tags; it's what provokes the scope check). CLAUDE.md release section documents the trap (don't push workflow-touching commits to main mid-release-build) and the local recovery path.
- **Open options (not done):** relax the promote guard to allow promoting from runs whose build jobs succeeded but publish failed; or add a fine-grained PAT (`contents`+`workflows` write) as RELEASE_TOKEN for the publish job.
