## Resolved both 2026-06-11 Eros TODO entries: "julie-extract hang" + exit-code contract

### Triage: the openclaw "hang" was NOT a hang
- Isolated `julie-extract scan --force` (pinned 2.4.0) on `/Users/murphy/source/openclaw` completes in **~90s** (status ok, 13,308 files, 660,851 symbols, ~2.0GB artifact). No per-file hang, no minimized repro needed.
- The real artifact showed a successful rebuild took **12.7 min under fleet load** (created 22:15:06Z → registry scan-stamp 22:27:49Z) — exceeding `JulieExtractRunner`'s fixed 600s TOTAL timeout, which killed a healthy, still-progressing scan.

### Fix: progress-aware bounded wait
- New pure `ExtractWaitPolicy` (src/Miller.Indexing/ExtractWaitPolicy.cs): kill only after the stall window (`DefaultTimeout`, 10 min) with NO progress; absolute backstop = 6× stall (60 min). Progress stamp = artifact db/-wal/-shm bytes + stdout/stderr line activity (any change counts, incl. WAL shrink on checkpoint).
- `JulieExtractRunner.Run` polls `WaitForExit` in ≤1s slices; kill messages now distinguish "no progress (likely hang)" from "progressing but over the hard cap (load)".
- Fast-suite `ExtractWaitPolicyTests` (9 tests); Scale `JulieExtractRunnerTimeoutTests` still passes (1ms stall → 6ms hard cap trips first poll deterministically).

### Contract: lock_busy now exits 0
- `CliDispatch.RefreshExitCode`: LockBusy moved to exit 0 (index served, live leader owns convergence; payload `status`/`index_fresh:false` is the freshness gate). Exit 3 reserved for `missing_root`/`missing_index`/`failed`/`ineligible_extractor`.
- docs/contracts/cli-eros-v1.md updated (exit-code table + lock_busy paragraph in the refresh section).
- Live-verified: `miller workspace refresh --workspace ~/source/miller --json` → `status: lock_busy`, EXIT 0.

### Question (2) from the field report
- `workspace full --json` ALREADY exits 3 on `status: failed` at HEAD — verified empirically on 0.4.1+86c7529 by injecting a sensitive-root registry row (Refresh rejects → Failed → exit 3). Eros's "exits 0" did not reproduce; likely a pre-0.4.1 binary.
