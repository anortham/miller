## Closed the silent-startup gap after a Windows plugin launch left zero log lines

A user's Miller MCP launch failed to connect in Claude Code on Windows (`C:\source\Lab Handbook`). A `/mcp`
reconnect worked. `<workspace>/.miller/logs/miller-20260825.log` held **no line at all** for the failed
attempt — a 40.5-second gap between miller 1.20.1 (pid 26756, client 2.1.238) shutting down and miller
1.22.0 (pid 32068, client 2.1.245) starting.

### WHY the log was empty (the real defect)

A plugin launch is TWO processes and neither could report a pre-server failure:

- `bin/miller-plugin-launcher.cjs` wrote **no log file anywhere**; its only output was
  `console.error(error.message)` on a throw.
- `miller.exe` assigned `Log.Logger` partway down `Program.cs`, with **no top-level catch** anywhere in the
  file and no `Log.CloseAndFlush()`. Everything above that line ran with the silent default logger.

So a failed launcher, a killed launcher, and a `miller.exe` that died early all produced identical evidence:
nothing. The silence was a design gap, not a symptom of the specific cause.

### The slow phase

The launcher caches per version, so a version bump is a **cold ~100MB download** (v1.22.0 Windows zip =
103,211,562 bytes, expanding to 324,744,223 bytes in 62 files). All of it runs **before** `miller.exe`
starts, inside Claude Code's `MCP_TIMEOUT` budget (ms, default 30000 — confirmed from docs and a live
`"Starting connection with timeout of 30000ms"` log line). Claude Code never auto-reconnects stdio servers.

Best fit: attempt 1 finished the download (which `ensureDownloadedArchive` caches), was killed during
hash/extract, and never spawned `miller.exe`; the retry reused the cached archive.

### Two triage claims that did NOT survive adversarial review

- The 4 ms between `transport reading messages` and `Application started` does **not** prove a warm cache —
  both lines come from inside `miller.exe`, after the launcher spawned it.
- A retry does **not** always re-download; a completed archive is cached under `downloads/` and reused.

### HOW it was fixed

- **Launcher:** writes `~/.miller/logs/launcher-<YYYYMMDD>.log` (honors `MILLER_HOME`) plus the same lines to
  stderr, naming every stage with MB/s progress; a cache miss names `MCP_TIMEOUT`; 14-day retention.
- **Launcher can no longer hang:** connect timeout on `https.get`, idle-body watchdog, `stream/promises`
  pipeline (a mid-body reset used to leave the promise unsettled forever), rename retry for
  `EPERM`/`EBUSY`/`EACCES`, actionable missing-`tar.exe` message, top-level `process.exit(1)`.
- **`Program.cs`:** tracks `startupStage`, wraps the whole startup in one catch calling new
  `StartupFailureLog` (exit 70) — always stderr, then a `role:startup` append to the first writable candidate
  (resolved logs dir → `<home>/.miller/logs` → temp), never throws, never recreates a candidate whose parent
  is gone.
- **`Serilog.Debugging.SelfLog`** enabled to stderr: the file sink opens lazily, so a locked file used to
  yield a healthy Miller writing zero bytes.
- **New `StartupBreadcrumb`** names the log directory on stderr unconditionally — an empty workspace log is
  now decisive.
- **Pre-logger throw guards:** `WorkspaceRootSafety.Normalize` skips a malformed forbidden entry (six come
  from Windows env vars); `MillerHome.Resolve` refuses an unrooted profile by name.
- Docs: `docs/install.md` "When the plugin fails to connect" + `docs/findings/2026-08-25-silent-plugin-startup-failure.md`;
  CLAUDE.md/AGENTS.md gained the "A launch may never fail silently" invariant.

### IMPACT

Every plugin upgrade is a guaranteed ~100MB stall inside a 30s connect budget. That is now self-describing in
three places instead of invisible. Tree is dirty and uncommitted — no commit, no release (both need approval).
