## Release 1.22.1 prepped: CT honesty fixes on top of the launcher/startup logging work

Follow-on to checkpoint_ac47ec34 (silent-startup gap). This adds the continuous-testing half and the
version bump, all verified and ready to publish.

### WHAT — CT told users nothing useful, then let them make it worse

**`tests status` on a CT-off workspace reported `projects: 0`.** Same tree, same file: 0 with CT off,
1 with CT on. The zero counted what CT had *recorded*, not what the tree holds, so it read as "no test
projects here" on a repo full of them. A field agent asking "are the tests passing?" correctly concluded
Miller had nothing and ran the suite by hand.

Status now runs the same `ContinuousTestProjectInventory` scan the daemon would, writes nothing (~85 ms
on 3,502 files; no `ct.db`, no `.miller/ct/`, no daemon), and emits `projects_discovered` in JSON plus a
compact `next:` line that names the **direct run first** — a one-off question wants a test run, not a
background daemon.

**`tests enable` on an unsupported repo silently "succeeded".** Go/Ruby/Java/PHP: `enable 0 project(s)`,
exit 0, opt-in marker written. Workspace left permanently `enabled: true` / `projects: 0` — unmovable,
and the new status guidance is suppressed by the very marker the failed enable wrote. Now exits 3 and
writes nothing, naming the supported set.

**`tests enable --project go.mod` actually worked.** `Identify` fell through to `FrameworkFallback`, got
null, and built a project with a NULL framework rendered as `(unknown)`. Now returns null. The
deliberate `.csproj`-with-no-test-package → `dotnet` fallback survives.

### WHY the rule ended up as "never decided"

Three review failures forced the design:
- An existing test caught me re-listing projects after an explicit `tests disable` — arguing with a
  decision already made.
- `Enable_OnWorktree_RemovesTombstoneAndWritesLocalMarker` caught the refusal stranding a linked worktree
  that has no projects of its own. Reversing a tombstone is a prior relationship, so it is always allowed.
- The byte-stability guard caught the enabled-but-empty hint firing over a live daemon run. It is now
  silent while a run is in flight.

Status discovery and enable refusal now turn on ONE helper, `HasContinuousTestHistory`.

### Bug found in the test infrastructure

The CT launcher Scale guard globbed `Miller.*.dll`, but Miller.Server's assembly is **`miller.dll`**.
Case-sensitive Linux never matched it, so it measured only referenced projects: it failed a
Miller.Server-only change as stale, and would have PASSED a stale `miller.dll` beside a fresh
`Miller.Core.dll`. Now case-insensitive.

### Guidance channels

The `tests` line in both the embedded instructions and the session-start routing block was three safety
disclaimers and no value proposition — the only tool line describing constraints instead of use. Both now
read "which tests your change made stale, and their last verdict". Core had 6 chars of headroom; it fits.
The routing-block canary anchor was re-derived.
