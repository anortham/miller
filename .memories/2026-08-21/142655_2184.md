## CT daemon control plane: three reported defects fixed, plus five found by review

Closes the three items left open at the end of the CT watermark work, and the
review findings they exposed. Fast suite 7775/0/27 (+28 new tests over the 7747
baseline); scale suite 153/0/12.

### The three reported defects

- **A. A lost adopted-status write was permanent.** `TryWriteAdoptedStatus` set
  `PublishedState`/`PublishedReason` BEFORE the write, so one failure armed the
  dedupe guard forever, and the attach loop skips a root already in `_adopted`.
  The worktree kept a DEAD predecessor daemon's record, and the new liveness
  probe then read a LIVE family daemon as `daemon gone`. Fix: mark published only
  after the write returns; a failed ATTACH record is retried on later scan passes,
  bounded by `MaxAdoptedStatusAttempts = 12`.
- **C. A detach record recreated the tree it was detaching from.** Every write went
  through one unconditional `Directory.CreateDirectory`. New
  `CtDaemonWriteMode.ReplaceExistingOnly` never creates the file or its directory;
  detach/stop records, `CtCommandChannel.Stop`'s two writes, and
  `CtDaemonLease.Dispose` take it. `CtDaemonLog.Write` had the same shape and now
  refuses to recreate a root that is gone.
- **B. The lease recorded `miller_version` and nothing read it.** New
  `CtDaemonVersion` is the one verdict. `tests status` reports four
  `daemon.version_*` keys plus a top-level `miller_version`; an explicit
  `tests start` from a different build stops the old daemon and reports
  `status: "replaced"`.

### Two rules carry the version design

- SAMENESS is the whole build string, so an agent swarm on one build never warns
  and never contends — the CT half of "equal versions never thrash".
- DIRECTION is numeric `major.minor.patch`, because version strings are not
  orderable as text: `1.9.0` sorts ABOVE `1.13.0`, and a text comparison would
  call a newer daemon older and authorize a kill.

### What the adversarial review caught in my own change

Nine confirmed findings; three lenses independently found the same high one.

1. **HIGH — the daemon could ping-pong.** `build_differs` is symmetric, and the
   new status hint fired on any `MayReplace`, so two worktrees of this repo on
   different commits would each read "replace the older daemon" about the other
   and follow it, killing every suite in flight. The hint is now gated on
   `Match: DaemonOlder`, the only verdict that proves a direction. The verdict
   itself is unchanged, so the mismatch stays visible and an explicit start still
   breaks the tie.
2. **The retry could reintroduce defect C.** An owed record is always an ATTACH
   record, which writes in CREATE mode. Running the retry before the detach pass
   let it re-mint the control plane of a worktree that had just been removed.
   Moved to AFTER the detach pass: everything still in `_adopted` there passed
   both detach triggers on the same pass.
3. **A failed DETACH write was un-retryable by construction** (the context leaves
   `_adopted` before the write), so it left an `adopted by ...` record naming a
   still-ALIVE daemon — which the liveness probe cannot contradict. Now the stale
   record is DELETED instead; an absent record reads as stopped, which is what a
   detached worktree is.
4. Status paid ~10ms per absent control-plane file to `ExistsThroughPublishWindow`.
   A publish never removes the directory, so an absent directory short-circuits.
5. Test-coverage gaps: the mismatch half of the renderers, `replaced` mapping to
   exit 0, and a kill-switch test that proved zero-CREATION but not zero-WORK
   (it now seeds a LIVE lease, so a version read above the short-circuit fails it).

### Method note worth keeping

Every fix was proven by REVERTING it and watching exactly the intended tests go
red. That caught a real problem: the `AdoptedStatusWriter` test seam did not carry
the write MODE, so a test delegating to the real writer created a control plane on
a detach record — the opposite of production. The seam now carries the mode.

### Rejected

- Setting `BuildDiffers -> MayReplace: false`. It is the rebuild-from-source case
  this repo actually needs. Removing the automatic NUDGE stops the loop; removing
  the explicit capability would break the workflow.
- An `_owedDetach` retry dictionary for finding 3. It introduces a re-attach
  clobber hazard (a stale Stopped write landing on a fresh Running record). The
  delete is smaller and its result is the honest reading.
