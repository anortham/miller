## Context latency diagnosed: the whole-index defect pattern, live — full detail in docs/findings/2026-08-21-context-latency-diagnosis.md

### WHAT

A read-only Opus agent diagnosed the `context` tool's ~6.1s of own-work latency (separate from the resolve-side causes the running workflow is fixing). The complete evidence, fix plan, and open questions are written to `docs/findings/2026-08-21-context-latency-diagnosis.md` (linked from docs/README.md) so no detail is lost to compaction — READ THAT FILE, this checkpoint is only the pointer.

### Headline findings

1. **Dominant cost: `TestLinkageReader.Read` scans every test symbol in the index** (7,128 rows, JSON-parsed per call) looking for `test_linkage`/`test_coverage` metadata that NO store family on this machine contains (probed all five, including julie-extractors: zero rows). Its `ORDER BY symbol_id` forces a scan of the whole 608k-row family table: 2,537ms with the sort, 178ms without. Dead code paying ~4.4s to return zero edges. The supplemental-edge cache key folds in counters any file edit moves (43% miss rate during development); the CLI (`CliDispatch.cs:3801`) never caches it at all — flat 13.6s per CLI context call.
2. N+1 term-rescue reads (`PromoteTermRescueTestSubjects`) pull the whole-generation fact load even under reference_mode=off (worst observed: 137s in one anchor_resolution phase); the batched ReadMany exists and is unused there.
3. LoadSemanticSeeds runs a full retrieval, then discards it at a routing check that should run first; the pivot ranker re-retrieves and misses the cache (limit differs).
4. 48 existence probes per call against a per-instance cache that always starts empty.
5. Token budget applied only after all work (budget 100 costs the same as 2000).
6. The reference_mode=usage branch has NO phase instrumentation and owns the worst numbers (113s, 519s cross-workspace).

### Decisions

- User approved fixing ALL of it. Fix order in the findings doc: existence-probe gate on the linkage scan (keeps the feature for when julie-extract emits linkage — language-parity rule applies to that emission), drop the ORDER BY, fix the cache key, batch the N+1, reorder the routing check, share the retrieval, batch probes, instrument the usage branch. DEFERRED: skipping promotion under reference_mode=off (ranking change; re-measure after the batching fix).
- The context-fix workflow must WAIT for wf_53acc9b2-04d (inspect-latency + daemon lanes, still running) — both touch WorkspaceIndexProvider and the CLI seam.
- Design rule saved to persistent memory (`prefer-query-time-over-precompute`): user affirmed twice — load what the query needs; a cache on top of an unbounded read is the defect, not the fix. Follow-up: retire the server's whole-generation RevisionFactCache load behind the CLI's bounded reader once it proves byte-identical.

### IMPACT

Context's fix plan is fully specified and user-approved; expected effect is removing ~4.4s from 43% of server calls and ~13s from every CLI call, before the resolve-side fixes stack on top. Open question 2 (where do the reported 24 supplemental edges actually come from — the probe found no source for them) must be settled by the fix lane BEFORE changing the edge readers.
