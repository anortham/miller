## Live verification of CT daemon build awareness (all 5 verdicts)

Exercised the `CtDaemonVersion` takeover path against **real leased daemon processes** on `C:\source\miller`, after the Release rebuild of commit `211eee34` landed. Unit tests already covered the logic; this was the live proof that the wiring, the lease record, the real process stop, and the hint gate all behave as designed.

### HOW — two binaries, same commit, different release numbers

The version string is `$(Version)+<git short sha>`, stamped by the `_MillerStampInformationalVersion` target in `Directory.Build.props`. To get differing build strings from one commit:

- `dotnet build -c Debug -p:Version=X` gives a different release number. **Works.**
- `-p:InformationalVersion=...` does **NOT** work — the target assigns the property at execution time, and a PropertyGroup inside a Target overrides an MSBuild global property.
- For the same-release/different-build case, `GIT_DIR=/nonexistent dotnet build -c Debug -p:Version=1.20.1` makes the `git rev-parse` Exec fail, the guard falls back to the bare `$(Version)`, and the binary reports `1.20.1` with no `+sha`. This is the documented no-repo fallback path.

Also pass `-nr:false`: a reused MSBuild node keeps its old environment, so `GIT_DIR` may not reach the Exec otherwise.

### Results — every verdict confirmed live

| Case | Daemon | Asking build | `version_match` | Start result |
|---|---|---|---|---|
| No daemon | — | 1.20.1+sha | `none` | — |
| Same | 1.20.1+sha | 1.20.1+sha | `same` | `alreadyrunning` |
| Daemon older | 1.20.1+sha | 1.20.2+sha | `daemon_older` | **`replaced`** |
| Daemon newer | 1.20.2+sha | 1.20.1+sha | `daemon_newer` | `alreadyrunning`, reason names both builds |
| Build differs | 1.20.1+sha | 1.20.1 (bare) | `build_differs` | **`replaced`** (explicit start breaks the tie) |

The replace is a **real** stop: replaced pids 46232 and 45196 were confirmed gone; the survivor's `daemon.lease.json` recorded the new `miller_version`.

### The two findings that mattered

1. **Numeric ordering beats the text-sort trap, proven live.** Ran a daemon stamped `1.9.0` against a `1.20.1` reader. A text comparison sorts `1.9.0` ABOVE `1.20.1` and would have reported `daemon_newer` and refused. Live output: `the daemon runs an older build (1.9.0+...)`, plus the replace hint. The numeric `major.minor.patch` compare is doing its job.

2. **The ping-pong gate holds, proven symmetrically.** With a `build_differs` pair, probed from BOTH sides. Each side reported `build_differs` and **neither printed a hint**. Had the hint stayed on `MayReplace` (the bug caught reviewing my own change), both operators would have been told to replace the other, and the takeover would kill every suite in flight. Gate is `Match: DaemonOlder` at `src/Miller.Server/Tools/TestsTool.cs:210`.

### Discoveries worth keeping

- The `next:` hint is an **MCP-only** channel (`NextStepHint`, compact output). The CLI's `miller tests status` shows the `daemon_build:` line but no hint. That is by design, not a gap. Driving the hint live means calling the MCP `tests` tool, whose server build is the comparison baseline.
- `"status":"alreadyrunning"` has no separator while `version_match` uses snake_case (`daemon_older`). **Not a defect** — `docs/contracts/tests-cli-v1.md:273` documents the `alreadyrunning` spelling explicitly. Left alone; changing it would break the published contract.
- **Start is status-only, confirmed.** Across the whole exercise `last_run` never moved from `2026-08-21T09:26:28` and `stale_count` stayed 7835. Starting a daemon with 7835 stale cases executed nothing. No test run was consumed.

### IMPACT

The build-awareness feature is now verified end to end, not just unit-tested. Working tree clean, no stray daemon processes, CT daemon back to `stopped`, Debug binary restored to `1.20.1+211eee34d2d5`. Nothing about the repo changed — this was pure verification.
