### Findings (verified with file:line evidence in the agent reports)

**Hung-daemon detection.** No signal on disk today is an honest heartbeat of the daemon MAIN LOOP. Both periodic writers (`daemon.heartbeat.json` 15s, status-record republish) run on the pulse task, which survives a wedged loop by design. Recommended design (option 2): add a trailing `loop_tick_at_utc` to `CtDaemonStatusRecord`, stamped only by the main-loop `TryWriteStatus` path, copied verbatim by the pulse; the reader compares two same-clock timestamps in one file (no reader clock, no age inference — satisfies the ScanGovernor rule). Gate on `activity`: never judge loop lag while `executing` (child governed by run.activity + 10-min stall guard); add `executing` + `run.activity=stalled` past the bound = hung supervision. Report only; `tests stop` already escalates to a process-tree kill. Two incidental defects: `daemon.lease.json` `heartbeat_utc` is written once and never renewed (dead field, verified live), and `CtDaemonLease.TryReadHeartbeat` has no production caller (heartbeat file written 5,760x/day, read by nobody).

**Telemetry.** 110 of 130 errors (85%) are ONE fixed bug — sidecar missing/stale after view replans, all on 1.19.x, zero on 1.20.x; they inflate the status line until retention ages them out (~2026-09-16). Real findings: `inspect` is the slow tool on the current build (p50 1,307ms, p95 8,953ms, n=118) — search is healthy (p50 191ms); the status line `top=` reports the BUSIEST tool, not the slowest, which misled us; the summary is a lifetime aggregate with no rolling window, so one bad day (08-17 store-resolve churn, now retired) sets the number for a month. Leads: `context` p50 6.1s / `impact` p50 3.3s (small n), one untyped edit failure, cross-workspace search up to 289s.

**Retired store views LEAK, confirmed.** Nothing in either repo deletes a view row, GC treats every view's current manifest as a permanent root, Miller never invokes store GC at all, and nothing deletes sidecars. The two dead dogfood worktree views pin ~806 MB (91% Miller-owned sidecars: content/search/vector per view). ~350-410 MB per removed worktree, forever. Correctness hazard: `StoreFamilyResolver` matches views by root path, so re-creating a worktree at the same path silently adopts the dead view and its stale sidecars. Side finds: a 171 MB `_quarantine-202916` orphan sidecar copy; 4 dead `store_families` rows in workspaces.db; the LIVE view holds 872 manifests / 1.47M manifest_entries (~315 MB) because generation GC has never run.

Fix split (agent recommendation): (1) Miller deletes its own sidecars on workspace remove/prune (~91% of bytes, no contract change); (2) julie-extract grows `store maintain retire-view`; (3) one-paragraph contract amendment defining end of view life. Do NOT infer death from a missing root path.
