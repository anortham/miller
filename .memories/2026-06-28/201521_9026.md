## Edit redesign decision

### WHAT
Updated `docs/findings/2026-06-28-julie-miller-edit-adoption.md` with a new evaluation of indexed content, removal vs redesign, and a stronger next-slice recommendation.

### WHY
The user pointed out that Julie edit was not meant to merely edit files; it was meant to save tokens in harnesses where native edit requires reading the whole file first. Miller's original edit design likely predated the current content corpus and may reflect old constraints.

### HOW
Verified current Miller data shape: `symbols.db` stores hashes/spans/facts, not full content; `content.db` is revision-fresh and stores raw text chunks with byte ranges, but is chunked/normalized and currently documented as advisory, not an edit buffer. `ContentCorpusWriter` reads disk under hash verification and skips large/missing/hash-mismatch/non-decodable/I/O-failed files. `EditService` reads disk internally and uses exact caller-supplied `old_text` today.

### IMPACT
The correct next move is not deletion. Redesign the existing `edit` tool so `replace_text` can use indexed content to locate candidate spans from small selectors, verify against disk, preview exact diffs, and apply with existing freshness/atomic guarantees. Removal should only be reconsidered if the redesigned edit still cannot beat built-in harness editing on common workflows.
