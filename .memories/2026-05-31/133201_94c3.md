## Miller Replacement Reframe

### WHAT
Reviewed Miller against Julie with the corrected product premise: Miller is a replacement opportunity, not a drop-in clone of Julie's daemon-heavy architecture.

### WHY
The initial review flagged missing daemon/CLI/workspace-registry compatibility, but the user clarified those are not necessarily desired because Julie's daemon has been a major source of resource use and reliability problems.

### HOW
Synthesized local inspection and four delegated explorer reports into a native Miller plan: keep stdio/single-process simplicity, preserve high-value code intelligence behavior, and only add compatibility where it reduces migration friction without reintroducing Julie's operational complexity.

### IMPACT
The recommended direction is to prioritize search parity, graph correctness, richer context, extracted signal consumption, MCP migration shims, and explicit non-goals for daemon/embeddings/Tantivy. This changes the plan from “port Julie” to “replace Julie’s value with a simpler Miller-native architecture.”
