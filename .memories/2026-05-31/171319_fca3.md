## Dogfood Fixes for Large Workspace Registry Reads

### WHAT

Dogfooding Miller against large repos (`openclaw`, `hermes-agent`) exposed and fixed two large-workspace failure modes:

- External `workspace status` no longer hydrates the full registered workspace index.
- Identifier-name fallback graph loading is capped to avoid explosive homonym fan-out.
- Registered workspace index cache now uses single-flight loads and evicts older entries for the same workspace.

### WHY

OpenClaw first indexed successfully, but external status/search revealed Julie-like resource sink behavior:

- `workspace status` for OpenClaw timed out while loading a 1.9 GB DB into full in-memory search/graph structures.
- Cross-workspace search climbed past 36 GB RSS before being killed.
- SQL showed the core fan-out problem: ~1.09M identifier rows and global fallback name resolution would create ~590M speculative edges, with `expect` alone at ~267M candidate edges.

### HOW

- Added `WorkspaceIndexFactsReader` for cheap status/dashboard metadata (`COUNT(*)`, distinct extensions) without BM25/graph/bridge hydration.
- Moved freshness label mapping into `WorkspaceFreshnessView` so status and provider share the same state wording.
- Changed `WorkspaceTool` registered status to render from registry + cheap DB facts instead of `IWorkspaceIndexProvider.Resolve`.
- Added `maxNameResolutionTargets` to `SymbolGraphReader`; production `RepositoryIndexLoader` uses cap 16 to skip overly ambiguous fallback names while preserving precise `relationships` rows and small homonyms.
- Reworked `WorkspaceIndexProvider` cache from append-only value cache to `Lazy<CachedIndex>` single-flight per key, with failed-load cleanup and same-workspace older-key eviction.
- Added focused regression tests for status without full-index tables, fan-out dropping, single-flight loading, and cache eviction.

### IMPACT

- OpenClaw external status dropped from timeout/huge load to ~153 ms.
- OpenClaw cross-workspace search dropped from runaway >36 GB RSS and timeout to ~6.2s with ~1.2 GB peak RSS.
- Hermes cross-workspace search completed in ~3.1s with ~327 MB RSS.
- Verification passed: focused 59 tests, fast suite 1,159/1,159, scale suite 14/14, `git diff --check` clean.

Remaining performance issue: first cross-workspace search still exceeds the 500 ms soft budget because it hydrates the whole registered workspace index on first read; next architectural target is projection-specific/read-through loading or persisted search structures.
