## Fixed rename-preview collapse in large files (commit `768565e6`)

The `edit` tool's rename preview reported ~1200 lines as changed for a 3-site rename. Found by dogfooding the live MCP server, not by any test.

- **Root cause:** `UnifiedDiff.TryDiffLines` bailed out whenever the post-prefix/suffix-trim region exceeded `MaxLcsCells` (1M). TraceTool.cs left ~1193 lines per side = 1.42M cells, so it fell through to `RenderBoundedFallback`, which treats *everything between the first and last touched line* as changed. Preview read `@@ -905,1193 +905,1193 @@` with "1153 old lines omitted".
- **Fix:** equal-length regions (`n == m`) admit an exact positional alignment in O(n) — emit Equal for matching lines, Delete+Insert pairs where they differ. Gated on `CountPositionalDifferences(...) <= MaxFallbackLinesPerSide` (40).
- **The gate is load-bearing, not decoration.** My first attempt took the `n == m` path unconditionally and broke `Render_LargeUnrelatedInputs_ReturnsBoundedChangeProofWithoutQuadraticMatrix` — that test feeds 2500-vs-2500 *fully different* lines, which is also equal-length, and expects the bounded fallback. Without the difference cap the fast path emits a 2500-line dump.
- **Why 40 specifically:** `EditService.RenderRenameDiff` concatenates per-file diffs with **no outer cap**, so the per-file fallback is the only bound on a wide multi-file rename. Deliberately did not widen the threshold for that reason.

### Verification (real file, not just synthetic)

Built a throwaway console against `Miller.Core` and ran renames against the actual 2918-line `TraceTool.cs`:

- 6-site rename → 6 tight hunks, 12 changed lines, no omissions
- 35-site rename → 26 hunks, 70 changed lines, no omissions
- 90-site rename → bounded fallback by design (above threshold)

Gates: fast 5124 passed / scale 92 passed / Release build 0 warnings.

### Method note worth keeping

This bug and the earlier `rename_symbol` gate bug both came from **dogfooding the live MCP**, after a static review fleet had already passed. The review fleet actually surfaced "'exact' is overloaded" and its adversarial verifier *refuted it as cosmetic* — dogfooding then showed it disabled `rename_symbol` entirely. Static review found the ambiguity; only dogfood found the consequence.
