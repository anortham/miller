## Fixed the artifact-identity bug class found by the Grok review fleet

A 10-chunk adversarial Grok review of the v1.14.0 RC (255 commits) surfaced one root cause with four reachable instances. All fixed together in one pass.

### Root cause

Derived and cached state gated freshness on `revision` — but `FullRebuildPromotion` **restarts julie's revision counter at 1**. Verified empirically on this workspace: `extraction_revisions` row 1 is `scan|force|2.18.0`. So a workspace sitting at revision 1 that force-rebuilds (exactly the schema 4→5 upgrade this release ships) lands on revision 1 *again*, the gate reads `1 == 1` as fresh, and the sidecar serves pre-rebuild data silently and permanently.

`CLAUDE.md` already stated the invariant — *"detects rebuilds by artifact_id changing, never by revision comparison alone"* — the derived artifacts just didn't honour it.

### Fixed

- **New `SymbolsArtifactIdentity`** — one definition of "same extract generation" so the sidecars can't drift apart again.
- **`search.db`** — `artifact_id` in `meta`, `SchemaVersion` 8→9 (self-heals every existing artifact once), both `EnsureBuilt` and `EnsureCurrent` gates fixed.
- **`content.db`** — `artifact_id` in `content_meta`, schema 2→3, new `BuiltFromCurrentArtifact` gate. Worse than search: `WorkspaceSourcesAgree` only walks content→symbols one-way on path+hash, so an extractor-upgrade rebuild of unchanged files reported the pre-promote corpus fresh *forever*.
- **`ContextTool` / `CliDispatch`** — `reference_mode=usage` read `content.db` with **no freshness gate at all**; `ReadContainingSymbolChunks` took no revision parameter. Now derives identity and contributes no evidence when stale.
- **`trace` refs continuation** — tokens never bound artifact identity despite `trace-json-v1.md` requiring it; `RunRefs` already loaded a `ReferenceEvidenceSnapshot` and ignored it.
- **`IndexBootstrapService`** — force-scanned and promoted with **no single-writer lock**, violating `JulieExtractRunner.cs:333`'s documented precondition, on the v1.14 upgrade path specifically.

### Judgement calls that diverge from Grok's recommendations

- **No `force` flag added.** Grok wanted `fullRebuild` wired through to force rebuilds. But a real full rebuild always mints a new nanosecond-stamped `artifact_id`, so the identity check already catches every genuine force — adding `force` would trigger expensive full FTS rebuilds on no-op converges.
- **Bootstrap lock skips rather than throws.** Throwing from `forceRescan` propagates out of `LoadIndexWithAutoRebuild` and surfaces as "MCP failed to connect" — the exact failure auto-heal exists to prevent. Waits 30s, then skips so the other instance's rebuild is picked up by the retry load.
- **Trace continuation binds artifact_id but deliberately NOT revision.** Binding revision broke `Refs_Json_ContinuationSurvivesUnrelatedWorkspaceRevision`, a deliberate affordance: the population fingerprint already invalidates a token whose own refs moved, so unrelated edits must not kill in-flight cursors. Updated `trace-json-v1.md` to match reality rather than leaving doc and code disagreeing.

### Two of my own errors, corrected

- First `EnsureCurrent` attempt only rebuilt across a swap at *equal* revisions. Applying julie's changed-file delta across an artifact swap is wrong at any ordering — the delta is expressed against the promoted extract's history.
- I told the user Grok's "`WorkspaceIndexProvider` is safe" verdict was unsupported by the code. **I was wrong.** `CacheKey` includes `FileWriteStampTicks` + `FileLength`, which a promote necessarily changes. I had grepped only for the literal string `artifact_id` and stopped instead of reading the record. No fix needed there; Grok was right and all four of its safe verdicts held up.

### Test fixtures made contract-faithful

Two fixtures built a `content.db` with no paired `symbols.db` and no `content_meta` row — unfaithful data that the new gates correctly rejected. Fixed the fixtures rather than weakening the gates, per the repo's own prior lesson.
