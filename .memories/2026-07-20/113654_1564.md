## P2a CI OOM root-caused: 19 GiB output buffer, not the compute buffer

The Linux CI failures on the 32768-token engine test were misdiagnosed across two sessions. The 2048→512→256 `MAX_DECODE_UBATCH_TOKENS` step-downs never touched the failing term.

- **Root cause:** `batch.add_sequence(tokens, seq_id, true)` in `encode_group` flagged EVERY token for output. llama.cpp's `output_reserve` then allocates a vocab-width f32 row per flagged token: 151,936 vocab × 4 B × 32,768 tokens ≈ 19,086 MiB. The 16 GiB Linux runner refuses the allocation (`ggml_aligned_malloc: insufficient memory`); macOS overcommits untouched pages, so it "passed locally," which hid the bug.
- **Evidence:** both failed CI runs (512 and 256 settings) show the compute buffer reserving fine (330/165 MiB) then `output_reserve: failed to allocate output buffer of size 19086.62 MiB` → `decode ret=-2`.
- **Fix (9bd9cb5):** pass `false` — `add_sequence` still flags each sequence's last token, which is all Last pooling reads; the non-causal encoder (bge/Cls) ignores per-token output flags. Measured: CPU output buffer 19,086.62 MiB → 0.58 MiB.
- **Verification:** conformance 9/9 both models (goldens byte-identical — proves the Cls path too), engine tests 11/11 (`--test-threads=1`; parallel in-process runs fail on `BackendAlreadyInitialized`, a harness artifact CI avoids via per-test processes), serve 5/5, unit suites green, fmt+clippy clean.
- **Doc correction:** `MAX_DECODE_UBATCH_TOKENS` comment rewritten with the real memory story; stale `<=256` assert removed; 256 kept as the verified setting (>9 GiB CI headroom now).

## IMPACT

The "tuning is out of room" trade-off decision (KV quantization / lower max_text_tokens / accept reduced CI coverage) is OFF the table — it was premised on the wrong diagnosis. CI run 29739131738 on 9bd9cb5 should now pass all four conformance legs.
