## WHAT

Implemented generated-ignore Task 2: successful workspace removal now cleans only the canonical root's Miller-owned global policy, reports bounded cleanup failures, preserves all root `.julieignore` files, and documents migration behavior.

## WHY

Moving generated policy out of the checkout creates Miller-owned lifecycle state. Removal needed exact cleanup without allowing corrupt registry data, test seams, or header guesses to redirect deletion.

## HOW

- Cleanup derives the policy ID from the validated canonical root, never from a registry row's workspace ID.
- The resolved target must be the exact non-recursive file under the configured Miller `ignore-policies` directory.
- `File.Delete` is called directly: absence is a no-op; path/access failures become `IgnorePolicyCleanupError` while existing index/registry/sidecar safeguards continue.
- Public removal signatures remain unchanged and always use the configured Miller home. Internal overloads allow isolated tests only.
- Removal JSON adds nullable `ignore_policy_cleanup_error`; CLI compact output includes an actionable warning.
- Legacy/user/inherited/edited/malformed root policies are never touched or classified by content.
- CLI, known-limits, and Eros CLI contract docs record ownership, warning semantics, and manual legacy cleanup.

## IMPACT

Workspace removal now owns the full global-policy lifecycle without expanding deletion authority. Corrupt path-safe registry IDs cannot target another workspace's policy, tests never touch live `~/.miller`, and consumers can distinguish successful removal with a cleanup warning.
