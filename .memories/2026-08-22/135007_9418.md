## Linux v1.21.0 continuous-testing dogfood

### WHAT

Exercised the released Miller `1.21.0+da6be63f68cf` CT lifecycle on Linux across .NET, JavaScript `node:test`, and Python `pytest`. Verified enable/start/run/status/failures/stop/disable behavior and restored original CT state.

### WHY

Windows coverage was thorough; this run sought Linux-specific provider, filesystem, process, and packaging failures on real repositories.

### HOW

- Miller: three xUnit projects, 8,247 selected cases, final `partial`, 15 red and 2 stale. The main project took about 205 seconds and used at least 53 per-method chunks.
- Razorback: one `node-test` project, 34 selected, green; CT returned to disabled/stopped.
- more-itertools: one pytest project, two file-level cases covering 736 pytest nodes, green in about 8.5 seconds; CT returned to disabled/stopped.
- Root-cause tracing separated real product evidence from fixtures: 13 reds depend on a helper host absent from the CT flat generation output while normal builds find it through repo-layout fallback. The Linux chatty-child failure is a fixture mismatch: it prints for ~2s inside a 6s sampling window. The shadow-copy test models a live process with a read handle, which is not equivalent on Linux.

### IMPACT

JS and Python release paths work end to end on Linux. Miller's own CT result is not yet authoritative because the generated .NET output does not reliably carry the helper host. `tests run --wait` can outlive the MCP call when sequential chunked projects exceed the client limit. A recommended `workspace refresh` also left vectors degraded with the same missing completeness stamp.
