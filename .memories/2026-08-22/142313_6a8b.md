## Linux dogfood repair plans written

### WHAT

Created three execution-ready light plans in `docs/plans/` and mapped them in `docs/README.md`:

- CT repair: deterministic .NET referenced-project output, portable Linux fixtures, selection/chunk diagnostics, bounded MCP wait/readiness, and additive provider/run metadata.
- Sidecar convergence: typed refresh outcomes, bounded search/content retry, resident vector desired-state reconciliation, and actionable health rendering.
- Ignore-policy hygiene: generated policy under Miller home instead of a new root `.julieignore`, with scan/update/watcher parity and safe lifecycle behavior.

### WHY

The dogfood findings span three independent module boundaries. Separate plans keep each branch shippable, give each risk its own gate, and avoid coupling CT changes to semantic/index lifecycle work.

### HOW

Used Miller evidence and focused Luna packets to prove exact symbols, callers, impacts, and tests. Architecture choices keep existing public tools and schema version 1, use MSBuild project-specific output rather than host-specific copying, use completeness stamps as durable vector desired state, and preserve user-authored root ignore policy.

### IMPACT

The user can approve all three plans as one program, but execution can land and verify them independently. No implementation has started; the planning worktree contains only plans, docs-map update, and memory checkpoints.
