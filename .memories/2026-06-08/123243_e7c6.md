## Hardened lock-busy recovery around duplicate workspace registry rows

The live writer lock was healthy after restart, but CLI/status still showed stale sidecar expectations because the machine registry contained two rows for `/Users/murphy/source/miller`.

- **WHAT:** Fixed registry upsert to prune legacy rows that point at the same canonical root and `symbols.db`, and hardened one-shot CLI current-workspace selection to prefer the current stable workspace ID before falling back to duplicate row ordering.
- **WHY:** `workspace_id` generation now folds case on macOS/Windows. The old non-folded row (`816...`) remained beside the current folded row (`b275...`), so CLI refresh/status could advance or display the wrong row while the server leader held `.miller/indexer.lock`.
- **HOW:** `WorkspaceRegistry.UpsertSeen` now prunes same-root/same-index duplicates transactionally, using case-insensitive path comparison on Windows/macOS only. CLI `workspace status`, `workspace refresh/full`, and `workspace list` share a current-row resolver that computes the stable ID from the symlink-resolved current root first.
- **IMPACT:** Existing duplicate registries self-heal on future registration/restart, and the CLI immediately targets the stable row even before the old row is pruned. `workspace refresh` verified locally advanced `b275...` to the latest sidecar revision without killing the leader process.

Remaining design gap: `workspace full` still cannot ask a separate lock-holding server process to force-scan when no revision changes are visible. Recorded TODO item 6 for a Windows-safe leader request path rather than weakening the single-writer lock.
