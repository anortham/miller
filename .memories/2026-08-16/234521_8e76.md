## Post-restart verification found two reproducible latency defects

Miller 1.19.3 and julie-extract 2.33.4 start successfully and converge to a correct, exact index, but the live system does not yet meet the expected immediate-return behavior.

- **WHAT:** Verified current versions, startup availability, one-time upgrade rebuild, exact store resolution, search/content/vector sidecars, common tool timings, graph-heavy tool timings, and a temporary one-file add/delete watcher cycle.
- **WHY:** The release needed live dogfood evidence after restart, especially for accumulated deltas and tool responsiveness.
- **HOW:** Used bounded MCP timing batches, structured phase telemetry from a snapshot of the active JSONL log, and a temporary unique C# symbol that was added and removed with the worktree returned clean.
- **Root cause 1:** Every family-store `context`/`impact` request constructs a new `SqliteSymbolGraphIndex`; its `_supplementalEdges` cache is instance-only. `LoadSupplementalEdges` replays the family-store snapshot and costs about 3.9 seconds to return only 24 edges. Warm context remained 5.84 seconds and impact 5.07 seconds.
- **Root cause 2:** A valid one-file add required 21.1 seconds to become searchable and deletion required 19.0 seconds to disappear. The primary revision advanced quickly, but search/vector sidecars were stale until their background convergence completed.
- **Healthy paths:** Lexical search, summary inspect, refs trace, and pattern listing normally complete in roughly 35–102 ms, with shared 0.7–0.8 second tails. Final health showed revision 24429 current, queue empty, and search/content/vector sidecars current.
- **IMPACT:** The release is functionally correct but not performance-clean. Next work should cache immutable supplemental edges at the existing revision-keyed `WorkspaceIndexProvider` cache boundary and separately phase-profile the ~20-second sidecar convergence path before changing it.
