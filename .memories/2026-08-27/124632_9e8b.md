## Context latency fix A1: cold fact-cache load off the critical path

### WHAT
- `docs/plans/2026-08-27-context-latency-diagnosis.md` — measured cost model replacing the audit's first guess: the whole-generation `RevisionFactCache` load (~4.8 s) blocked `anchor_resolution` via term-rescue test-subject promotion on EVERY query call, even at reference_mode=off; plus graph_reach rebuilds per revision advance (1.3–4 s cold); per-lookup sidecar cost secondary (0.32 ms warm).
- Fix A1 (user picked over A2 bounded-read): `RevisionFactCacheStore.IsWarm(scope, identity)` probe; `FamilyStoreReadSession.ResolutionFactsWarm` + `WarmResolutionFactsInBackground()` (own connection, safe past session dispose); exposed via `WorkspaceReadHandle`; ContextTool ReferenceMode.Off path skips promotion when cold, stamps `term_rescue: skipped_cold_facts`, kicks the background load. reference_mode=usage untouched.

### WHY
Telemetry audit Priority 2: context p50 ~7 s field / p95 20–37 s; the field profile is the cold profile because context is a first-call tool and every save re-colds revision-keyed caches.

### HOW verified
- TDD: store IsWarm test, session warm/cold/store-less tests (4 new), all EditTool/Context suites green, fast suite 8,936/0.
- End-to-end proof on a fresh server via a stdio MCP probe script, same query as baseline: anchor_resolution 4,813 ms → 6 ms; second call promoted warm (404 ms); telemetry stamp confirmed in export. Cold total 7,633 → 5,666 ms.

### IMPACT / next
Remaining context cost is fix B1: graph_reach rebuild per revision advance (3,978 ms in a fresh process) — give the reachability graph advance-on-revision shape or converge it in the leader. Then audit Priority 3 (mid-scan file deletion, likely julie-extract side).
