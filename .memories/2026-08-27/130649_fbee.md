## Context latency fix B1: the per-save graph rebuild was one unbounded SQL scan

### WHAT
- `BlazorComponentGraphReader.ReadEvidence` no longer scans the whole family-store symbols table. The query is bounded to razor files (`file_id IN (SELECT file_id FROM files WHERE language='razor' OR path LIKE '%.razor')`), carries a razor-type LIKE prefilter with the TestLinkageReader-style escaped-spelling arm, and guards on `SqliteSchemaObjects.Exists(connection, "files")` for minimal legacy DBs (RepositoryIndexLoaderBridgeTests caught that).
- Guard test added: `Read_EscapedComponentTypeSpelling_StillProducesTheEdge` (a `-`-escaped `razor-component` type still yields the edge — pins the prefilter's escape arm forever).
- Plan doc + TODO updated with measured before/after.

### WHY
After fix A1, statement-level logs showed post-advance graph_reach was almost entirely the supplemental edge reload: 1,192 ms for 25 edges. EXPLAIN showed a full SCAN of the 908k-row symbols table (8.1 GB store.db) — no symbols index matches the query's filters and the visibility join can't drive one; 61k rows streamed into managed JSON parsing for ~70 razor rows.

### HOW verified
- Wrong first hypothesis honestly recorded: a LIKE-only prefilter did NOT move the number (the scan itself was the cost, proved by re-measure). The version-id IN drive was found via EXPLAIN + sqlite3 timing on the live store (958 ms → 0.25 ms for the identical row set).
- Probe (fresh server, 3 calls, same query): supplemental 1,192 → 135 ms; post-advance graph_reach 1,285 → 223 ms; post-advance total 3.1 → 2.0 s; cold 7.6 (pre-A1) → 4.8 s.
- Blazor/graph/bridge suites green; fast suite 8,937/0.

### IMPACT
The common case (context call after a file save) is now ~2.0 s on this machine, down from ~3.1 s, and from ~7 s before the day's two fixes on a fresh process. Optional remainder: a fresh process's first call joins the background fact load inside graph_reach (~2.9 s once) — decide after field telemetry.
