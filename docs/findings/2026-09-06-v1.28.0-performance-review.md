# v1.28.0 performance regression review

Date: 2026-09-06. Measured source: `66e30294994301ac4b68b78ea54b0549cb97bd60`.
Baseline: released v1.27.2, `e32dc5e2b29d12928de424eb148843d2d292236c`.
[Raw measurements and replay script](2026-09-06-v1.28.0-performance-review.json).

## Findings

There is a measurable CLI latency regression. Reader retention adds fixed work to small
commands. A separate 20-sample confirmation measured summary inspect at 167 ms median / 176 ms
p95 on v1.27.2 and 296 ms median / 319 ms p95 on v1.28.0. The median increase is 129 ms, or 77%.
The broader replay also recorded intermittent longer tails on the new version. Their precise
lock-versus-storage cause is not established.

The tested CLI source search improved from 5,256 ms to 3,284 ms median, about 38%.
All 96 calls in the eight-workload comparison succeeded. Every workload returned byte-identical
JSON across versions and repetitions. This includes context after its implementation refactor.

Warm live MCP calls remained usable on this corpus: context p95 1,221 ms, changed-path impact
p95 1,593 ms, and lexical symbol search p95 233 ms. These are current-version measurements,
not a controlled old-versus-new resident MCP comparison. The first overview inspect took
6,498 ms; subsequent calls took 359–460 ms. That first-call cost remains visible and is not
classified as a new regression without a matched cold baseline.

No avoidable implementation defect was established. Reader protection was preserved and no
production code changed. The measured CLI overhead remains; this review does not declare
performance regression-free or treat the reliability cost as a speed improvement.

## Reader-registration cost

An isolated copy of the current runtime used a transparent extractor wrapper. It recorded only
the operation name, elapsed time, CPU time, and exit status, then forwarded the real producer's
output unchanged. No credentials were recorded and no reader safety bypass was used.

Each summary inspect invoked exactly one `store reader acquire` and one `store reader release`.
Across ten diagnostic pairs, median child times were 41.0 ms wall / 6.2 ms CPU for acquisition
and 55.8 ms wall / 5.1 ms CPU for release. The parent wrapper overhead is outside those child
measurements. Earlier diagnostic pairs observed 441/358 ms and 56/129 ms acquire/release times.
This locates substantial cost in producer process operations and waiting, not result rendering.

The call path is `WorkspaceReadSessionFactory.OpenForOneShotCli` →
`FamilyStoreReadSession.Acquire` → `StoreReaderRegistrationRunner` →
`JulieStoreClient.InvokeReaderAsync`. Disposal releases the registration.

Read-only producer inspection at `e4f6a5db601ec7f1b9812b373346a74a7ccd8117` found
`begin_coordinator` uses `BEGIN IMMEDIATE`, a five-second busy timeout, and `synchronous=FULL`.
Acquisition and release therefore add serialized durable writes. Existing producer evidence in
`docs/evidence/2026-09-producer-retention-contract.md` reports the same 10 data statements,
134 VM steps, and zero full-scan steps at 1k, 10k, and 100k manifest entries. That evidence does
not measure CLI setup, commit latency, or contention and was not rerun during this review.

The wait/CPU split is consistent with lock or durable-I/O costs; it does not distinguish them.
A future optimization needs phase timings around coordinator admission and commit, plus the
same workload before/after. Removing registration or weakening durability is not a justified fix.

## Live MCP and resource observations

One initial call followed by five warm calls per workload, serially through the session's server,
with `ensure_fresh=false`. Semantic retrieval remained at the live server's normal setting.

| Workload | First call ms | Warm p95 ms |
|---|---:|---:|
| Lexical symbol search | 175 | 233 |
| Natural-language search | 986 | 1,078 |
| Source search | 289 | 425 |
| Inspect overview | 6,498 | 460 |
| Trace refs | 1,625 | 1,640 |
| Context | 1,371 | 1,221 |
| Changed-path impact | 1,285 | 1,593 |

All 42 calls succeeded. An additional search comparison with default freshness versus explicit
false showed 136–259 ms versus 142–154 ms across three post-warmup calls; no large default-path
penalty was reproduced.

After warming the graph and fact caches, the server held about 1.3 GiB RSS. Three five-second
idle samples were 2.4%, 2.6%, and 2.8% CPU, with RSS settling at 1,316 MiB. The family store WAL
was zero bytes. These short observations do not prove long-term memory stability. The 256 MiB
fact-cache setting is a soft retained-cache budget, not a process-RAM limit.

Historical telemetry was inconclusive for resident regressions: old v1.27.2-labelled rows span
12 commit builds and mostly different workloads. Only two non-null target groups matched the
initial current-build sample. One recent comparable inspect was 133 ms old / 131 ms new.
The other was 19/29 ms old / 127 ms new but came from an earlier September 4 build. Historical
aggregate p95 values were not used as a controlled baseline.

## Verification and scope

- `scripts/bench-fact-cache-resources.sh --runs 5 --output /tmp/miller-perf-review/fact-cache.json`
  passed. After the first run, fixture times were 6.35–6.91 ms. Each run reported four loads and
  the same retained/active/evicted accounting. This tiny fixture checks accounting, not realistic
  process memory or production throughput.
- `scripts/bench-sidecar-convergence.sh --fixture sqlite-synthetic --mode both --runs 4
  --output /tmp/miller-perf-review/sidecar.json` passed with parity validation. Each incremental
  path read four delta rows, handled two changed paths, and performed zero full-file/document
  scans. Fresh-process incremental content times were 10.80–11.67 ms; search 13.79–16.56 ms.
  These small-fixture numbers establish bounded work, not a historical performance comparison.
- Full fast/Scale/Windows suites were not rerun: no production code changed. The existing release
  verification remains the correctness evidence outside these focused measurements.
- Extraction throughput, dashboard browsing, CT provider execution, sustained load, and a
  controlled old/new resident MCP comparison were not measured. No claim is made about them.
- All existing worktrees were checked. The prior `v1.26.0-mcp-dogfood` worktree has an untracked
  `.tools` entry; it was untouched. Other existing worktrees were clean. Temporary benchmark
  builds stayed outside the repository and no branch/worktree changes were stranded.
