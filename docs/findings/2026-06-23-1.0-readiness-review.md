# Miller 1.0 readiness review

Date: 2026-06-23

Scope:

- Audit Miller's current architecture for 1.0 release risk.
- Compare Miller against the live Julie checkout at `/Users/murphy/source/julie`.
- Focus on whether Miller can credibly replace Julie for agent code-intelligence workflows.

## Bottom line

Miller is close to a 1.0-quality deterministic local core, but it should not claim "Miller alone replaces all of Julie" yet.

The accurate 1.0 positioning is:

- Miller replaces Julie's deterministic local agent-tool core: search, symbol/file inspection, context bundling, references, trace/path, impact, editing, workspace lifecycle, content/web/text import, structural facts, TODO marker audits, and JSON/JSONL integration feeds.
- `julie-extractors`/`julie-extract` replaces Julie's old embedded external-extract/parser-host role.
- Eros replaces Julie's semantic/vector, higher-level guidance, confidence/evidence, dead-code, hotspot, and multi-workspace/fleet intelligence workflows.

If the public 1.0 message is "Miller replaces Julie completely" without that product split, there are still gaps.

## Findings

### 1. Direct reference enumeration was the clearest Julie parity gap

Julie has a first-class `fast_refs` tool and CLI command with caller-controlled `limit`, optional definitions, workspace selection, and reference-kind filtering.

Evidence:

- Julie `FastRefsTool` exposes `symbol`, `include_definition`, `limit`, `workspace`, and `reference_kind` (`crates/julie-tools/src/navigation/fast_refs.rs`).
- Julie CLI exposes `julie-server refs "Command" --kind call --limit 20` (`src/cli_tools/subcommands.rs`).
- Miller exposes bounded context references through `inspect depth=full`; that path uses `ExtractReader.ReadReferences(dbPath, sym.Name)` and caps `refs`, `callers`, and `callees` at an internal `RefLimit = 50`.
- Miller now exposes direct reference enumeration as `trace mode=refs`, with MCP/CLI/JSON support for `reference_kind`, `include_definition` / `--no-definition`, `limit`, `scope`, and `workspace_id`.
- `ExtractReader.ReadReferences` is explicitly name-based: `SELECT ... FROM identifiers WHERE name = $name`.

Status:

- Addressed as an existing-tool mode, not a new tool: use `trace target mode=refs`.
- JSON labels rows with `confidence: "name_based"` and keeps references in a mode-specific `references` array.
- Future improvement remains possible if `julie-extractors` emits resolved target symbol IDs for identifier refs.

### 2. Julie `signals` belongs in Eros, not Miller

Julie has a standalone `signals` report that produces entry-point, auth-coverage, review-marker, scheduler, entry-point linkage, and centrality-gap sections.

Miller has the lower-level facts needed for this kind of work:

- `patterns` for extractor structural facts.
- `search --mode markers` for comment/doc-comment review markers, with `todos --json` kept as a CLI compatibility alias.
- `symbols export --jsonl` with `body_hash`, `has_doc`, and `is_test`.
- `complexity export --jsonl` for hotspot inputs.
- `workspace health --json` for readiness and extraction-quality aggregates.

Miller does not provide a single equivalent `signals` command/report, and that is intentional. The report answers
"what should I care about?" across entry points, coverage/linkage gaps, scheduler jobs, and centrality. That is an
Eros-level workflow over deterministic Miller feeds, not a Miller navigation primitive.

Decision:

- Do not add a Miller `signals` MCP tool, CLI command, or export just for Julie parity.
- Treat old `julie-server signals` usage as an Eros migration concern.
- Miller's 1.0 obligation is only to keep the deterministic feeds stable enough for Eros: `patterns`, marker search
  (`search --mode markers` plus the `todos --json` CLI alias), `symbols export`, `complexity export`,
  `workspace health`, and telemetry/content exports where useful.

### 3. External extract is a `julie-extractors` concern, not a Miller concern

Julie exposes `julie-server extract scan|update|delete|analyze|info` for host-owned SQLite extraction.

Miller deliberately delegates parsing to a pinned `julie-extract` binary and consumes the resulting artifact.
Standalone extraction is already owned and documented by `~/source/julie-extractors`.

Decision:

- Do not add a Miller compatibility surface for `julie-server extract ...`.
- Keep Miller docs focused on the consumer boundary: Miller consumes `julie-extract` artifacts; parser/extraction
  workflows live in `julie-extractors`.
- If release messaging mentions Julie replacement, point extraction users to `julie-extractors` rather than
  restating its full documentation inside Miller.

### 4. The live health path is strong, but stale-leader remediation is still operator-driven

Current health output is useful and honest. In this checkout, `workspace health --json` reported:

- `state: usable_with_warnings`
- `search_sidecar: current`
- `content_corpus: current`
- `indexer_leader_version_mismatch` because a live leader is running a different git SHA of Miller with the same extractor version
- recommended action: "stop stale Miller processes so the current build leads indexing"

This is not a release blocker for normal packaged users, because extractor-version-aware leadership is the load-bearing invariant and equal extractor versions intentionally avoid thrash. It is still a 1.0 support risk because the suggested remediation is manual, and Windows users have fewer comfortable process-management tools.

Recommendation before or shortly after 1.0:

- Keep the no-thrash equal-version policy.
- Improve the operator path: clearer `workspace status` text, a docs recipe for macOS/Linux/Windows, or a safe `miller workspace leader` diagnostic/remediation command that requests graceful handoff where possible.

### 5. The main architecture is viable, but new public CLI work should not keep growing `CliDispatch`

Current size hotspots:

- `src/Miller.Server/Cli/CliDispatch.cs`: 1585 lines, 47 methods, 21 catch blocks.
- `src/Miller.Server/Tools/SearchTool.cs`: 1609 lines, 59 methods.
- `src/Miller.Server/Tools/TraceTool.cs`: 1485 lines, 63 methods.
- `src/Miller.Server/Tools/WorkspaceRender.cs`: 1141 lines, 56 methods.
- `src/Miller.Server/Hosting/IndexerService.cs`: 1001 lines, 42 methods.
- `src/Miller.Server/Workspaces/WorkspaceIndexProvider.cs`: 810 lines, 48 methods.

This is not automatically bad. Several files are large because they are public surface coordinators with compact and JSON renderers plus telemetry. The risk is that any more 1.0 parity additions or migration aliases will make `CliDispatch` and tool renderers harder to change safely.

Recommendation:

- Do not broad-refactor the host/indexer before 1.0 without a concrete bug.
- If adding new public CLI commands before 1.0, first split `CliDispatch` by command family or introduce small command handlers so the new work does not make the existing dispatch file worse.
- Keep JSON DTO/source-generated serialization close to contract docs for any new stable JSON surface.

## Recommended 1.0 gate

Completed during this readiness pass:

- Published the replacement boundary in README, public site copy, and generated agent guidance: Miller is the
  deterministic local core; `julie-extractors` owns parser-backed extraction; Eros owns semantic retrieval,
  guidance, signals, confidence/evidence, and commercial orchestration.
- Added `trace mode=refs` so Julie `fast_refs` parity is covered without adding another public tool.

Before tagging 1.0, close these:

1. Re-run full release validation on macOS, Linux, and Windows package artifacts.
2. Prepare v1.0 README/site/release-note metadata from live command output and release facts.
3. Verify downloaded v1.0 assets and `.sha256` sidecars before updating final release evidence.

Post-1.0 cleanup candidates:

- Split `CliDispatch` before adding another broad command family.
- Factor compact/JSON rendering out of the largest tool files only when touching those tools for product work.
- Consider a safer, documented stale-leader remediation workflow for local dev and Windows users.
