## External review

The dashboard and registry changes were reviewed by two external models in one bounded campaign
(`convergence` profile, 2 of 3 external invocations spent, closed `clean`):

- Grok found one critical defect: `WorkspaceTool.Remove` pre-resolved its row with the default read
  intent, so `WorkspaceRemoval`'s mutate guard could never fire. Reverting the fix reproduced a real
  deletion of a live workspace's `.miller` directory.
- Codex found five, including the general form of the same defect (the intent parameter had a
  default at all) and two open holes in the destructive prune gate.

Every accepted finding was reproduced as a failing test before it was fixed. Three carry red-to-green
evidence; the rest are covered by new tests that pass.

`workspace prune` was run against the author's registry with the new gate. Five runs drained the

| --- | ---: | ---: | --- |
| 1 | 9 | 51 | 10 files, 482 MB |

| 5 | 1 | 35 | 4 files, 128 MB |
| 6 | 0 | 35 | — |

The registry went from 60 rows to 35 and reclaimed about 5.4 GB. Before this release the same
registry pruned four rows per run and refused twenty-five as unconfirmed.

Four rows remain, honestly:

- Two are correct refusals — a scratchpad repo and a temp directory whose removal cannot be proven.
  The gate is doing its job.
- Two fail with `store view retirement exited 1: no diagnostic output`. That is julie-extract's
  retire subprocess exiting non-zero with nothing on either stream. The prune degrades rather than
  fails: the rows stay and no data is lost.

`store maintain` exited the same way six times during the first run, with the same non-fatal
outcome. Both belong to julie-extract, not to Miller, and this prune only surfaced them because it
now reaches far more families than it used to. Recorded here as producer-side follow-up.
