### The "no diagnostic output" rows were a Miller bug, not a producer one

This was first recorded here as a julie-extract fault. That was wrong, and running the command by
hand disproved it. julie-extract emits a complete JSON report on **stdout** and exits 1 with an
**empty stderr**:

```json
"failure_class":"invalid_arguments",
"error":{"class":"invalid_arguments","code":"view_not_found",
         "message":"store has no view 18c75c7b-bb27-4e0c-ac87-596e8855814d"}
```

`StoreViewRetirementRunner.Run` and `StoreMaintenanceRunner.Run` both branched on the exit code
before reading stdout, and reported `exited {code}: {first line of stderr}`. Stderr was empty, so the
precise diagnosis was discarded.

The cost was more than a vague message. Miller already maps `view_not_found` to
`StoreViewRetirementDisposition.AlreadyAbsent` and treats it as success — the view being gone IS the
retirement goal — but that path was unreachable, so a stale `store_members` row pointing at a view
the store no longer has could never be pruned.

Fixed after the v1.25.3 release: both runners parse the stdout report whatever the exit code, and use
the exit code and stderr only when stdout carries no report. Both stuck rows then pruned, taking the
registry to 32 rows with only the two correct refusals left. Two new tests spawn a fake producer that
writes a report and exits 1; both are red without the fix.

`store maintain` exited 1 six times during the first prune run and could not be reproduced afterwards
— `store maintain gc --apply` now succeeds on the same store. Its reporting had the same defect and
got the same fix, so a recurrence will name its own cause.
