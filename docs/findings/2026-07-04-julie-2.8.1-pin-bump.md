## Consumer-side adaptation: Express `router_mount.v1` narrowed to same-file attested routers

v2.8.1's release notes list "Express router mounts" under fixed backend edge cases. The one consumer-
visible behavioral change in the backend-HTTP lane is in `collect_express_mounts`
(`crates/julie-extractors/src/base/framework_structural_facts/node.rs`):

- **v2.8.0** pushed an `express.router_mount.v1` fact for every `app.use("/path", <target>)` whose target
  was not a string/destructuring literal — the `receivers.contains_key(&mount_target)` check only gated
  `same_file_prefixes`; the `MountCandidate` was pushed **outside** that `if`. So v2.8.0 over-emitted mount
  facts for **middleware functions and cross-file imported routers** (the importer cannot attest the
  imported identifier's kind).
- **v2.8.1** tightens the gate to `if receivers.get(&mount_target) != Some(&ReceiverKind::ExpressRouter) { continue; }`
  — the fact is emitted **only when the mount target is an in-file `express.Router()` receiver** (or a
  recognized `import { Router } from "express"` / `require('express').Router()` factory used in-file).
  Upstream tests `express_routes_and_same_file_router_mounts_emit_boundary_facts` and
  `express_middleware_mount_does_not_emit_router_mount_fact` pin both halves of the new contract.

**Decisive live-binary comparison** on the v2.8.0 JsTs group fixture (`app.use("/users", usersRouter)` with
`usersRouter` imported from a sibling `usersRouter.ts`):

| binary | `express.router_mount.v1` emitted? |
| --- | --- |
| `julie-extract 2.8.0` | yes — `server/app.ts`, `mount_target=usersRouter`, `mount_path=/users` |
| `julie-extract 2.8.1` | **no** — cross-file imported router is not attested in-file |

So v2.8.1 **drops cross-file imported-router mount facts**. This is an intentional correctness narrowing
(fixing v2.8.0's middleware/import over-emission), not a Miller bug; Miller consumes the extractor's
contract and must not re-derive the mount (`CLAUDE.md`: Miller does not own parser recognition).

### Fixture + assertion update (`LiveBridgeTraceTests.cs`)

- `WriteJsTsBackendGroup`: the cross-file `usersRouter.ts` + `import { usersRouter }` mount was converted to
  a **same-file** mount — `const usersRouter = express.Router(); usersRouter.get("/:id", …); app.use("/users", usersRouter);`
  all in `server/app.ts`. v2.8.1 emits `express.router_mount.v1` for this shape AND folds the mount prefix
  into the route fact's `effective_route_template` (`/users/:id`, `route_group_prefix=/users`), verified
  live. The `server/usersRouter.ts` file is removed.
- `BackendHttpJsTsGroup_ExpressMountFastifyVueClient_LiveBridges`: the cross-file composition assertions
  (`composedRoutes >= 1`, `HitsInto(graph, "server/usersRouter.ts")`) became the same-file effective-route
  join — `composedRoutes == 0` (an `effective_route_template` route is joined directly, never double-
  composed; see `BackendHttp_route_with_effective_template_is_never_double_composed`) and
  `HitsInto(graph, "server/app.ts")`. The Vue SFC client still bridges the effective `/users/:id` route at
  High, so the `vue` client-language proof is preserved.
- Cross-file mount **composition** is still proven live for the families that still emit cross-file mount
  facts — `axum.nest.v1`, `actix.mount.v1`, `phoenix.forward.v1` — in `BackendHttpV280Group_*` (44 of 46
  scale tests were unaffected by the v2.8.1 scanner changes; only the two Express tests needed adaptation).

### Real-world note (not a Miller defect)

Cross-file `app.use("/api", importedRouter)` is the dominant real-world Express route-organization
pattern. v2.8.1's same-file attestation drops mount facts for it, so Miller can no longer compose `/api`
onto an imported router's routes for Express (the router file's route facts keep their unprefixed
`normalized_route_template`, and no mount fact anchors them). Same-file Express mounts still bridge
correctly (the extractor folds the prefix upstream). This is an upstream extractor characteristic; raising
it with julie-extractors (cross-file router attestation via import resolution) is a product decision, not
a Miller code change.
