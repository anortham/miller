## Open: CI `windows-fast` is red on the release commit

[CI run #344](https://github.com/anortham/miller/actions/runs/31726955506) failed the `windows-fast` job on
`0da4f60a`. Everything else in that run passed: `build-test` and all four `sqlite-vec-aot-spike` legs.
`windows-scale-smoke` and `scale-test` were skipped, `windows-scale-smoke` because it depends on the failed job.

**This is not yet attributed.** Two facts bound the question in opposite directions:

- `windows-fast` passed on the previous commit `a94d7571` in run #342, which points at this commit.
- Runs #342 and #343 executed that SAME commit `a94d7571` and disagreed — #342 fully green, #343 red on
  `windows-scale-smoke`. The Windows jobs are demonstrably not deterministic on this repo, so a single red
  run is not proof of a regression.

The failure could not be reproduced locally. Two attempts, both invalid for the same reason — Release output
had to be redirected to a scratch artifacts path to dodge the file lock, and several tests resolve fixture
paths by walking up from `AppContext.BaseDirectory`:

1. First attempt: 70 failures, all `Could not locate repo root (Miller.slnx)` from `ScaleTestSupport.RepoRoot`.
2. Second attempt with `EROS_WORKSPACE_ROOT` set: 13 failures, all from two path walks that do not honor that
   escape hatch — `SharedSemanticBrokerConnectionFactoryTests.RequireBrokerHostExecutable` and the private
   `DashboardFragmentCachingTests.RepoRoot`.

Neither run reproduced anything from CI. A faithful local Release run needs the build to land in the normal
`bin/` path, which needs the live Miller server stopped.

**Next step:** read the `windows-fast` log from run #344 and either fix the cause or record it as a known
Windows flake with evidence. Until that is done, treat v1.19.0 as published with an unverified Windows CI
signal.

A candidate worth checking first, unproven: `CliDispatchTests.WindowsPipeExists` calls
`Directory.EnumerateFiles(@"\\.\pipe\")` and catches only `IOException` and `UnauthorizedAccessException`. That
call can throw `ArgumentException` on a machine holding a pipe whose name contains characters invalid in a
path, which would turn an intended skip into three errors on a hosted runner and not on a developer machine.
The same pattern exists in `SemanticBrokerScaleTests`, where `windows-fast` never exercised it.
