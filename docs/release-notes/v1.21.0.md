# Miller v1.21.0 Release Notes

- **Audience:** All users. This is a feature release: Miller can now keep
  test verdicts as fresh as the index, and named-workspace reads got
  faster.
- **Release shape:** Continuous-testing feature release. The MCP surface
  grows from nine tools to ten; `tests` is the new one, and it is opt-in
  per workspace and off by default.
- **Pinned extractor:** `julie-extract 2.35.0`, raised from `2.34.1`.
- **Pinned semantic sidecar:** `julie-semantic-sidecar 0.1.0`, unchanged.

## What changed

### Continuous testing

Miller can watch a workspace and keep test verdicts current. The unit of
freshness is a test case, not a run. Every result carries the index
generation and revision it was proved at, in a Miller-owned
`<workspace>/.miller/ct.db` sidecar.

When a file changes, Miller advances the revision and asks the index which
symbols the change can reach. Green cases the change cannot reach carry
their verdict forward; only the impacted cases go stale. A run then
executes the stale set as an explicit test-ID list, so a one-line edit runs
the tests that edit can break instead of the whole suite. An explicit run
also retries every red case, because asking for a run means prove it again.
Automatic runs debounce on the trailing edge (2 seconds,
`MILLER_CT_DEBOUNCE`); changes during a run queue a follow-up rather than
killing a healthy run.

Green requires complete results at the current index key. If impact data is
truncated, degraded, or unavailable, Miller marks everything stale and runs
nothing. There is no whole-suite fallback and no optimistic green. An index
rebuild changes the generation identity, which stales every stored result.

The surface is the `tests` MCP tool
(`status|failures|start|stop|enable|disable|run`) and the matching
`miller tests` CLI verbs. `tests status` is a cheap read: it never creates
`ct.db`, never creates `.miller/ct/`, and never starts the daemon.
JSON contract: [`docs/contracts/tests-cli-v1.md`](../contracts/tests-cli-v1.md).

### Continuous testing is proven on real repositories

Before announcing it, every provider was run against a real repository
outside Miller itself. The evidence ledger is
[the CT cross-repo dogfood finding](../findings/2026-08-21-ct-cross-repo-dogfood.md).

| Ecosystem | Repository | Result |
| --- | --- | --- |
| .NET (`dotnet`/`xunit`/`nunit`/`mstest`) | Miller's own suite | green |
| Rust (`cargo`) | `julie-extractors`, 4,173 cases | 4,172 green, one pre-existing wall-clock flake |
| Python (`pytest`) | `more-itertools`, 736 tests | green |
| JavaScript (`vitest`) | a 48-spec Vue library | 46 green, one genuine repo failure |
| JavaScript (`node-test`) | `razorback`, `classnames` | honest red and honest green |
| JavaScript (`jest`) | `vercel/ms`, 4 suites, 167 cases | green twice over fresh `ct.db`s |

Ten defects the dogfood exposed were fixed in this release:

- **A whole-suite Rust run executed nothing and reported "passed."** A run
  covering every known case handed the provider an empty ID list, and the
  Rust provider's run loop is driven by that list — so no `cargo` process
  started and an empty result set read as passed. Whole-suite is now an
  explicit flag, Rust runs per-target groups under it, a provider given no
  IDs and no command throws, and the coordinator refuses to record `passed`
  for zero results over a non-empty selection. The fail-safes did hold
  while the defect was live: the run surfaced as `partial` with everything
  stale, never as green.
- **Every explicit run rebuilt its compiler cache from scratch.** The
  per-run generation directory was also `CARGO_TARGET_DIR`, so each run
  compiled the crate graph into an empty directory and the reap then
  deleted the warm result — about 8 GB and 3.5 minutes on
  `julie-extractors` before a test could run. Compiler caches now live at a
  project-stable path beside the generations, the reap never touches them,
  and two consecutive provider failures wipe the cache and retry once.
- **A partially-red `node --test` suite marked every file red.** The junit
  parser collapsed the report to one status plus the first failure text and
  stamped that pair on every per-file case. The parser now reads the `file`
  attribute Node writes on each `<testcase>` and groups per file. A report
  with no `file` attributes keeps the old aggregate behavior exactly.
- **`node --test` projects were undiscoverable.** Discovery identified
  `package.json` only by `vitest`/`jest` tokens, so a `node --test`
  repository enabled zero projects. Case discovery now follows Node's own
  documented default patterns, and a script that names positional paths or
  globs replaces those defaults the way Node's command line does.
- **A chained package test script produced a false red.** Appending
  reporter and isolation arguments to a compound `a && b` script does not
  deliver them to the runner that needs them. The provider now refuses to
  append arguments to a script that cannot carry them and runs the local
  runner binary directly instead. A missing binary or a spawn failure fails
  the run with a visible reason rather than a false red.
- **vitest 0.x failed at its own CLI parser.** The provider always passed
  `--cache.dir`; dot-notation options arrived in vitest 1.x. The flag is
  now version-gated.
- **One Python repository became three projects,** because `pyproject.toml`,
  `setup.cfg`, and `tox.ini` each enabled separately. Discovery now keeps
  one pytest project per directory, choosing the config file pytest itself
  reads first.
- **Test fixtures became phantom projects.** A `Cargo.toml` proven to be a
  `[workspace]` member is dropped, and the walk prunes `fixtures`,
  `__fixtures__`, and `testdata`. The real `julie-extractors` layout goes
  from six discovered manifests to one.
- **`tests disable` listed the wrong projects.** It now heads the projects
  it turned off and names the remainder on a `remaining enabled:` line.
  JSON gains `changed_count`/`changed_projects` without changing any
  existing field's meaning.
- **A whole-suite selection blanked the reported selection.** It is now
  named as whole-suite instead.

### Worktrees, and a daemon that stays out of your way

One family daemon adopts registered, opted-in linked worktrees of the same
repository. Each worktree gets its own `ct.db` and its own index-bound
context. Enablement inherits from the main checkout through the git link,
with a local `.miller/ct.disabled` tombstone as the per-worktree opt-out. A
worktree `stop` detaches that worktree only; it never kills the family
daemon.

The daemon now runs from a private per-build copy under
`~/.miller/ct-daemon/`, keyed on every file it copies. A running daemon
therefore never locks the installed binary or your build output — before
this fix, a daemon started from `bin/Release` failed the next build and
blocked a plugin upgrade.

Other bounds: a test process silent for 10 minutes has its process tree
killed and its run failed (the bound is on silence, not total duration, so
a slow suite survives). At most one workspace executes tests at a time,
worktrees included. A wedged main loop is reported from the daemon
record's own stamps — Miller reports it and never watchdogs or kills.
`MILLER_CT=off` is a permanent zero-work guarantee.

### A cross-model review campaign closed clean

Two external reviewers (codex and grok) plus a security pass read the whole
release range before publication. 24 raw findings were verified against the
code; six were accepted, all medium, and all are fixed:

- An unacknowledged `tests run` exited 0 with the standing store verdict.
  Exit 0 now requires an acknowledged submit; "no daemon" falls through to
  the foreground one-shot, and an unacked or rejected submit exits 3 with
  an unknown verdict.
- Duplicate case IDs in one run committed last-write-wins, so a
  delay-enumerated theory whose rows failed then passed recorded a **false
  green**. Results now fold worst-wins at the store-applier chokepoint.
- A sticky truncated impact answer recorded a healthy poll and became a
  silent 4 Hz loop with automatic runs stopped. Consecutive unavailable
  answers now degrade the poll, and the reason reaches `tests status`.
- A malformed command filename threw before the per-command guard and
  crash-looped the daemon across restarts. Bad files are now renamed and
  moved out of the listing.
- The VSTest `--filter` expression escaped only commas, so MSTest DataRow
  display names and trait values broke the expression. The reserved
  grammar is now escaped at both sites.
- Child-process output was buffered without a bound. Capture is now capped
  per stream with a head plus rolling tail, and the stdout result parsers
  refuse a truncated stream loudly rather than risk a wrong verdict.

Full campaign record, including what was refuted and what was deferred:
[`docs/findings/2026-08-22-v1.21.0-review-campaign.md`](../findings/2026-08-22-v1.21.0-review-campaign.md).

### A removed workspace takes its store sidecars with it

A workspace's per-view `content-`, `search-`, and `vector-` sidecars live in
the shared family store, which no `.miller` delete reaches. `workspace
remove` and `workspace prune` now reclaim the whole per-view family,
including every retained vector generation and the freshness stamp. Each
dead view previously pinned roughly 350–410 MB forever. The reclaim is
crash-durable and race-safe: an unfinished reclaim writes an owed record
that the next reclaim, or `workspace prune`, discharges. A skip is reported
in the JSON, never treated as a removal failure.

### Reads are faster

- A read with an explicit `workspace_id` now serves the pinned view
  immediately and refreshes in the background, coalesced to one refresh per
  workspace. Such a read reports `freshness: refresh_pending`.
  `ensure_fresh=true` still blocks.
- `inspect`, `context`, and `impact` serve a readable lagging search
  sidecar instead of rebuilding a projection.
- One-shot CLI reads load reference facts per file rather than loading the
  whole generation. Output is byte-identical; `MILLER_BOUNDED_FACTS=off`
  restores the old load.
- The `context` tool no longer scans every test symbol in the index for
  linkage keys no store has ever contained. The scan is now gated behind a
  costless existence probe.

Measured on this repository: CLI `context` 13.6 s to 7.2 s; CLI `inspect
--depth overview` 4.9 s to about 1.1 s; `trace refs` about 1.25 s.
Diagnosis:
[`docs/findings/2026-08-21-context-latency-diagnosis.md`](../findings/2026-08-21-context-latency-diagnosis.md).

### The telemetry status line is honest

The status line reports a 7-day window, the busiest and slowest tools, and
a drop signal, and it reads one snapshot rather than several.

### Pinned extractor 2.35.0

`julie-extract 2.35.0` adds `store maintain retire-view` — transactional
removal of one dead view's manifest entries and `views` row. It is the
producer half of the dead-view story whose Miller half is the sidecar
reclaim above. Artifact schema 7, SQLite schema 7, extract contract 4,
report schema 3, JSONL 5, and blake3 are all unchanged, so no re-extract is
needed. Adoption evidence:
[`docs/findings/2026-08-22-julie-extract-2.35.0-adoption.md`](../findings/2026-08-22-julie-extract-2.35.0-adoption.md).

## Known limits

These are recorded rather than fixed. None of them can produce a false
green.

- **jest runs under one environment.** Miller invokes jest once with the
  default environment. A repository whose own script runs the same suite
  under several environments gets one pass, not several.
- **Case discovery follows test-file naming.** JavaScript and TypeScript
  cases are found by `*.test.*` / `*.spec.*` or by the paths a script
  names; Python by `test_*.py` / `*_test.py`. A suite named some other way
  reports no cases rather than a false green.
- **`tests run --wait` does not wait for the execution budget.** If another
  workspace holds the user-global budget, the call returns immediately with
  an unknown verdict and a `execution budget held` reason. Poll `tests
  status` in that case.
- **Budget-pause temp directories are not reaped.** `miller-ct-budget-pause-*`
  directories accumulate under the system temp directory and can be deleted
  by hand.
- **An explicit run still rediscovers the project inventory,** because that
  run is currently the only inventory-refresh path. The compiler-cache fix
  removes the dominant cost; the rediscovery pass remains.
- **A daemon automatic-run spawn failure reaches `ct.db` only as a log
  line.** A run-level reason surface needs a schema and contract change.
- **CLI paper cuts:** `workspace open <path>` requires `--path` rather than
  accepting the positional form, and `workspace remove` can leave an
  untracked `.julieignore` in the removed root.

## Upgrade notes

- **Continuous testing does nothing until you ask for it.** It is opt-in per
  workspace (`miller tests enable`) and the daemon starts only from an
  explicit `miller tests serve`, the dashboard, or MCP `tests
  operation=start`. Upgrading changes no behavior for a workspace that
  never enables it.
- An existing `ct.db` from a pre-release build migrates itself in place.
- Re-run `scripts/restore-julie-extract.sh` or
  `scripts/restore-julie-extract.ps1` after updating a source checkout. The
  build guard rejects a missing or stale 2.35.0 binary.
- No re-extract and no forced rescan: the extractor contract constants did
  not move in 2.35.0.
- The MCP tool count goes from nine to ten. A harness that caches the tool
  list should refresh it.
- Restart the CT daemon by hand after rebuilding Miller inside one version.
  `tests status` compares the daemon's version string alone, so a daemon
  that predates a same-version rebuild still reports `version_match: true`.
- `MILLER_SEMANTIC=off` remains a zero-work guarantee, and lexical-only
  output stays byte-identical.
