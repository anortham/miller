# Miller v1.22.1 Release Notes

- **Audience:** All users, especially plugin installs on Windows or on slow, proxied, or metered links.
- **Release shape:** Patch release. No MCP, CLI, or index contract changed; no producer pin moved.
- **Pinned extractor:** `julie-extract 2.35.1`, unchanged.
- **Pinned semantic sidecar:** `julie-semantic-sidecar 0.1.0`, unchanged.
- **Pinned sqlite-vec:** `0.1.9`, unchanged.

## What changed

This patch closes one class of defect: a Miller launch that fails without
leaving any evidence a user can find. A field report on 2026-08-25 could not be
diagnosed from Miller's own logs at all, because neither process in a plugin
launch could report a failure that happened before the server started.

### A stalled download can no longer hang the launcher

The plugin launcher fetches the release archive before `miller` starts. That
download had no bound of any kind: no connect timeout, no idle watchdog, and a
bare pipe that left the promise unsettled when a response body simply stopped
arriving. A stall therefore hung forever with no error, no exit code, and no
output, and the client could only report that the server failed to connect.

The download now carries a connect timeout, and a body that stops delivering is
abandoned after 15 seconds — deliberately shorter than a client's default MCP
startup budget, so the launcher reports and retries while the client is still
waiting. A stalled or reset download retries up to three times.

### The launcher writes a log

Every install stage is now recorded to `~/.miller/logs/launcher-<YYYYMMDD>.log`
and to stderr, which the client captures: resolved version, cache hit or miss,
download progress in MB/s, hash, archive listing, extraction, promotion, spawn,
and child exit. A launch killed part-way through leaves a record that ends at
the stage it died in. The log never throws and is retained for 14 days.

A cache miss also says plainly that a large download is starting, and names the
`MCP_TIMEOUT` setting that bounds it.

### `miller` records a startup failure instead of dying silently

`miller` assigned its logger partway through startup and had no top-level catch.
Any failure above that point — resolving the workspace, the sensitive-root
guard, creating the log directory — ended the process with nothing written
anywhere, and a failure below it was equally unreported.

Startup now tracks a named stage and captures every failure. The record always
reaches stderr, then appends a `role:startup` line to the first writable
location of the resolved log directory, `~/.miller/logs`, or the temp directory.
It never throws, and it never recreates a directory tree that has been removed.

Serilog's own failure channel is enabled to stderr, so a file sink that cannot
open its file no longer yields a healthy-looking Miller writing zero bytes. A
breadcrumb line names this process's log directory unconditionally, so an empty
workspace log is now decisive rather than ambiguous.

Two startup paths that could throw before the logger existed are guarded: a
malformed Windows environment variable in the sensitive-root set is skipped
rather than fatal, and an unrooted user profile fails by name instead of
silently writing Miller's machine state into the launch directory.

### The plugin cache no longer grows without bound

Each version installed into its own cache directory and nothing ever removed the
old ones, so a machine that followed a few releases retained about 430 MB per
dead version indefinitely. The launcher now keeps the version being installed
plus the one other most-recently-used, pruning only on a cache miss so a warm
start pays nothing. Recency comes from a marker stamped on every launch, so a
version another client still uses survives; a locked version is reported rather
than retried.

Leftovers from a killed install — the staging directory and the partial download,
whose cleanup cannot run when a process is terminated — are swept once they are
older than ten minutes.

### Windows install robustness

The archive rename retries the sharing violations Windows raises while a scanner
holds a freshly written file. A missing `tar.exe` now reports what to install
instead of `exit null`, and archive listing and extraction failures report the
spawn error rather than an empty status.

### `tests status` answers the question a reader actually asked

On a workspace without continuous testing, `tests status` reported `projects: 0`
and offered no next step. That zero counted what CT had recorded, not what the
tree contains, so it read as "there are no test projects here" on a repository
full of them. An agent asking whether the tests passed correctly concluded
Miller had nothing to offer and ran the suite by hand.

Status now runs the same project scan the daemon would, writes nothing, and
reports what it found together with `projects_discovered: true` in the JSON. The
compact output names the cheap path first — run the tests directly for a one-off
answer — and only then the enable-and-start path for ongoing verdicts. A tree
with genuinely no test projects still reports `projects: 0`, and that now means
what it says.

The scan runs only for a workspace that has never decided. An opt-out tombstone
or any recorded project row, including a disabled one, is an answer of "no", and
those workspaces are left alone. Measured at about 85 ms on a 3,500-file tree,
and status still creates no `ct.db`, no `.miller/ct/`, and no daemon.

The `tests` line in the agent routing guidance described only safety — cheap,
explicit, opt-in — and never what the tool gives you. Both the embedded server
instructions and the session-start routing block now lead with the capability.

### Enabling CT where it cannot work now fails instead of pretending

`tests enable` on a repository with no supported test toolchain — Go, Ruby, Java,
PHP — reported `enable 0 project(s)`, exited `0`, and wrote the opt-in marker.
The workspace was then permanently `enabled: true` with `projects: 0`: a state
nothing could ever move, and one where the status guidance is suppressed by the
very marker the failed enable wrote.

That enable now refuses with exit `3` and writes nothing at all, naming the
toolchains that would work. Reversing an opt-out is still allowed, because a
linked worktree of an enabled main checkout has no projects of its own to
discover and refusing would strand it opted out.

`tests enable --project <file>` had a sharper version of the same fault: any
existing file was accepted. Pointing it at `go.mod` enabled a Go module file as a
test project with a null framework, rendered as `(unknown)`, that no provider
could ever run. A file with no identifiable framework is now refused. A `.csproj`
whose contents name no test package is still accepted — it runs under
`dotnet test` regardless, and that fallback was deliberate.

A workspace already stuck in the enabled-with-nothing state now says so, and says
how to turn it back off.

### A Scale guard measured the wrong assemblies on Linux

The continuous-testing launcher Scale tests refuse to run when the built output
predates the source they would exercise. That guard globbed `Miller.*.dll`, but
Miller.Server's own assembly is `miller.dll` — which a case-sensitive filesystem
does not match. On Linux the guard therefore measured only the referenced
projects: a change confined to Miller.Server failed as stale because those
assemblies correctly did not relink, and a stale `miller.dll` beside a fresh
`Miller.Core.dll` would have passed. The match is now case-insensitive.

### Documentation

`docs/install.md` gained a "When the plugin fails to connect" section naming all
three logs a user should read, in order, with the exact Windows and Unix paths
for the client's own MCP log, and how to raise `MCP_TIMEOUT` correctly.

## Upgrade notes

- No producer pin changed. Existing installations need no re-extract and no
  forced rescan for this patch.
- The first launch on this version downloads the new release archive, as every
  version bump does. After it succeeds, the launcher prunes older cached
  versions and may reclaim several hundred megabytes.
- Rebuild and restart a resident Miller server or CT daemon to load the new
  binary. `MILLER_SEMANTIC=off` remains a permanent zero-work guarantee, and
  lexical-only output remains byte-identical.

## Verification

- Linux Release build passed with zero warnings and zero errors.
- Linux fast and Scale suites passed with no failures.
- The `tests status` contract change is additive at `schema_version` 1:
  `projects_discovered` is new, and `projects` is populated on a never-decided
  workspace. See `docs/contracts/tests-cli-v1.md`.
- Plugin validation passed, including new coverage for the launcher log, the
  connect and idle timeouts, mid-body reset cleanup, download retry, cache
  pruning, and killed-install sweeping.
- The startup failure path was exercised directly: a workspace whose `.miller`
  is a file produces exit 70, empty stdout, the failing stage and stack on
  stderr, and a `role:startup` line appended to `~/.miller/logs`.
- This note makes no claim about a Windows CI or Windows local run for this
  patch.
