# Miller v0.4.3 Release Notes

- **Audience:** Fleet orchestrators (Eros) and anyone running `workspace full` / force rebuilds on large
  registered workspaces, especially while `miller serve` instances are reading them.
- **Release shape:** Patch release resolving the 2026-06-11 Eros field report #2 (the openclaw
  `workspace full` that ran 50+ minutes at ~7KB/s and could never finish).
- **Pinned extractor:** `julie-extract 2.4.0` (unchanged).

## What Is Fixed

- **Full rebuilds now build-to-temp and atomically promote — never merge in-place into the served DB.**
  A force scan previously pointed `julie-extract` at the live `symbols.db`; on a multi-GB artifact the
  merge does random indexed reads while live serve readers keep the WAL from checkpointing (the field
  profile: 380MB WAL, per-page `walFindFrame` scans, ~7KB/s effective throughput — days to complete).
  Force scans now extract into a fresh sibling `symbols.db.rebuild` (a pure bulk insert) and
  `FullRebuildPromotion` replaces the live artifact: any temp WAL is folded in, the live DB's stale
  `-wal`/`-shm` are removed (so the promoted file can never pair with cross-inode sidecars), and the
  single self-contained file is overwrite-moved into place (bounded retry for transient Windows sharing).
  A FAILED force scan now leaves the live artifact untouched. Covers every force path through the single
  scan chokepoint: leader full scan, extractor-upgrade rescan, cross-workspace `workspace full`, and
  bootstrap auto-rebuild. Escape hatch: `MILLER_FULL_REBUILD_INPLACE=1` restores the historical in-place
  merge (e.g. when `.miller` cannot hold two artifacts at once).
- **The serve freshness pipeline now survives artifact replacement.** A promoted rebuild restarts julie's
  revision counter, which the revision-only freshness rule could not see, and a long-lived poll connection
  would keep reading the replaced file's old unlinked inode forever. `FreshnessService` now opens a
  transient reader per poll, and the holder/poller track `artifact_metadata.artifact_id` — the index
  rebuilds + swaps when the identity changes even when the revision tied or went backwards. The lock-busy
  `workspace full` wait (`CrossWorkspaceRefreshService`) confirms a live leader's rebuild through the same
  artifact-id arm, so the registry is stamped correctly. Registered-workspace read caches were already
  rebuild-safe (file-stamp cache keys, v0.4.1).

## Field Verification

- Re-running the exact failing case with this build — `miller workspace full --path ~/source/openclaw
  --json` (13,308 files, 660,851 symbols, ~2.0GB artifact) against the artifact still carrying the killed
  scan's 382MB WAL — completed in **50.2s total (43.8s scan)**, exit 0, `status: refreshed`,
  `index_fresh: true`, search + content sidecars current, stale WAL gone, single-file artifact.
