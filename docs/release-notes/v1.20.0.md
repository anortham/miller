# Miller v1.20.0 Release Notes

- **Audience:** All users. This is a feature release: references are now
  resolved at query time, and the index gets smaller.
- **Release shape:** Query-time resolution feature release. The MCP surface
  remains nine tools.
- **Pinned extractor:** `julie-extract 2.34.1`, raised from `2.33.7`.
- **Pinned semantic sidecar:** `julie-semantic-sidecar 0.1.0`, unchanged.

## What changed

### References resolve at query time

Miller no longer waits for the extractor to materialize reference resolution.
`QueryTimeResolver` applies resolution policy v6 to the raw fact tables when a
tool asks, and `RevisionFactCache` keeps the packed symbols, type facts,
imports, and propagation index resident for the pinned generation. Identifiers
stay on disk and stream per query.

What this means in practice:

- A save is served as soon as the delta import commits. There is no resolve
  phase between the import and fresh answers, so the save-to-answer window
  shrinks to the import itself.
- Warm reads measured on this repo: `trace refs` 86–144 ms, `inspect`
  160–200 ms, `impact` 1.0–2.7 s. The first query after a restart loads the
  fact cache once (about 2 s on this repo).
- Answer parity against the old materialized resolution was gated before the
  cutover (`docs/findings/2026-08-18-query-time-resolution-phase1-gates.md`).

### The index is smaller

`julie-extract 2.34.x` (artifact schema 7, JSONL contract 5) stops writing the
materialized resolution tables. A fresh artifact of the same tree is 8.9%
smaller; the whole difference is the removed `identifier_resolutions` table and
its indexes. Existing family stores free the same space internally on their
next writer open.

### Existing stores migrate in place, including wedged ones

`julie-extract 2.34.0` had a regression: a family store written by an earlier
binary hit a permanent "capability snapshot conflict" on every import. The
pinned `2.34.1` fixes it — the writer reaps the retired capability rows on
open, so a pre-2.34.0 store, including one already wedged by 2.34.0,
self-heals with no manual repair and no re-extract.

### Dead-code candidates are removed

The `references candidates` dead-code surface is removed (retired contract:
`docs/contracts/references-candidates-v1.md`). Recorded `dead_code_*` metric
history rows stay readable through an explicit `--metric` on
`miller metrics history`.

## Upgrade notes

- Re-run `scripts/restore-julie-extract.sh` or `scripts/restore-julie-extract.ps1`
  after updating a source checkout. The build guard rejects a missing or stale
  2.34.1 binary.
- Existing workspaces run one extractor-upgrade rescan on first launch. The
  store migrates in place; views keep serving.
- The first query after each restart pays the one-time fact-cache load.
- `MILLER_SEMANTIC=off` remains a zero-work guarantee, and lexical-only output
  stays byte-identical.

## Verification

- The fast suite and the Scale suite passed on the release tree with the
  2.34.1 binary (`docs/findings/2026-08-18-julie-extract-2.34.1-adoption.md`).
- The store self-heal was proven end-to-end against a copy of a real wedged
  store before the pin was taken.
- The release was dogfooded live on this repo: incremental saves, full
  rebuilds, query-time reads, and an off-mode export smoke.
