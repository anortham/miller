# Miller v1.25.0 Release Notes

- **Audience:** Continuous-testing users first — JavaScript, QML, VB.NET, and Go projects gain
  provider coverage and more honest selection and result handling.
- **Release shape:** Stable feature release. Continuous testing remains opt-in and off by default;
  the existing `tests` surface gains provider coverage and additive evidence without a new MCP tool.
- **Pinned extractor:** `julie-extract 2.37.2`, unchanged.
- **Pinned semantic sidecar:** `julie-semantic-sidecar 0.1.0`, unchanged.
- **Pinned sqlite-vec:** `0.1.9`, unchanged.

## What changed

### CT selection now preserves language and identity evidence

Continuous testing now maps Julie's language labels to the correct source-language family and keeps
provider cases joined to their current symbol name and path. Detailed test roles remain available to
selection, so containers and lifecycle symbols are not mistaken for runnable cases.

Incomplete, stale, ambiguous, truncated, unavailable, or otherwise unsupported evidence fails closed
as `Unknown`. A real test file cannot become `KnownEmpty` because its language family or provider
identity was lost, and an unresolved provider case cannot produce a green verdict.

### JavaScript and TypeScript discovery follows the runners

Jest, Vitest, and Node's test runner now use typed, bounded discovery rules. Jest and Vitest support
the documented test-file extensions, including `.mjs`, `.cjs`, `.mts`, and `.cts`, plus supported
literal config arrays. Vitest applies its runner-default excludes when no `exclude` is declared;
an explicit `exclude` replaces those defaults. Jest's `testMatch` and `__tests__` defaults remain
runner-specific, and Vite library `include` is not treated as a test pattern.

Configuration is read but never executed. Unsupported, interpolated, truncated, malformed,
`testRegex`-based, or unknown-version discovery refuses with a provider diagnostic instead of
silently changing the suite. JSON result handling keeps selected files attributed to their discovered
cases, while missing reports and launch failures are surfaced rather than becoming an empty success.

### QML supports CMake/CTest and qmake Qt Quick Test

The `qt-quick-test` provider now covers both supported Qt Quick Test build paths. CMake projects
recognize the Qt Quick Test main-macro family, require static CTest registration, and keep independent
nested projects separate. qmake projects require proven Qt Quick Test evidence and a generated `check`
target before Miller records CT state; they build outside the source tree and use generation-scoped
Qt 5 `xunitxml` or Qt 6 `junitxml` results.

QML case selection remains at CTest-name or qmake-target granularity. Qbs, PySide6, native Qt Test,
device runners, function-level selection, and QML coverage remain outside this release.

### VB.NET and Microsoft.Testing.Platform are first-class .NET paths

`.vbproj` projects now participate in the existing .NET CT inventory with VB-specific language and
symbol identity. MSTest, NUnit, xUnit, the .NET test SDK, and `MSTest.Sdk` signals are classified
without guessing from a file name. Effective runner evidence selects the VSTest or Microsoft.Testing.Platform
backend; MTP uses the built test application and its proven TRX report extension, while VSTest keeps
the `dotnet test` filter path. Parameterized and qualified VB test names retain their provider identity
through discovery, selection, execution, and result parsing.

### Go modules, workspaces, and subtests

The `go` provider discovers one project per `go.mod`. An in-root `go.work` supplies workspace context
without merging modules, and persisted module/workspace identity scopes manifest impact to the cases
that actually belong to that module or workspace. Discovery uses `go list -json` and `go test -list`;
runs group selected top-level `TestXxx` cases by package and use complete `go test -json` verdicts.

Child `t.Run` subtests roll up to their top-level parent and are not independently selectable in V1.
Examples, benchmarks, fuzz targets, and function-level source identity remain outside the current
contract. Go 1.24 or newer and complete module/package metadata are required.

### Final manual-review corrections

The final review pass closed three provider-boundary issues:

- qmake refuses unsafe `TESTARGS` values before make can reinterpret a path as recipe-shell syntax;
- no-config Vitest discovery retains the runner's dependency-tree and tool-directory excludes; and
- Go manifest impact matches the persisted workspace identity instead of treating every descendant as
  a member of the nearest `go.mod` or `go.work`.

## Upgrade notes

- Continuous testing remains opt-in (`.miller/ct.enabled`) and can still be permanently disabled with
  `MILLER_CT=off`. Existing projects keep their framework keys; the new providers use the existing
  `tests` operations and additive evidence fields.
- All producer pins are unchanged, so this release does not require an extractor or semantic-runtime
  pin migration. Restart a resident Miller server or CT daemon to load the new Miller binary.
- Go support requires Go 1.24 or newer. QML qmake support requires a usable qmake/Qt/make toolchain;
  projects without proven runner evidence remain refused rather than enabled with no cases.
- `MILLER_SEMANTIC=off` remains a permanent zero-work guarantee, and lexical-only output remains
  byte-identical.
