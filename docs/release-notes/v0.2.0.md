# Miller v0.2.0 Release Notes

- **Audience:** Developers and coding-agent users using Miller as a local code-intelligence server.
- **Release shape:** Source checkout plus self-contained per-platform release archives.
- **Pinned extractor:** `julie-extract 2.1.3`.

## Product Summary

Miller is the free local code-intelligence core for coding agents. It keeps a current SQLite-backed view of a
workspace and exposes the same structural read paths through MCP and a one-shot CLI.

Use Miller when an agent needs to answer local code questions without spending tokens on broad file reads:

- find symbols, files, source text, docs, logs, and imported web content;
- inspect a symbol or file;
- build a focused context bundle;
- trace structural relationships;
- assess likely impact before a change;
- check workspace freshness and telemetry from a local dashboard.

Miller stays deterministic and embedding-free. Eros remains the higher-level commercial layer for guidance,
confidence/evidence workflows, semantic/vector retrieval, and commercial orchestration.

## What Is In This Release

- MCP stdio server plus matching CLI verbs for `search`, `inspect`, `context`, `impact`, `trace`, `edit`,
  `content`, `workspace`, `dashboard`, `version`, and `serve`.
- Workspace registry and selectors by display ID, unique prefix, full workspace ID, `current`, `primary`, or
  registered root path.
- Default-on symbol search sidecar with C# BM25 ranking retained as the source of ranking truth.
- Content corpus sidecar for workspace source, docs/config, imported external files, and imported web markdown.
- `search --mode source|content|external|web|all-text` for path/line/snippet hits from the content corpus.
- `content import`, `content add-markdown`, `content search`, `content read`, `content list`, `content remove`,
  and `content export` for bounded large-file/web research and future Eros semantic ingestion.
- Stale-checking for workspace-derived content corpus searches so old source/docs/config text fails visibly.
- Shared content-corpus write locking so workspace rebuilds do not race external/web imports or removals.
- Projection-specific read paths so `search`, `inspect`, graph-only `context`, `impact`, non-bridge `trace`,
  and workspace status/list avoid unnecessary full graph hydration.
- Provider-scoped bridge tracing for the current `dotnet-web` surface.
- Loopback dashboard for registered workspaces, index facts, telemetry, latency/failure signals, and refresh
  troubleshooting.
- Cross-platform restore and test wrappers for macOS/Linux shells and Windows PowerShell.

## Release Archives

The release workflow builds one self-contained archive per pinned `julie-extract` platform:
`aarch64-apple-darwin`, `x86_64-apple-darwin`, `x86_64-unknown-linux-gnu`, and `x86_64-pc-windows-msvc`.

The main `miller` binary ships with Native AOT, so a release machine does not need the .NET SDK to run it.
Each archive contains `miller`, the matching `.tools/julie-extract` binary, the packaged dashboard helper
under `dashboard/`, `dashboard/wwwroot/dashboard.css`, `LICENSE`, and `THIRD-PARTY-NOTICES.md`, plus a
`.sha256` sidecar. Download the archive for your platform and its sidecar, verify the checksum, extract, and
point your MCP client at the absolute path of the extracted `miller` binary with the `serve` arg.

## Quick Start

```bash
bash scripts/restore-julie-extract.sh
dotnet build Miller.slnx -c Release
dotnet run --project src/Miller.Server -c Release -- workspace open --path /path/to/repo --full
dotnet run --project src/Miller.Server -c Release -- search "WorkspaceIndexProvider" --limit 5
dotnet run --project src/Miller.Server -c Release -- search "release archive" --mode content --limit 5
dotnet run --project src/Miller.Server -c Release -- dashboard
```

Windows PowerShell:

```powershell
scripts/restore-julie-extract.ps1
dotnet build Miller.slnx -c Release
dotnet run --project src/Miller.Server -c Release -- workspace open --path C:\source\repo --full
dotnet run --project src/Miller.Server -c Release -- search "WorkspaceIndexProvider" --limit 5
```

For MCP source-checkout use, [`mcp-config.json`](../../mcp-config.json) runs:

```bash
dotnet run --project src/Miller.Server -c Release -- serve
```

That means the MCP client machine needs the .NET 10 SDK on `PATH` for the source-checkout path. The packaged
AOT binary in a release archive does not.

## Known Limits

- No embeddings or semantic/vector retrieval in Miller. Use Eros for that product layer.
- Source-region search is opt-in and can fail closed when the region-capable sidecar is missing or stale.
- Ambiguous targets may require a file path, scope, or symbol ID.
- Bridge trace is provider-scoped. The current provider is `dotnet-web`; generic all-language bridge behavior
  is not claimed.
- The packaged `miller` release binary ships with Native AOT; the dashboard helper is still a self-contained
  ASP.NET executable because Razor Components do not currently support Native AOT.
- A rebuilt MCP server appears only after the MCP client restarts the Miller subprocess. Use `miller version`
  and `workspace status`'s `pid` field to confirm which process is live.

## Not In This Release

- Eros workflows, commercial dashboards, or next-action recommendations.
- Semantic/vector retrieval.
- Default-on source-region indexing.
- A Native AOT dashboard executable.
- Hosted accounts, team policy, billing, organization analytics, or remote portfolio search.
