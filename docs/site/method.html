Why Benchmark Method Tools Install GitHub

Process piece

Auditing your own tool with adversarial agents.

Every benchmark a tool author runs on their own tool flatters it. You wrote the tasks, you know the happy paths, and you stop investigating when the numbers look good. Before Miller replaced its predecessor, it went through a different exercise: a structured adversarial audit in which independent agent reviewers were pointed at the code and asked, in effect, to prove the replacement should not happen. It worked — a tool the author believed was finished gave up twelve prioritized defects, two of them P0.

The method is not specific to Miller. It needs a candidate tool, a comparison target, agent sessions you can make genuinely fresh, and the discipline to accept nothing without evidence. This page records the recipe, what it caught, and where it fits relative to benchmarking.

The setup

Fresh eyes, read-only hands.

The audit compared Miller tool-by-tool against the tool it aimed to replace: one broad review of product boundaries and cross-cutting risks, then nine separate reviews — one per MCP tool — each against its counterpart. Every review ran in an ephemeral session: no session persistence, no memory of earlier passes, strict MCP isolation, and read-only access (Read, Grep, Glob — nothing that could run or index either product). The broad review did not count toward any tool-specific pass; each tool got its own fresh reviewer.

Isolation matters in both directions. A reviewer with session history inherits the author's framing; a reviewer with write or execute access starts "fixing" instead of auditing. And the comparison target was never built, indexed, or modified during the audit — its behavior was established from source and recorded artifacts, so the audit could not perturb the thing it was measuring against.

The rules

No claim survives without local evidence.

Reviewer output was treated as hypotheses, not findings. The lead accepted no claim — flattering or damning — until local source, artifact, telemetry, or observed behavior supported it, and every material claim was classified one of four ways: accepted, corrected, rejected, or unproven. The rejected and corrected buckets are the point: agent reviewers confidently mis-read code, and an audit that transcribes reviewer output unverified just swaps one bias for another.

The bar for "Miller replaces the old tool" was written down before the audit and is the part most worth stealing: the replacement stands only when an agent obtains the evidence needed to act correctly with equal or better relevance, fewer calls, fewer returned tokens, lower wall-clock time, explicit uncertainty, and no correctness loss. Capability presence is not parity — "we also have a rename tool" means nothing if the rename can touch a homonym the old tool would have excluded.

What it caught

Twelve real defects in a "finished" tool.

The highest-severity finding was structural, not cosmetic: reference workflows resolved a symbol to an exact identity and then threw the identity away, querying references by bare name — so four tools could return homonym results and a rename could over-reach. It had survived every author-run benchmark because the benchmarks never asked a homonym question. Other accepted findings included hard failures returned as successful plain text (breaking automation's ability to distinguish success from failure), context bundles that omitted implementation bodies, and payloads that bounded rows but not delivered tokens.

Every finding got a written disposition, the fixes became a phased remediation program, and each tool was then re-audited — fresh session again — before its finding closed. The full audit matrix, source proofs included, is committed in the repository.

Where it fits

Audit for defects, benchmark for value.

The audit answers "is this tool correct and complete enough to ship?" It cannot answer "is this tool worth installing?" — that needs measurement against the baseline users actually have, which for a code tool in 2026 is a capable agent with shell access, not a rival product. After remediation, Miller ran that experiment too: same agent, same tasks, same budgets, with and without the tool. The result — 2.2× correct tasks, 0% vs 27% wrong actions — is written up on the benchmark page.

The recipe, compressed: define the replacement standard in writing first, counting calls, tokens, and correctness — not features. Run one broad plus one-per-surface reviews in fresh, read-only, isolated sessions. Treat reviewer claims as hypotheses; classify every one as accepted, corrected, rejected, or unproven against local evidence. Turn accepted findings into a remediation program; re-audit each surface before closing it. Then benchmark against the honest baseline. None of it requires special tooling — only the willingness to let something try to talk you out of shipping.
