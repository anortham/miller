# Miller v1.21.2 Patch Release Plan

> **For agentic workers:** Use the repository release process in `docs/release-process.md`. Keep package validation and promotion as separate workflow runs so promotion reuses the exact validated artifacts.

**Goal:** Publish Miller v1.21.2 as a stable patch containing the completed continuous-testing and performance hardening since v1.21.1.

**Architecture:** This is a metadata-and-publication release over the already-verified Miller source tree. Producer pins remain unchanged. Package validation builds the full platform matrix once; promotion reuses that successful run.

**Tech Stack:** .NET 10, GitHub Actions, GitHub Releases, Claude/Cursor/Codex plugin manifests.

**Architecture Quality:** No architecture impact. Release prep changes version metadata, documentation, and live-release evidence only.

## Global constraints

- Stable version is exactly `1.21.2` and the tag is `v1.21.2`.
- `julie-extract` stays `2.35.0`.
- `julie-semantic-sidecar` stays `0.1.0`.
- `sqlite-vec` stays `0.1.9`.
- Every plugin manifest and marketplace version stays aligned with `Directory.Build.props`.
- The pushed prep commit and published GitHub release happen in the same working session.
- Use the two-step package-only validation → promotion path; do not publish from a tag-push or an unvalidated run.
- Do not overwrite an existing stable release.
- No final v1.21.2 verification finding is created until live GitHub facts exist.
- Reviewer choice: none.

## Verification strategy

**Project source of truth:** `AGENTS.md` and `docs/release-process.md`.

**Worker red/green scope:** Version-alignment tests, release-note/map assertions, plugin tests, manifest/version inspection, and diff checks.

**Worker ceiling:** Focused release/version/plugin tests only; do not rerun broad suites in the metadata packet.

**Worker gate invariant:** Every advertised version is `1.21.2`; all three producer pins remain unchanged; release notes describe only verified source-tree and local `win-test` evidence.

**Lead affected-change scope:** Release metadata diff, README links, documentation map, plugin smokes, git state, exact-code gate reuse, and live GitHub facts.

**Exact-code gate reuse:** The performance/CT implementation tree has already passed the Release build, Linux fast/Scale, Windows fast/Scale, plugin, and security gates recorded in the performance audit and Windows closure plan. The lead may reuse those results only after proving the release-prep diff contains no production-code or test-behavior changes; version assertions and metadata still receive focused verification. Windows post-fix evidence is the local NTFS guest through `win-test`, not an assumed GitHub result.

**Branch gate:** Run the final Release build, focused version tests, plugin tests/smokes, `git diff --check`, and `cmp -s CLAUDE.md AGENTS.md` on the release-prep tree. Cite the exact-code Linux/Windows fast+Scale results by source SHA when the tree is unchanged.

**Security scope:** `security-secrets`: `gitleaks detect --source . --no-banner --log-opts=HEAD` so unrelated local checkpoint refs are excluded. `security-deps`: `dotnet list Miller.slnx package --vulnerable --include-transitive`. Any secret or high/critical dependency finding blocks publication.

**Release evidence:** Package validation and promotion conclusions are hard gates. Verify four platform archives plus four checksum sidecars, archive checksums, stable release state, notes body, plugin URLs, and version smoke from the published assets.

**Escalation triggers:** Any producer-pin, workflow, package-composition, or source-code change invalidates reused evidence and requires its owning gate. Any missing or contradictory live fact blocks the final verification record.

**Verification ledger:** Record command, SHA, result, timestamps, workflow run IDs, asset names, checksums, release URL, and the local `win-test` evidence reference.

## Parallel execution contract

| Task | Parallel batch | File ownership | Serialization required | Dependency reason |
|---|---|---|---|---|
| Task 1: Prepare metadata and notes | None - serial | Version manifests, README, version tests, v1.21.2 notes, docs map, this plan | Yes | Produces the exact marketplace state to validate and publish. |
| Task 2: Verify release candidate | None - serial | Read-only verification plus corrections to Task 1-owned metadata/docs | Yes | Requires the complete prep diff. |
| Task 3: Integrate and push main | None - serial | Git refs and `origin/main` | Yes | Requires every local gate green and explicit release authorization. |
| Task 4: Validate, promote, and verify | None - serial | GitHub Actions, GitHub Release v1.21.2, and final live-evidence finding | Yes | Promotion consumes the successful package-only run; the final finding consumes live facts. |

### Task 2: Verify release candidate

**Files:** Read-only, except corrections to Task 1-owned metadata and docs.

**What to build:** Prove metadata alignment, documentation accuracy, plugin launch behavior, security gates, and clean release source control. Reuse exact-code gate evidence only after confirming the source tree is unchanged outside release metadata, docs, and version assertions.

**Acceptance criteria:**

- [ ] Release build has 0 warnings and 0 errors.
- [ ] Focused version assertions pass.
- [ ] Plugin tests and required launcher smokes pass.
- [ ] Manifest/version and unchanged-pin checks pass.
- [ ] `git diff --check` and `cmp -s CLAUDE.md AGENTS.md` pass.
- [ ] Gitleaks reports no findings.
- [ ] Dependency audit reports no high/critical vulnerabilities.
- [ ] Exact Linux and Windows fast/Scale gate evidence is cited by source SHA; Windows evidence identifies local `win-test`.

### Task 3: Integrate and push main

**Files:** Git refs and `origin/main`.

**What to build:** Reconcile the release-prep metadata with the verified main tree, commit the intentional release-prep changes, and push `main`. Do not leave `origin/main` advertising `1.21.2` without continuing immediately to package validation.

**Acceptance criteria:**

- [ ] Local `main` and `origin/main` name the exact prep commit.
- [ ] All involved worktrees are clean and no release changes are stranded.
- [ ] The pushed commit contains no unverified source or workflow change.

### Task 4: Validate, promote, and verify

**Files:** GitHub Actions and GitHub Release v1.21.2; add final release evidence locally only after live facts exist.

**What to build:** Run package-only validation, promote that exact successful run without rebuilding, set the release body from `docs/release-notes/v1.21.2.md`, and verify the stable release plus all eight assets.

Package-only validation:

```bash
gh workflow run release.yml \
  -f version=1.21.2 \
  -f prerelease=false \
  -f publish=false \
  -f allow_overwrite=false
```

Promotion of the successful run:

```bash
gh workflow run release.yml \
  -f version=1.21.2 \
  -f prerelease=false \
  -f publish=true \
  -f allow_overwrite=false \
  -f promote_run_id=<successful-package-run-id>
```

Set the release body after publication:

```bash
gh release edit v1.21.2 --notes-file docs/release-notes/v1.21.2.md
```

**Acceptance criteria:**

- [ ] Package-only workflow succeeds for version `1.21.2`.
- [ ] Promotion succeeds using that exact package-only run ID.
- [ ] v1.21.2 is stable, non-draft, and carries the notes file as its body.
- [ ] Four platform archives and four checksum sidecars exist and verify.
- [ ] Marketplace download URLs resolve and version smoke reports `1.21.2`.
- [ ] Final v1.21.2 release verification evidence is written only from live facts, then committed and pushed.
