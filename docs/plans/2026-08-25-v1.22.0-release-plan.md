# Miller v1.22.0 Stable Release Plan

> **For agentic workers:** Use the repository release process in `docs/release-process.md`. Keep package validation and promotion as separate workflow runs so promotion reuses the exact validated artifacts.

**Goal:** Publish Miller v1.22.0 as a stable minor release containing first-class QML indexing/resolution and CMake/CTest Qt Quick Test continuous testing.

**Architecture:** This is a metadata-and-publication release over the QML implementation tree already tested at source SHA `a7e04ecb`. Later commits `0d36b0c7`, `1601a350`, and `496fbb4d` changed documentation and Goldfish memory only. The release must not silently broaden the QML provider beyond CMake/CTest Qt Quick Test.

**Tech Stack:** .NET 10, GitHub Actions, GitHub Releases, Claude/Cursor/Codex plugin manifests.

**Architecture Quality:** No new architecture change is planned. The source behavior is already implemented and verified; this plan covers version alignment, public release documentation, package validation, promotion, and live evidence.

## Global constraints

- Stable version is exactly `1.22.0` and the tag is `v1.22.0`.
- `julie-extract` stays `2.35.1`.
- `julie-semantic-sidecar` stays `0.1.0`.
- `sqlite-vec` stays `0.1.9`.
- `Directory.Build.props`, `miller-plugin.json`, `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`, `.cursor-plugin/plugin.json`, `.codex-plugin/plugin.json`, README release links, and the three literal version-test assertions must agree on `1.22.0`. Leave `.agents/plugins/marketplace.json` unchanged.
- The pushed prep commit and published GitHub release happen in the same working session.
- Use the two-step package-only validation → promotion path; promotion must reuse the exact successful package run and must not rebuild.
- Publish stable with `prerelease=false` and `allow_overwrite=false`; do not overwrite an existing stable release.
- No final v1.22.0 verification finding is created until live GitHub facts exist. The notes and plan may describe local evidence but must not claim publication before it happens.
- The QML CT scope is CMake/CTest Qt Quick Test only. qmake projects, function-level QML coverage, and native QML coverage remain unsupported.

## Verification strategy

**Project source of truth:** `AGENTS.md` and `docs/release-process.md`.

**Worker scope:** Run only the focused Miller version tests, JSON manifest validation, and `git diff --check` for the metadata packet. The lead owns the Release build, plugin/security gates, and exact-code gate reuse.

**Version gate:** Run `dotnet test tests/Miller.Tests/Miller.Tests.csproj --filter "FullyQualifiedName~MillerVersionTests|FullyQualifiedName~CliDispatchTests"` and prove every advertised Miller version is `1.22.0` while Julie remains `2.35.1`.

**Plugin gate:** Validate all five changed JSON manifests and the Claude marketplace plugin entry; run `scripts/test-plugin.sh` plus the required Cursor-style launcher smokes from the release process. `.agents/plugins/marketplace.json` must remain byte-unchanged.

**Source gate reuse:** Reuse the exact-code Linux/Windows evidence at `a7e04ecb` only after proving the release-prep diff contains no production-code or test-behavior changes beyond the two literal version assertions. Those gates are Linux fast 8,462 passed / 9 skipped and Scale 196 passed / 17 skipped; Windows fast 8,446 passed / 25 skipped and Scale 199 passed / 14 skipped. The real Qt fixture remains **NOT VERIFIED** because the available hosts lacked Qt Quick Test development tooling.

**Build and security gates:** The lead must run `dotnet build Miller.slnx -c Release` with 0 warnings/errors, `gitleaks detect --source . --no-banner --log-opts=HEAD`, `dotnet list Miller.slnx package --vulnerable --include-transitive`, and `cmp -s CLAUDE.md AGENTS.md`. Any secret or high/critical dependency finding blocks publication.

**Release evidence:** Package validation and promotion conclusions are hard gates. After publication, verify the stable release state, release-body byte match with `docs/release-notes/v1.22.0.md`, four platform archives plus four checksum sidecars, archive checksums, plugin download URLs, and `miller version` smoke from each published package. Record live facts in a new final verification finding only after they exist.

**Escalation triggers:** Any producer-pin, workflow, package-composition, source-code, test-behavior, or plugin-launcher change invalidates the reused evidence and requires its owning gate. Any missing or contradictory live fact blocks the final verification record.

## Parallel execution contract

| Task | Parallel batch | File ownership | Serialization required | Dependency reason |
|---|---|---|---|---|
| Task 1: Prepare metadata and notes | None - serial | Version manifests, README, version assertions, v1.22.0 notes, docs map, this plan | Yes | Produces the exact marketplace state to validate and publish. |
| Task 2: Validate the release candidate | None - serial | Read-only verification plus corrections to Task 1-owned metadata/docs | Yes | Requires the complete prep diff and source-gate provenance. |
| Task 3: Integrate and push main | None - serial | Git refs and `origin/main` | Yes | Requires every local gate green and explicit release authorization. |
| Task 4: Validate, promote, and verify | None - serial | GitHub Actions, GitHub Release v1.22.0, and the final live-evidence finding | Yes | Promotion consumes the successful package-only run; the final finding consumes live facts. |

### Task 1: Prepare metadata and notes

**What to build:** Bump every advertised Miller version to `1.22.0`; preserve Julie `2.35.1`, semantic sidecar `0.1.0`, and sqlite-vec `0.1.9`; update README archive links; write the QML release notes; and move the docs map to v1.22.0 current with v1.21.2 previous.

**Acceptance criteria:**

- [x] Every changed version manifest and literal assertion reports `1.22.0`.
- [x] README current-release and all four archive links target `v1.22.0`.
- [x] Notes cover QML store/artifact/bounded parity, module/directory/alias/version/internal visibility, user-facing tool evidence, the Qt Quick Test provider, six fixed Grok findings, exact Linux/Windows source-SHA gates, unchanged pins, and explicit NOT VERIFIED/unsupported limits.
- [x] `.agents/plugins/marketplace.json` is unchanged.
- [x] Docs map points to the v1.22.0 plan and notes as current and v1.21.2 as previous.

### Task 2: Validate the release candidate

**What to build:** Prove metadata alignment, documentation accuracy, plugin launch behavior, security gates, and clean release source control. Reuse exact-code gate evidence only after confirming the source tree is unchanged outside release metadata, docs, and the two literal version assertions.

**Acceptance criteria:**

- [x] Focused version tests pass.
- [x] JSON manifest validation, plugin tests/smokes, and unchanged-pin checks pass.
- [x] Release build has 0 warnings and 0 errors.
- [x] `git diff --check` and `cmp -s CLAUDE.md AGENTS.md` pass.
- [x] Gitleaks reports no findings and dependency audit reports no high/critical vulnerabilities.
- [x] Exact Linux/Windows fast/Scale evidence is cited by source SHA `a7e04ecb`; missing Qt tooling is explicitly NOT VERIFIED.

### Task 3: Integrate and push main

**What to build:** Reconcile the release-prep metadata with the verified main tree, commit the intentional prep changes, and push `main`. Do not leave `origin/main` advertising `1.22.0` without continuing immediately to package-only validation.

**Acceptance criteria:**

- [ ] Local `main` and `origin/main` name the exact prep commit.
- [ ] All involved worktrees are clean and no release changes are stranded.
- [ ] The pushed commit contains no unverified source, workflow, producer-pin, or package-composition change.

### Task 4: Validate, promote, and verify

**What to build:** Run package-only validation, promote that exact run without rebuilding, set the release body from `docs/release-notes/v1.22.0.md`, and verify the stable release plus all eight assets.

Package-only validation:

```bash
gh workflow run release.yml \
  -f version=1.22.0 \
  -f prerelease=false \
  -f publish=false \
  -f allow_overwrite=false
```

Promotion of the successful run:

```bash
gh workflow run release.yml \
  -f version=1.22.0 \
  -f prerelease=false \
  -f publish=true \
  -f allow_overwrite=false \
  -f promote_run_id=<successful-package-run-id>
```

Set the release body after publication:

```bash
gh release edit v1.22.0 --notes-file docs/release-notes/v1.22.0.md
```

**Acceptance criteria:**

- [ ] Package-only workflow succeeds for version `1.22.0`.
- [ ] Promotion succeeds using that exact package-only run ID.
- [ ] v1.22.0 is stable, non-draft, and carries the notes file as its body.
- [ ] Four platform archives and four checksum sidecars exist and verify.
- [ ] Marketplace download URLs resolve and version smoke reports `1.22.0`.
- [ ] Final v1.22.0 release verification evidence is written only from live facts, then committed and pushed.
