1. In julie we implemented full cli functionality not just for cli/ci/tool call usage but for making testing easier. Should we do that in miller as well?
2. Dogfooding the mcp server as I develop it means I have the release version of miller connected as the mcp server in session and this means that rebuilding, restarting, reconnecting can be a bit clumsy, is there a way to make that smoother?
3. [search follow-up] Widen the symbol search projection. Miller currently ranks only symbol `name + signature`, even though `julie-extractors` v1 now supplies richer structural facts. Measure and then consider indexing `symbols.doc_comment`, `identifiers.name`, bounded `identifiers.code_context`, `literals.literal_text`, and path tokens into a richer symbol projection. This improves code recall but is not a substitute for document/content search.
4. [search follow-up] Add a content search projection. Julie parity and web-research-style workflows require searching files/docs that may have zero symbols. Treat this as a Miller-owned content/document index sourced from disk through the `files` manifest plus `content_hash` freshness checks. The engine and tokenizer are still measurement questions: start with the search projection spike before choosing in-memory BM25, SQLite FTS5/trigram, Lucene.NET, or another persisted index. Expect symbol/code search and prose/docs search to need different tokenization.
5. [performance follow-up] Measure rebuild and first-read projection cost before adding incremental in-memory patching. Today a single file change can trigger a full `RepositoryIndexLoader.Load`, which reloads symbols, graph edges, bridge data, bridge graph, and search together. First compare full load, current symbol projection, widened symbol projection, and content projection on large/code-heavy plus docs-heavy corpora. Prefer projection-specific loading before per-file patching unless the numbers prove patching is needed. See `docs/plans/2026-06-01-julie-extractors-migration-design.md` §13.
